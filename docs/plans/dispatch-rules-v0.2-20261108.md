# 主脑 / 外脑分层派发标准 v0.2

> 版本：v0.2 ｜ 2026-11-08 ｜ 取代 v0.1（人工驱动、单跑模式）
> 上位规范：G-TASKFLOW-001《任务工作流范式》｜ 图：`docs/diagrams/dispatch-flow-v0.2.html`
> 唯一权威源：`H:\UltimaAI\_shared\paradigms\Ultima-工程铁律清单.md` §10（G-ORCH-001）

## 0. 一句话

主脑只转话与报结果，DeepSeek 编排与审计全流程，Codex 只写代码。审计权不外借。

## 1. 三层职责（不可越界）

### 1.1 主脑（四项，仅此）

1. 传达 Owner 需求——原样转，不加工、不拆解、不改写
2. 最后结果汇报——必须带 tag 名 + commit
3. 本地记忆存储——偏好、历史决策、常用口径
4. 按 Owner 个人习惯的方式交互

**禁止**：判需求对错、拆解、排程、派发、审计、改主表。

### 1.2 外脑 DeepSeek（八环节 + 两支撑，分环节独立上下文）

①理解方案 ②拆解依赖 ③工单制定 ④排程 ⑤分发 ⑥监控心跳 ⑦审计打tag ⑧整体审计
支撑：排程复核（④内第二会话）、异常处置（⚡链）。

**每个环节独立会话**，不与上下环节共用上下文。

口径修正（2026-11-09）：此前写作「独立 Agent / 独立审计」，与实现不符。本机只有一个 DeepSeek 身份，
⑦ 是**同身份模型的二轮质量复核**，是冻结的必要肯定门，不能覆盖确定性校验器的拒绝；
它不是独立第三方检查，也不构成 maker-checker。独立复核的职责由 `scripts/verify-order.py`
的确定性校验承担——同一份代码谁跑都得同一个答案，那才是可替代「第二个人」的部分。

### 1.3 Codex（三项，仅此）

1. 照工单写代码
2. 自检（跑验收命令、提交证据）
3. 提交（commit，**不打 tag**）

**禁止**：任何审查、任何裁决、打 tag、改工单、改主表。自检结果不算验收。

## 2. 八环节与判据

| # | 环节 | 执行者 | 产出 | 通过判据 | 不过怎么办 |
|---|---|---|---|---|---|
| ① | 理解·方案 | DeepSeek | 方案文档 | 目标可验收、边界与不做清单在、拆解骨架含依赖、方案已落盘 | 回①；经主脑转 Owner 批准（门1），不批不下单 |
| ② | 拆解·依赖 | DeepSeek 独立 | 模块清单+依赖图+写域 | 模块↔工单一一对应、依赖无环、写域不重叠、每单有可判定验收门、开源 verdict 已附 | **第1轮自审**：审→修→复验 |
| ③ | 工单制定·审 | DeepSeek 独立 | 工单卡（三段式） | DoR 六项全绿 | **第2轮自审**：审→修→复验；发现拆解本身错 → 回② |
| ④ | 排程·复核 | DeepSeek 两会话 | 执行顺序+复核结论 | 依赖排序正确、WIP 与容量符合、并发=min(cap,可开工单数) | 复核不过 → 回④ 重排 |
| ⑤ | 分发·监控 | DeepSeek 编排+常驻监工 | 派发记录+心跳流 | 派发证据齐才算在跑；心跳 30s；连续 3 次缺失判异常 | 异常 → ⚡ 链 |
| ⑥ | 执行·自检 | Codex | 代码+commit+自检报告 | 验收命令全绿、改动与写域一致、越界声明在 | 自检失败**短路回⑥ 修**，不许硬走到⑦ |
| ⑦ | 审计·打tag | DeepSeek（同身份二轮复核 + 确定性校验器） | 审计结论+tag | 确定性校验全绿；二轮复核 PASS；REVISE≤2 原地修；FAIL 回② | 审计不过一律不打 tag |
| ⑧ | 整体审计 | DeepSeek 跨单 | 整体结论 | 全部工单 tag 齐、跨单接口一致、回归通过 | 不过 → 回② 重定工单与派发 |

## 3. 两轮自审（② 与 ③）

1. 每轮流程：产出 → 自审 → 修（≤2 次）→ 复验 → 放行
2. 修完只复验，**不重开计数**，避免无限循环
3. 两轮都过才进 ④；任一不过不得带病下传
4. 自审由**另一个会话**执行，与产出不同会话；这是**同身份的第二遍**，作用是换一份上下文重新读，不是独立方复核。
   真正的可替代独立复核落在确定性判据上（文件是否真变了、验收命令是否真跑过、树是否还是那棵树）。

## 4. 打回四级

| 级别 | 场景 | 去向 |
|---|---|---|
| L1 原地修 | 要素缺、口径不清、验收门写得不可判定 | 本环节自己改 |
| L2 回上游 | 拆解错、模块划分不合理 | 回② |
| L3 重推 | 结构性错：依赖环、写域冲突、验收不可判定 | 回② 全重来 |
| L4 终止 | 环境不可解、外部阻塞、连续同点失败 | BLOCKED，交人工 |

## 5. 异常退场链（⚡）

**触发**：进程消失 + 无 `final-message.json` + 日志静默超阈值（心跳 30s × 3 = 90s）。
**链路**：常驻监工 Agent（事件驱动、秒级）→ 主脑（收事件、不判）→ DeepSeek 异常处置（判环境/业务、出方案）→ 按方案回 ⑤ 重派。
**性质**：不算业务失败，**不占 REVISE 额度**；同一位置连续 2 次 → 升级人工。

## 6. 心跳与生命周期

- 心跳周期 30s；连续 3 次缺失判异常
- 状态机**对齐已实现的** `tasks/queue_engine/state_machine.py`（**8 态**）：`QUEUED → EXECUTING → SELF-CHECK → AUDIT → COMPLETED`，旁支 `FAILED / BLOCKED / CANCELLED`；合法迁移由 `_ALLOWED` 表 fail-closed 校验
- REVISE 不新增状态：审计 REVISE 走 `FAILED → QUEUED` 重新排队，修复轮次记工单卡 `revise_count`（≤2），不占新状态
- 引擎无「派发中」态（派发与执行瞬时衔接）；如需展示派发窗口，在 run 目录写 `dispatch-record.json` 时间戳，**不改状态枚举**
- 任一状态变更写全局主表；**主表是唯一权威**，看板与镜像只读

## 7. 主脑汇报凭据（硬）

- 必须带 **tag 名 + commit sha**
- 无 tag = 闭环未完成，**不得报"完成"**
- 模板：`<工单号> 已完成｜tag <tag名>｜commit <sha>｜<一句话结论>`
- Owner 验收时可直接 `git show <tag>` 核对，不信任何口头描述

## 8. 人工门（两处，仅此）

| 门 | 位置 | 判据 |
|---|---|---|
| 门1 方案批准 | ① 出方案 → 主脑 → Owner | 不批不下单 |
| 门2 最终验收 | ⑧ 过 → 主脑报（已带 tag）→ Owner 自测 | tag 在门2 之前已打 |

高危动作（删文件、推主分支、付费调用、发布放量）另设即时拦截，不属这两门。

## 9. 接口契约（外脑走 API）

- `POST /dispatch`：工单卡 + 方案路径 + 写域 + 验收命令 + 推理强度
- `GET /report/{task_id}`：状态 + 回执 9 字段 + tag
- 凭证不进工单卡与主表；成本按预算推并发；超时退避接异常退场链

## 12. 与 v0.1 的差异

| 项 | v0.1 | v0.2 |
|---|---|---|
| 驱动方式 | 人工逐单派发 | 主脑转需求 + DeepSeek 编排 |
| 主脑角色 | 组任务包、报结果 | 加本地记忆、按习惯交互 |
| 审计主体 | 混在派发方 | 全部归 DeepSeek，Codex 零审查 |

## 13. 首次试跑结论（wo-orb-w6，2026-11-08）

真实派发两轮：第 1 轮因 `queue-status-gen.py` 校验失败中断（主表 8 条非法状态，已归一 + 备份）；第 2 轮跑通 ⑤⑥，Codex 判 `BLOCKED` 后正确短路（未写报告、未 commit、未打 tag）。详见 `docs/reports/wo-orb-w6-oversight-20261108.md`。

**新增强制口径（试跑换来的）**：

1. **主表只认 6 态**（frozen / pending / executing / audit / blocked / cancelled）。写 `completed`/`interrupted`/`dispatch-ready`/`approved` 会让 `queue-status-gen.py` fail-closed，阻断**任何**派发。
2. **全量测试必须声明收集边界**：默认 `tests/`，仓库根含 `Topo Backup` 等历史目录，根目录收集会产生 3,430 errors（与本单无关）。工单需写死"全量 = `tests/`，`-o addopts=`"，或附成文 ignore 清单。
3. **派发无原子性**：状态先切 executing、进程后起，进程起不来会留下"假执行中"。派发失败须立即回滚 pending，并核查无 exec 进程。
4. **`err.log` 的 `failed to refresh available models` 属噪声**，不代表执行端卡死；判活看 `out.jsonl` 是否增长 + 进程 CPU。
5. **自报数字必须独立复跑**：本次 `14 passed` 复跑一致；但 `done.json` 的 `receipt_valid:false` 说明回执字段契约与派发器期望尚未对齐。
