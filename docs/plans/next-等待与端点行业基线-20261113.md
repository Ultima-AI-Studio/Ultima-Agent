# Next · 等待与端点：行业基线调研（2026-11-13）

> 目的：回答"行业经验里等待（waiting）到底怎么调"。
> 结论先行：**没有任何一家用一个全局"等待值"**，全部是"下限 + 语义/音频确认 + 上限 + 按阶段动态切换"四件套。
> 状态：**建议值，待 Owner 一句确认**后才并入 `next-感知交互参数基线-20261113.md`（本文不改权威基线）。

---

## 一、先分清四种"等待"，混在一起调必然调坏

| # | 等待类型 | 什么时候发生 | 等太久 | 等太短 |
|---|---|---|---|---|
| W1 | **端点等待**（endpointing / EOU） | 用户说完一句，系统判"是否真说完" | 死气沉沉，用户以为断线，说"喂？" | 抢话，把人思考中的停顿当结束 |
| W2 | **无输入等待**（no-input） | 系统问完，等用户开口 | 用户以为没听见 | 话还没起头就被打断/重问 |
| W3 | **会话保持**（session idle） | 多轮之间，没人说话 | 一直占麦、耗电、易误听 | 每次都要重喊唤醒词 |
| W4 | **处理等待**（tool/latency） | 工具慢、模型慢 | 静默卡死 | 频繁"正在处理"变成噪音 |

**行业共识：W1 是决定"像不像人"的那一个**（AssemblyAI 原文：endpointing 延迟"处于链路最前端，在这里花的每一毫秒都是死气"）。

## 二、行业实际数值（逐家口径）

### 2.1 端点等待（W1）

| 来源 | 参数 | 值 | 说明 |
|---|---|---|---|
| AssemblyAI（Universal-3.6 Pro） | `mode=min_latency` | min **128ms** / max **640ms** | 短促确认、IVR 替代 |
| AssemblyAI | `mode=balanced`（默认） | min **128ms** / max **1280ms** | 多数对话 Agent 起点 |
| AssemblyAI | `mode=max_accuracy` | min **512ms** / max **2560ms** | 嘈杂、远场、不能错 |
| LiveKit Agents | `endpointing.min_delay` / `max_delay` | **0.5s / 3.0s**（配音频 turn detector 时 0.3s / 2.5s） | 另提供 `dynamic` 按会话停顿统计自适应 |
| Pipecat | VAD `stop_secs` / SmartTurn 兜底 | **0.2s / 3.0s** | Smart Turn v3 为默认 |
| Deepgram Flux | `eot_threshold` / `eot_timeout_ms` | **0.7 / 5000ms** | 模型内建 end-of-turn |
| Smallest AI（Pulse） | `eou_timeout_ms` | 默认 **600ms**（开 endpointing）/ 800ms（关）；对话场景建议 **1000ms** | 区间 100–10000 |
| Rapida（EOS 三档） | silence-based | 后端默认 **1000ms**、UI 默认 **700ms** | 500–600 极快 / 700–800 平衡 / 1000–1500 从容 / 2000–4000 极耐心 |
| 经典对话系统（Skantze 2021 综述） | 静默阈值 | **700–1000ms** | 因为"轮内停顿平均比轮间间隔更长" |

**人类基准**：Stivers et al. 2009（PNAS，10 种语言）测得答话平均间隔 **约 200ms**（日语最快 ~7ms，丹麦语最慢 ~469ms）。这说明：**任何级联式 Agent 都不可能靠"等静默"达到 200ms**。

### 2.2 关键反证：纯静默阈值不可能又快又准

同一份基准（eot-bench，英文操作点）：

| 检测方式 | 300ms 下的误切率 | 600ms 下的误切率 | 5% 误切时的等待 |
|---|---|---|---|
| 纯静默 VAD | **55.6%** | 21.7% | **1600ms** |
| Smart Turn v3.2 | 35.2% | 14.8% | 1051ms |
| Deepgram Flux | 12.9% | 9.9% | 1151ms |
| LiveKit Turn Detector v1 | **9.9%** | **4.5%** | 543ms |

**读法**：想 300ms 就响应，纯静默方案要切掉超过一半的句子；想压到 5% 误切，要等 1.6 秒。**速度与准确在静默阈值上是直接对立的**，必须引入语义/音频判定才能移开这条曲线。

### 2.3 打断与误打断恢复

| 来源 | 参数 | 值 |
|---|---|---|
| LiveKit | `interruption.min_duration` | **0.5s**（另有 `min_words`，默认 0） |
| LiveKit | `false_interruption_timeout` + `resume_false_interruption` | **2.0s**，默认开启恢复 |
| AssemblyAI | `interruption_delay` | 0ms（min_latency）/ **500ms**（balanced、max_accuracy） |
| LiveKit | `interruption.mode` | `adaptive`（音频模型区分"真打断"与"嗯/好"这类附和） |

### 2.4 按阶段动态切换（最实用的行业做法）

- **实体听写期间抬高上限**：AssemblyAI 明确建议"问邮箱/电话/地址时把 `max_turn_silence` 抬到 **2000–4000ms**，拿到答案后再恢复默认"。理由是号码中间必然有停顿，按默认会被切成三段。
- **自适应端点**：LiveKit `endpointing.mode="dynamic"`，按本会话停顿统计做指数滑动平均（`alpha` 默认 0.9）。
- **情绪/场景分档**：Rapida 给的耐心档 2000–4000ms 明确是为"老人、非母语、常中途停顿"的用户。

## 三、对照 Next 现状：我们已有什么、缺什么

| 项 | Next 现状 | 行业对照结论 |
|---|---|---|
| 端点等待下限（min_turn_silence） | **未定义**。只有"轮次间隔 P95 ≤450ms"（那是轮间目标，不是端点判定） | **这是真缺口**。行业 600–800ms 是平衡点，我们连值都没有 |
| 端点等待上限（max_turn_silence 强制收口） | **未定义** | **真缺口**。没有上限时，语义判定失败会无限等 |
| 语义/音频确认 | 已有：混合 VAD（本地 50–100ms 先暂停 + 语义 ~200ms 确认） | **方向对**，但只覆盖"打断判定"，未覆盖"句子说完判定" |
| 打断最小持续 | **300ms** | 比 LiveKit 默认 0.5s 更灵敏；配合语义确认可用，但要靠实测压误打断 |
| 误打断恢复时长 | **未定义**（只有 `voice.barge_in.resume` 事件名） | **真缺口**。行业 2.0s 是通用值 |
| 实体听写抬上限 | **未定义** | 缺。念手机号/邮箱必被切碎 |
| 无输入重问（W2） | 未定义（10s 只是"轮内静默"事件） | 缺。IVR 通例是重问 1–2 次后收口 |
| 会话保持（W3） | **5 分钟**（R-53 已定） | 与智能音箱通行区间一致，**无需改** |
| 处理等待（W4） | 超 2s 先说"正在处理" | 与行业一致，**无需改** |

## 四、建议值（待拍板）

| 参数 | 建议 | 依据 | 可配区间 |
|---|---|---|---|
| `min_turn_silence`（说完下限） | **600ms** | 介于 Rapida 平衡档 700–800 与 AssemblyAI 128ms+语义 之间；中文语速下 600 已少于"听着卡"的阈值 | 400–1200ms |
| `max_turn_silence`（强制收口） | **2500ms** | LiveKit 2.5s（音频检测器档）；低于 Flux 的 5s，避免死等 | 1500–4000ms |
| 语义端点判定 | **开启**，用开源小模型（Pipecat Smart Turn ~8MB ONNX 或 sherpa 同类） | 纯静默 300ms 误切 55.6%，模型可降到 4.5–9.9%；符合"能用开源绝不自研" | 可关（关=退回纯静默） |
| 实体听写抬上限 | 识别到"电话/邮箱/编号/地址"意图时临时抬到 **3000ms**，答完恢复 | AssemblyAI 明确建议 2000–4000ms | 2000–4000ms |
| 误打断恢复 | **2000ms** 内无转写即判误判，恢复播报 | LiveKit 默认 2.0s + resume on | 1000–3000ms |
| 无输入重问（W2） | 10s 无输入 → **轻问一次**（"还需要我做什么吗"）；再 10s 仍无 → 不再追问，保持会话等 5 分钟 | IVR 重问 1–2 次后收口的通例；避免变成催问 | 重问次数 0–2 |
| 自适应端点 | **v1 不做**，只做固定值 + 实体听写切换 | LiveKit dynamic 需会话停顿统计，v1 数据量不足；先固定后自适应 | — |

### 一条设计红线（写进基线时一并带上）

**不许把"等得久"当成"想得深"**。端点等待只影响感知流畅度，与模型能力无关；任务复杂靠"超 2s 先说正在处理"（W4）兜，不靠拉长 W1。
