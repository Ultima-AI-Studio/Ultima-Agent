## 0. 一句话

**把"这句要不要动手"从模型随口判定，改成一个在分类器之前就生效的确定性判据**——顺带修掉 Phase 2 留下的跨轮串话，让同一个请求不再因为上一轮有个未答问题而翻转处置。

## 1. 为什么做（实测基线，非推演）

### 1.1 记录里写的"1~15 秒判定抖动"（L165）实测为**零摇摆**

11 类请求，每句连跑 5 次（`baseline_p5.py` → `baseline_p5.json`）：

| 编号 | 输入 | 5 次分布 | 耗时区间 | 首例回复 |
|---|---|---|---|---|
| D1 | 帮我把桌面的日志整理一下 | query ×5 | 1.5~1.7s | 这个我做不到，这需要真的去执行，属于执行类任务。 |
| X1 | 帮我把日志清理一下 | **task ×5** | 1.0~1.1s | 好的，我现在去安排。已派给策划部… |
| X2 | 帮我整理一下项目文档 | **task ×5** | 1.2~1.3s | 同上 |
| D2 | 帮我把这个文件重命名，可以吗 | **task ×5** | 1.1s | 同上 |
| X3 | 帮我写一份周报 | task ×5 | 1.3~1.4s | 同上 |
| X4 | 帮我把这句话翻译成英文 | query ×5 | 2.6~3.8s | 先生，您需要翻译的句子是什么？ |
| F1 | 帮我把那个弄一下 | clarify ×5 | 1.1~1.5s | 你说的「那个」是指哪一个？ |
| R4 | 什么是市盈率 | query ×5 | 1.4~2.4s | 市盈率是股价除以每股收益的比率… |
| X5 | 给我讲个笑话 | query ×5 | 2.7~3.3s | 不确定您想听哪种笑话… |
| X6 | 帮我查一下今天的新闻 | query ×5 | 2.7~4.9s | 您今天想了解哪方面的新闻？… |
| X7 | 打开浏览器 | query ×5 | 2.5~3.5s | 好的，我马上安排。这需要执行，我将派给外脑处理。 |

**摇摆句数 0/11**。抖动假说是错的——真正的问题比抖动更难堪：**判据对同类表达给出相反结果**。

D1「帮我把**桌面的**日志整理一下」→ 承认做不到；
X1「帮我把日志清理一下」→ 派单。

两句在"主脑能不能做"上没有任何区别，只差"桌面的"三个字，处置完全相反。

### 1.2 根因：兜底挂在分支里，判 task 就绕过

`_ask_query_branch` 入口的求代劳硬兜底（Phase 1 加）只在**判 query 之后**才执行。`ask_once` 的走向是：

```
_classify_intent(query)  ──task──>  _ask_task_branch(query)  → 真派单
                        └─query──>  _ask_query_branch(query) → 兜底生效
```

`_DELEGATED_ACTION_PATTERN`（L442）的取值来自 `_CLAIM_ACTIONS`（L427-430），其中**已包含「重命名」「整理」「删除」「打开」**。也就是说判据本来就覆盖了这些动作——但**它只在 query 分支里被读**。判成 task，判据形同不存在。

### 1.3 0044 工单的"PASS（应派单）"是误追认

0044 工单 §6.3 第 302 行把 D2「帮我把这个文件重命名，可以吗」判 task 记为 `PASS（应派单）`。但 D2 的"重命名"本就在 `_CLAIM_ACTIONS` 内，本该命中兜底。它没命中，只是因为模型先给了 task，绕开了那条路。**这是把分类器的随机结果当成正确行为记进了冻结记录。**

### 1.4 跨轮串话：同一个请求，因上一轮有个未答问题而翻转（Phase 2 遗留）

`_PENDING_CLARIFY` 挂起后，Phase 2 的 `_pending_fill` 把**任何**下一轮输入都当补槽，拼成 `旧请求（补充：新输入）` 再重新分类。

实测（`check_crosstalk.py`）：

| 场景 | 轮次 | 输入 | 实际结果 |
|---|---|---|---|
| A | 轮 1 | 帮我把那个弄一下 | clarify（挂起 referent） |
| A | 轮 2 | **帮我把桌面的日志整理一下** | **task → 派单**（挂起被当补槽吃掉并清空） |
| B 对照 | 单轮 | 帮我把桌面的日志整理一下 | query → 承认做不到 |
| C | 轮 1 | 帮我把那个弄一下 | clarify（挂起） |
| C | 轮 2 | 就是桌面那个日志文件 | task → 派单（有效补槽，符合预期） |

场景 A 的轮 2 是一个**完整的、可独立成立的新请求**，用户已经放弃上一个澄清；它却被当成对「那个」的回答，拼进旧 query 重新分类，结论从"做不到"翻成"派单"。这正是 Phase 2 活体 `/ask` 那条 11.65s 派单的成因。

### 1.5 顺带发现：query 分支的"将来承诺"

X7「打开浏览器」判 query（正确：不该派单），但回复是「好的，我马上安排。这需要执行，我将派给外脑处理。」——**query 分支里出现了派单承诺**。Phase 1 的 `_claim_clean` 只管"已完成"类完成态声明，不管"我这就去做/我将派给…"这类**将来态承诺**。

## 3. 范围冻结

**本阶段只做**：

1. 新增确定性前置判据 `_preclassify_local(query)`，在 `_classify_intent` **之前**生效；命中即走 query 兜底话术，不再调模型分类。
2. 修 `_pending_fill`：第二轮输入若本身是完整新请求，**放弃旧挂起**按新请求独立处理（判据见 §4.2）。
3. 新增将来态承诺剥离，覆盖"我将派给／我马上安排／我这就去做"类表述。
4. 上述三项的单元测试 + 回归。

**本阶段不做**：

1. 不改 `_classify_intent` 自身的判据与提示词（它仍是 query 判定的兜底路径，只是不再是"求代劳"类请求的第一道门）。
2. 不改 `_risk_gate` / `_no_tool_gate`（Phase 1 冻结，本轮零差分）。
3. 不改 `_slot_gate` 的任何判据与澄清话术（Phase 2 冻结）。
4. 不改 `ask_once` 函数签名，不新增落盘状态。
5. 不动 `_ask_task_branch` 的派单机制（`UltimaDispatchTool` 是真派单，本轮只决定"什么请求该进它"）。
6. 不重命名、不重构既有符号；只新增。
7. 不做多任务拆分与主动回报节奏（Phase 4）。
8. 不修模型层反问（P4）。

## 4. 改动明细

### 4.1 `_preclassify_local(query)` —— 确定性求代劳前置

**位置**：`agent_server.py`，常量区（`_DELEGATED_ACTION_PATTERN` 附近），`ask_once` 内于 `_classify_intent` 之前调用。

**判据（三条全部满足才命中，任一不满足返回 None 交还模型）**：

1. **求代劳标记**：`_DELEGATE_HINT` 命中（`帮我|帮你|给我|麻烦你|请` + `把|将|给我`）。
2. **本机动作词**：`_DELEGATED_ACTION_PATTERN` 命中（沿用既有 `_CLAIM_ACTIONS`，不新增动作词）。
3. **不含可交付物产出词**：无 `写|起草|翻译|分析|总结|方案|报告|代码|文档|表格|计划` 等"产出物"词。

命中 → 返回固定话术（复用 Phase 1 既有 text）：

> 这个我做不到，这需要真的去执行，属于执行类任务。

**判据为何是这三条**：主脑派单的对象是策划部/Codex，它要的是"能变成工单的产出物"。上表里"整理日志/清理日志/整理项目文档"产出的是**本机状态变更**，不是工单；"写周报"产出的是**文档**，是可派的。第 3 条正是这条边界的机器化。

> **注**："整理一下项目文档"含"文档"一词，会因第 3 条被放行到模型。这是**有意的保守**：宁可漏拦（回到当前行为），不可误拦（把真任务吞掉）。误拦的代价是主脑失去派单能力，附带本方案 §7 的 D2 争议。

### 4.2 `_pending_fill` 的新请求识别

**位置**：`_pending_fill`（L546）内，在拼接之前。

**判据**：本轮输入同时满足以下两条 → 判定为**新请求**，丢弃 `_PENDING_CLARIFY` 并按新请求独立处理：

1. 长度 ≥ 12 字（补槽通常更短）。
2. 含完整请求结构：`帮我|请你|麻烦|把|将` + 动作词。

实测映射：

| 输入 | 判定 | 依据 |
|---|---|---|
| 帮我把桌面的日志整理一下（14 字） | 新请求 | 含"帮我…一下"完整结构 |
| 就是桌面那个日志文件（9 字） | 补槽 | 长度不足、无请求结构 |
| 应用（2 字） | 补槽 | 同上 |
| 帮我把 D:\logs\a.log 重命名成 b.log | 新请求 | 完整结构 |

丢弃挂起后，该请求走完整链路（含 §4.1 前置判据），D1 类恢复为"承认做不到"。

### 4.3 将来态承诺剥离

**位置**：`_clean_content` 内，与既有 `_PUSHBACK_PATTERN` 剥离同级。

**新增** `_FUTURE_PROMISE_PATTERN`，命中整句删除：

- `我(马上|这就|立刻|现在就)?(去)?安排`
- `我(将|会|要)?(把|将)?(这|那)?(件)?事(派|交给)`
- `(派|交)(给)?(外脑|策划部|执行端)`
- `我(们)?(这边)?(马上|立刻|这就)(处理|跟进|着手)`

**约束**：仅剥离**将来态承诺**，不触碰"已完成"陈述（那由 `_claim_clean` 管）、不触碰澄清话术与兜底话术（那是固定文本，不经 `_clean_content`）。

## 7. Owner 裁决（2026-11-12，已定，采用选项 A）

**D2「帮我把这个文件重命名，可以吗」现在判 task 派单，并被 0044 工单记为 `PASS（应派单）`。按 §4.1 的新判据，它会变成 query 兜底。**

**裁决：选 A —— 统一走兜底，D2 从 task 改为 query。**

理由（Owner 采信）：`_CLAIM_ACTIONS` 本来就把"重命名"算作本机动作词，Phase 1 能力声明原文也写着"不能重命名"。0044 那条 PASS 是在 D2 恰好被判 task 之后追认的，不构成事先约定。统一之后规则只剩一套：**动本机状态 → 承认做不到；产出文档/方案 → 派单**。

**本裁决对既有记录的处置**：0044 工单 §6.3 第 302 行 D2 的 `PASS（应派单）` **就地标注为已被本裁决取代**（写入 0046 工单回执，不改动 0044 原文件正文——0044 已冻结并打 tag，历史记录不重写，只在后续记录中注明裁决）。
