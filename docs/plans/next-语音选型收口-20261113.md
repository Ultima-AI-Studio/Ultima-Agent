## 二、这套现有件，撑不起 Next 的哪几条规格

| Next 规格 | 现有件能不能实现 | 原因 |
|---|---|---|
| §十二 端点等待 800ms / 2500ms | ✅ **能**（已有基础） | v1 的 webrtcvad 就是"**0.8s 静音收尾**"，与我们定的 800ms 同值，有真机实证 |
| §九 G2 待机（KWS 降频 / ASR 关） | ✅ 能 | KWS 与 ASR 本就是两条独立通道 |
| §九 G1 单采集器 | ⚠️ 需重构 | 现在是"唤醒后另起一段录制"，不是单实例订阅制；但改造是结构问题，不是选型问题 |
| §九 G4 **热词表偏置** | ❌ **做不到** | `OfflineRecognizer.from_sense_voice(...)` **没有 hotwords 参数**；sherpa-onnx 的词表偏置（`hotwords_score`）只给 **transducer / streaming zipformer**。全仓也没有任何 `OnlineRecognizer`（已 grep 确认） |
| §八 打断"语义 ~200ms 确认" | ❌ **做不到** | SenseVoice 是**离线整段识别**：`accept_waveform` 整段 → `decode_stream` 出全文。它产不出 partial，200ms 内不可能出语义判断 |
| 首字 ≤800ms（目标 500ms） | ❓ **未知** | 离线识别要等一段音频结束才出字，长句必然超；无实测数据 |
| §十二 语义端点判定（Smart Turn） | ❌ 缺 | 该能力需要 partial/音频片段喂模型，同样受"离线"限制 |

**这就是关键**：末尾三条（热词、打断语义确认、语义端点）**在选型上就被卡死了**，不是实现不够努力。规格写进去了但引擎给不出——正是 v1/v2"文档一套、实现一套"的老毛病。

## 三、可直接定的两项（无需 Owner 拍板，有实测支撑）

### T3 · AEC = 沿用 `pywebrtc-audio`（WebRTC APM3）+ far 参考

- 版本：`pywebrtc-audio==0.2.0`（Apache-2.0，Chrome 同款算法，非自研）
- 关键约束（照抄现有实证，别自己发明）：**`lead_seconds` 必须保持 0**，AEC3 内部延迟估计自适应；实测 far 偏移两次差 400ms 而效果相同 → **不要硬编码标定常数**（lessons-log L134）
- 播放期**不暂停采集**（否则 AEC 无 near 可消），播放期数据只过 DSP 不进 KWS/VAD，避免自声误唤醒
- 已达标：真机 96%、纯回声 99.8% → 满足 §八"说话时必须继续拾音"

### T2 · 实时端点 VAD = **统一到 Silero**，webrtcvad 降为兜底

- 理由：LiveKit/Pipecat 默认都是 Silero；且我们**已经在用** Silero（离线精切），模型文件在位，不需要新增依赖
- 参数沿用实测组（弱麦）：`threshold 0.35` / `min_silence 0.25` / `min_speech 0.2` / window 512 —— **这套是"离线精切"调优出来的**，用于实时端点需在 N-04 重测（阈值可能偏灵敏）
- 端点 **800ms / 2500ms 是策略层计时**，与 VAD 的 `min_silence` 不是一回事：VAD 报"这段是语音/这段是静音"，策略层数静默时长
- webrtcvad 只保留为"Silero 加载失败"时的降级通道（并发 low CPU 场景）

## 四、必须二选一的两项（T1/T5 + G4 绑定）

### 方案 A：双通道（流式 zipformer 实时 + SenseVoice 终稿）

| 通道 | 模型 | 职责 | 解决什么 |
|---|---|---|---|
| 实时 | sherpa-onnx **streaming zipformer bilingual zh-en**（int8） | 出 partial、支持 `hotwords_score` 词表偏置、供端点/打断语义判定 | **G4 热词**、**打断 200ms 语义确认**、**语义端点**、首字延迟 |
| 终稿 | SenseVoice int8（复用现有） | 说完后出高质量终稿（CER 7–10%），纠正流式草稿 | 保住识别质量 |

- 代价：**双模型**（估算 +30–80MB 流式 + 250MB SenseVoice≈ 300MB 级），CPU 双跑；需实测是否越过 E4 红线（常驻 <600MB、空闲 CPU <5%）
- 风险：两模型结果不一致时以谁为准要定规则（建议：终稿覆盖草稿，草稿只用于"打断/端点"这类时序判断，**不进记忆**）
- 好处：**一处收口解决四个问题**（T1、T5、G4、打断语义）

### 方案 B：单模型（只留 SenseVoice）+ 文本层纠错

| 能力 | 做法 |
|---|---|
| G4 热词 | 改成**识别后纠错**：词表 + 拼音相似度/编辑距离替换（"MCP→马克西皮"这类误识别可修） |
| 打断语义确认 | **放弃语义**，退回"能量 + 最短 300ms 时长"（靠 §八 的 2000ms 误判恢复兜底） |
| 语义端点 | 放弃，纯 800/2500ms 计时 |
| 首字延迟 | 只能优化分段（提前 VAD 收口），天花板受离线模型限制 |

- 代价：热词只能"事后纠"不能"事前防"；打断误判率上升（但可恢复）；端点退回纯静默（误切率 21–55% 区间的风险回到我们身上）
- 好处：**单模型、内存最低、结构最简**，与 v1 一致，迁移风险最小

### 我的建议：**方案 A**，但要带一条硬约束

理由：你已定的三条规格（G4 热词、打断语义 200ms、端点语义判定）**在方案 B 下全部要降级或作废**。也就是说选 B 等于**回头改三条已拍板的规则**——这比多装 80MB 模型贵得多。

配套硬约束（防止双模型把体验搞成两套声音）：
1. **草稿不进记忆、不进上下文**，只用于时序判断（打断/端点）；
2. **终稿覆盖草稿**，呈现与记忆只认 SenseVoice 结果；
3. 双模型不一致率要计量（`voice.asr.disagree` 事件），超 5% 说明流式模型不适配，退回 B；
4. 双跑若导致空闲 CPU 越 5% 或常驻越 600MB，**优先砍流式模型的空闲常驻**（按需加载、空闲 5 分钟卸载）。
