## 一、结论先行（建议采用的参数｜**已落表** → `docs/specs/next-感知交互参数基线-20261113.md`）

| 参数 | 我们原来定的 | 调研口径 | **建议值** | 依据 |
|---|---|---|---|---|
| 打断最小持续 | 300ms | 200–300ms（低于 200ms 会被咳嗽/语气词误触发） | **300ms** | 多源一致，300ms 还被写成「打断延迟硬上限」 |
| 打断检测 → 停播 | 未定 | <150ms 才「像人」；TTS flush <60ms；LLM cancel <40ms | **检测 ≤150ms / flush ≤60ms / cancel ≤40ms** | 生产实测预算 |
| 播报淡出 | 未定 | 硬切会出爆音 | **最后 15ms 淡出** | 体感修复 |
| 会话静默超时 | 8s | 主流设备默认 10s（可配 5–15s） | **10s** | 智能音箱 SDK 默认值 |
| 单次监听上限 | 15s | — | **15s**（保留） | 防呆 |
| 唤醒置信阈值 | 0.25 | sherpa 默认 0.25（偏低）；生产调优后 0.72（openWakeWord） | **0.30–0.35 起步 + VAD 门 + 连续 2–3 帧确认**，实测再调 | 0.25 太松，容易电视声误唤醒 |
| 误唤醒目标 | 未定 | <0.5 次/小时；漏唤醒 <5% | **误唤醒 <0.5/h，漏唤醒 <5%** | 行业通行目标 |
| 误打断率 | 未定 | <2% | **<2%** | 生产目标 |
| 打断成功率 | 未定 | >96% | **>96%** | 生产目标 |
| 端到端首字 | ≤800ms | 300–500ms 理想 / 500–800 可接受 / >800 摩擦 | **首字 ≤800ms，目标 500ms** | 体感阈值 |
| 轮次间隔 P95 | 未定 | 200–450ms（人类对话平均间隔 ~200ms） | **P95 ≤450ms** | 对话自然度 |

**两条机制层面的建议（比参数更重要）**：

1. **混合 VAD**：本地快速 VAD（50–100ms）先**暂停** TTS，服务端/语义判定（~200ms）再确认。确认失败就恢复播报——这样误打断率能从 ~11% 降到 ~2%。
2. **状态回滚（state reconciliation）**：打断后必须把「模型以为说完了、用户其实没听到」这一段落回滚掉，否则下一轮会基于用户从没听过的内容继续。这一步最多团队会漏。

## 二、各家实测口径对照（挑关键几条）

| 指标 | 数值 | 来源口径 |
|---|---|---|
| 人类对话轮次间隔 | ~200ms（跨 10 种语言研究） | 语音交互研究 |
| 打断延迟硬上限 | 300ms | 人机对话系统论文（超过则 >50% 用户语句出现不流畅） |
| 打断检测到停播 | <150ms（体感）/ <60ms（flush）/ <40ms（cancel） | 多家语音 Agent 生产实践 |
| 误打断率 | 目标 <2% | 同上 |
| 端到端响应 | 理想 300–500ms；>800ms 用户开始重复；>1.5s 对话崩 | 同上 |
| 唤醒误接受 | <0.5 次/小时 | openWakeWord 生产线实测 |
| 唤醒漏接受 | <5% | 同上 |
| sherpa KWS 默认阈值 | 0.25（`keywords_threshold`） | sherpa-onnx 文档 |
| 唤醒后动态提阈值 | 窗口1（0–5s）+10%，窗口2（5–10s）+20% | 智能音箱 SDK：减少交互中误唤醒 |
| pre-roll 保留 | 1.5s | 防止唤醒后指令头被吞 |
| 前端处理预算 | AEC 20–50ms / 波束 15–40ms / NS 10–30ms | 嵌入式实践 |

**可直接抄的三条工程习惯**：①唤醒后分两阶段提高阈值（减少自己人说话时误唤醒）；②保留 1.5s pre-roll（否则「幂幂，打开…」的「打开」被吞）；③冷却时间必须设，否则一句话触发多次。

## 三、Audio8 TTS（你说的那个新开源项目）

### 3.1 是什么

**Audio8-TTS**（发布方 Edge0 / Audio8-AI），0.6B 参数的多语言 TTS + **零样本语音克隆**，**Apache 2.0**（代码与权重都可商用）。

| 项 | 值 |
|---|---|
| 架构 | DualAR（24 层 slow 预测语义 token + 4 层 fast 预测 codec 码本），血统来自 Fish Audio S2 Pro |
| 采样率 | 44.1 kHz（自带神经 codec，无需另下） |
| 语言 | Preview 11 种 → Realistic 23 种（含中文、粤语、英日韩法德西等） |
| 克隆方式 | 一段参考音频 + **对应的准确转录文本**，零样本 |
| 权重体积 | bf16 约 1.2 GB；ONNX INT4 约 1 GB |
| 硬件 | 推荐 CUDA；**Preview 有官方 ONNX INT4 CPU 路径**（M2 实测约 1 GiB 内存） |
| 服务化 | SGLang Omni 适配器，**OpenAI 兼容 `/v1/audio/speech`**，支持流式 PCM |
| 限制 | 单次输入宜 ≤150 字符；上下文 2048 位置；参考音频 ≤10s；参考转录必须与音频一致 |

**质量（厂商自报，CV3 测试集）**：Audio8 错误率 4.86%，Qwen3-TTS 7.73%，VoxCPM2 5.35%，Higgs TTS 3 4.41%。英文 WER 2.9%，中文 CER 1.8%。**弱项**：泰语 48.57% WER、粤语 31.35% CER——我们主要用中文普通话，弱点不构成阻碍。

### 3.2 对我们意味着什么

**好的一面**：

- 0.6B + 44.1kHz + Apache 2.0，比现在的 CV3 链路更轻、许可更干净；
- **有 OpenAI 兼容接口**，可以按 `plugin.tts.<name>` 的统一契约接进来，调用方不用改；
- 有 CPU 路径（Preview 版 ONNX INT4），没有独显的用户也能跑。

**要小心的一面**：

- **Realistic 版目前没有官方 ONNX/CPU 路线**（社区转换未经验证）；想要 CPU 就得用 Preview（11 语言）；
- 参考转录写错会明显掉相似度——克隆音色时这一段得人工校对，不能靠自动转写糊过去；
- 单次 ≤150 字符，长回复必须分段合成再拼，否则质量掉；
- Apache 2.0 给的是**代码与权重**的许可，**不给音色授权**——克隆任何真人音色都需要本人同意并披露合成音。

### 3.3 建议（不动已冻结的 CV3）

1. **登记为选装插件** `plugin.tts.audio8`，与 `plugin.tts.cv3` 同一契约（`/v1/audio/speech` 兼容），调用方零改动；
2. **v1.0 仍以 CV3 为准**——CV3 音色与参数已冻结，换引擎等于换音色，属变更，不能顺手替换；
3. 先做**A/B 听辨**：同一段文本，CV3 vs Audio8（用同一段参考音），你听过后再决定是否在 v1.1 切换；
4. 若切换，必须同步 `docs/specs/kws-wakeup-params-baseline.md` 并记录变更——这是既有纪律，不因新模型而破例；
5. 优先评估 **Preview 的 ONNX INT4 CPU 路径**（我们用户不一定有独显），Realistic 等官方出 CPU 版再考虑。

## 五、MOSS 系列（补充调研）

### 5.1 MOSS-Live 是什么，能不能用

**`moss-live-1.0`（Beta）**是模思智能（MOSI / OpenMOSS）平台上的**云端实时交互模型**：实时音频 + 实时视频流 → 音频 + 文本，走 `WebSocket /v1/realtime`，当前限时免费。

**结论：不能用。** 它是**云端 API，不是开源权重**——一旦接入，麦克风音频与画面就要离开本机，直接撞 R-24「数据默认不出本机」。除非将来出本地权重，否则不进入选型。

### 5.2 同门里真正能落地的三个开源件

| 模型 | 规格 | 许可 | 对我们的价值 | 建议 |
|---|---|---|---|---|
| **MOSS-TTS-Nano** | 0.1B，48kHz 双声道，纯自回归 Audio Tokenizer + LLM，**4 核 CPU 可流式**，支持音色克隆、中英 | Apache-2.0 | 体积极小、首包快，**低配机器兜底**最合适 | 登记 `plugin.tts.moss_nano`（选装） |
| **MOSS-TTS-Realtime** | 1.7B，**情境感知多轮流式 TTS**：以对话历史 + 用户声学为条件，跨轮保持音色与韵律 | Apache-2.0 | 比单句 TTS 更贴“多轮对话”场景，语气连贯 | 候选，v1.1 评估 |
| **MOSS-Speech** | 真·语音到语音（无文本中间态），arXiv 2510.00499，冻结文本 LLM 骨干 + 模态分层 | 开源（OpenMOSS） | 端到端、情绪保留好 | **不作为核心**，列入 v2 探索 |

### 5.3 为什么「真 S2S」不能当核心

MOSS-Speech 这类模型会**跳过文本中间态**——听起来更自然，但代价是：

1. **没有可审计的中间结果**：意图、路由、裁决都在模型内部，Manager 的探针抓不到「它为什么这么做」；
2. **和主脑/外脑分层冲突**：R-10 定的是「主脑判性质、外脑出方案」，S2S 模型自己就是大脑，等于把两层压成一层；
3. **记忆与习惯的写入点没了**：我们靠文本判断「该不该记」，纯语音链路没有这个抓手。

所以它适合做「v2 的体验实验」，不适合做 v1.0 的骨架。

### 5.4 TTS 候选最终排序（v1.0 只留 CV3）

| 顺位 | 插件 | 定位 | 何时启用 |
|---|---|---|---|
| 1（基线） | `plugin.tts.cv3` | 已冻结音色，v1.0 唯一默认 | 现在 |
| 2 | `plugin.tts.audio8` | 高质量克隆、44.1kHz、OpenAI 兼容接口 | 选装，A/B 听辨后定 |
| 3 | `plugin.tts.moss_nano` | 0.1B CPU 流式，低配兜底 | 选装，无独显用户 |
| 4 | `plugin.tts.moss_realtime` | 多轮语境连贯 | v1.1 评估 |
| 5 | MOSS-Speech（S2S） | 端到端体验实验 | v2 探索，不排期 |
