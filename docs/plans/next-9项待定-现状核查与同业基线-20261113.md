## T4 · KWS 阈值与触发冷却

**现有设置**

- `config\voice-next\live.json`：`threshold=0.25`（v1 现行），`keywords_score=1`、`num_trailing_blanks=1`
- 基线 §七：Next 用 `0.30`（v1 与 Next 有意不同）
- `src\voice-next\kws_backend.py:54-55` 只做范围校验 `0 < threshold <= 1`，**没有冷却逻辑**
- 全仓 grep `cooldown|last_trigger|retrigger|debounce`：只命中 HostShell Guardian（进程冷却），**语音侧零命中** → 「1.5s 触发冷却」目前只存在于基线文档，没有实现

**同业做法**

| 来源 | 数值 |
|---|---|
| sherpa-onnx 官方 KWS 文档 / C API 注释 | `keywords_threshold` 默认 **0.25**；"Larger values are more conservative"；`keywords_score` 默认 1.0 |
| openWakeWord | 默认阈值 **0.5**，官方明确"按环境实测再定" |
| CodeSOTA 关键词唤醒最佳实践 | 检测后 **冷却 2–3 秒**；目标召回 **>95%**、误触发 **<1 次/天** |
| Jinn 唤醒词系统设计 | 误拒 **<5%**、误触发 **<0.5 次/小时**、延迟 **<200ms**、CPU **<10% 单核** |
| Outspoken 训练指南 | 训练期误触发目标 **0.1–1.0 次/小时** 可调 |

**建议**（Next）

- 阈值保持 **0.30**；触发冷却取 **2.0s**（行业 2–3s 的下沿：我们轮间已保持 60s，不需要更长的重唤醒抑制，2s 足够挡住"同一句话连触发两次"）
- 验收沿用现有门：**误唤醒 <0.5/h、漏唤醒 <5%**（与 Jinn 完全同量级，可直接对标）
- 落地要求：冷却必须进 `live.json`（`trigger.cooldown_seconds`），不许再留成文档值

**现有设置**

- `src\brain\ultima-config.toml`：`[agent] max_turns=5`、`[intelligence] max_tokens=8192`、`temperature=0.3`
- `src\brain\bootstrap.py:355-358`：底座默认 10 轮被**强制改成 5 轮**
- **没有**上下文窗口轮次、摘要触发比例、摘要长度、保留原文轮数 —— grep `compress|summariz|history_limit|window_size` 在 `src` 内只命中无关项

**同业做法**

| 来源 | 数值/策略 |
|---|---|
| Context-Engineering 预算规范 | 各上下文类别先分配 token 预算，**预留缓冲 5–10%**；总占用**超 70%** 触发优化 |
| 同类工程实践 | token 利用率 **>80%** 触发 compaction（二次阈值） |
| Microsoft Agent Framework | Truncation 默认保留 `MinimumPreserved=32` 组；SlidingWindow 保留最近 1 组（按"轮"为原子单位，工具调用与结果同进同出） |
| MT-OSC（多轮压缩研究） | 10 轮对话可压 **72% token**，准确率不降 |
| 通识实践 | 长对话必然推掉原始指令，需"定期 reset 或 summarize" |

**建议**（Next）

- 上下文窗口：**10 轮 / 4000 token**（沿用盘点已定），触发压缩点 **70%**（≈2800 token）
- 压缩方式：**只由本地主脑做**（R-19 隐私红线，禁外派）；保留**最近 3 轮原文** + 更早内容摘要
- 摘要长度上限：原文 **30%**；压缩后必带 `context.compacted` 事件，写清压缩前后 token 数
- 硬护栏：压缩前若剩余 <1 轮原文，停止压缩并显式报错（防"压没了"）

**同业做法**

| 来源 | 数值 |
|---|---|
| Dativo Talon 记忆治理 | `retention_days`（超期自动清除）+ `max_entries`（**硬上限**，超限逐出最旧），后台 `StartRetentionLoop()` 周期执行 |
| agent-sh rolling-history | 摘要库 **maxBytes = 50MB**，超限**前置截断**（front-truncation） |
| Hermes Agent 记忆策展 | `MEMORY.md` 硬顶 **~2200 字符**，写满即拒绝写入并要求"先合并" |
| Zylos 状态预算 | working memory 预算 **4–8KB**；system 10–15%、tools 15–20% 固定配额 |

**建议**（Next）

- 双阈值都上：**条目** 30k 警戒 / **60k 硬顶**；**体积** 150MB 警戒 / **300MB 硬顶**
- 硬顶触发动作不是静默删除：先"合并去重"，仍超限才逐出最旧，且必须写逐出审计（沿用现有 `memory-evictions.jsonl`）
- 延迟门：**P95 ≤60ms 通过 / >120ms 告警**；度量点落在 `retrieve(top_k=5)` 单次调用上，作为 N-03 的验收证据
- 一句提醒：条目与体积**必须同时生效**（只卡条目会出现"条数够但每条很长"导致 300MB 被撑爆）

## T10 · 沙箱形态（外部执行隔离）

**现有设置**

- `src\middleware\sandbox.py` `SandboxRunner`：`subprocess` 执行、`timeout_seconds=5.0`、`max_script_bytes` 字节上限、`ticket_id/action_id` 身份校验、`source` 来源校验
- **没有** Job Object、受限令牌、AppContainer、UI 限制 —— 即"进程内超时沙箱"，逃逸即全权

**同业做法**

| 来源 | 做法与数值 |
|---|---|
| Windows Sandboxing（Microsoft） | Job Object 限**活动进程数 / 内存 / CPU / 优先级**；关键 flag：**禁止 job 内进程创建 job 外进程** |
| 同类 CLI 沙箱实现 | `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`；内存 **1GB/进程、2GB/作业**；**活动进程上限 64**；UI 限制（禁桌面句柄）；受限令牌（去 Administrators、中等偏低完整性） |
| Qoder 桌面沙箱 | `CreateRestrictedToken` + 按工作区 **Capability SID 动态注入 DACL**（退出即撤销）+ Job Object 管生命周期 |
| AppContainer | 低完整性 IL，能力受限；适合"真外部不可信代码" |

**建议**（Next）

- **v1 先补 Job Object**：`KILL_ON_JOB_CLOSE` + 活动进程上限 **64** + 内存上限（1GB/进程、2GB/作业）+ 禁 job 内再建 job 外进程
- **v1.1** 再加受限令牌 / AppContainer（较低完整性）给"外部接入"用；v1 的 `timeout 5s` 与字节上限保留不变
- 必须留拒收路径：Job Object 创建失败时**显式拒跑**（不许降级到裸 subprocess 静默放行）

## T13 · 主壳与托管壳的进程边界

**现有设置**

- 双域规范已画两进程：`UltimaAgent.exe`（唯一启动入口）+ `HostShell.exe`（常驻托管壳）
- 0054 已把 Guardian（20s/3/300）**内化进 HostShell**，`config\host-tasks.json` 只管 `agent-server`(guardian) 与 `voice-launcher`(manual)
- **没有**成文职责边界：Console / Manager（另一产品线）与 HostShell 谁管窗口、谁管进程、谁管更新，未定

**同业做法**

| 来源 | 模式 |
|---|---|
| Electron 官方架构 | main process 可信（能做任何事）、renderer 不可信；**IPC 是信任边界上的检查点** |
| Grida 桌面进程模型 | `AgentSidecar` 长期进程持有密钥/会话/agent loop/能力面；Electron 壳只管窗口与 OS；renderer 只经 IPC |
| LobeHub Desktop | main 管生命周期、系统 API、窗口管理；renderer 复用 Web 代码 |
| 通用结论 | 一个进程树 = 一个产品；**不同产品不共享进程边界**，只经 API 对接 |

**建议**（Next）

- 客户端域固定**三进程树**：`UltimaAgent.exe`（壳：窗口/托盘/UI）—IPC— `HostShell.exe`（守护/任务面板/Guardian）—子进程（`agent_server`、voice worker）
- **Console / Manager 不并入客户端进程树**：它们各自独立（各自 user data 目录），只经本地 API（如 18766 登记接口）对接 —— 这条直接消除"两壳互相踢进程"的风险
- 判定口径（可机检）：客户端域内同时只有一个 `UltimaAgent.exe` 与一个 `HostShell.exe`；任一方被外部强杀后由对方或 Guardian 在 20s 内恢复

## 结论

1. **没有一项是"完整已有"**：4 项有半套（T4/T7/T9/T10/T11/T12/T13），1 项空白（T6），1 项"有件但没选"（T8）。

3. **可以立刻收口的是 3 项**：T4（0.30 / 2.0s）、T11（5% 阶梯）、T12（静默参数 + 150% 成文）—— 这三项不依赖实测，定值即可开工。
4. **需要实测才能定值的是 2 项**：T4 的阈值微调、T9 的容量与延迟（都要真机数据）。
5. **T8 已裁决（2026-11-13）：SQLite 主用** —— 落基线 §14.1，含表集/容量/延迟门/七条验收；文件层降为归档。
