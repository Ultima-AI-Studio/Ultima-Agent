# 方案 · 队列体检判据独立审计与修正（2026-11-11）

> 状态：已定稿，随工单 0037 落盘
> 对应工单：`tasks/queue/wo-ultimaagent-20261111-0037--queue-doctor-criteria-audit.md`

## 1. 问题

`scripts/queue-doctor.py` 是 2026-11-11 新建的只读队列体检器，用来回答「队列哪里不一致」。首跑报 92 条 P0，活跃窗口 12 条。逐条复核后发现：**10 条是判据自己造出来的假缺口**。

根因单一：判据把「事实是否存在」判成了「命名是否符合我的约定」。本仓冻结 tag 大量采用 `ultimaagent-<功能>-<日期>` 语义命名，而 `FROZEN_WITHOUT_TAG` 只认「tag 名以工单号开头」，于是已打完的 tag 被判成没打。

后续补了 note-token 兜底，把假阳性这一头压住了。但**假阴性那一头从未被检查**——判据在什么情况下会漏掉真问题，没有任何系统化的验证。

## 2. 为什么不在主脑流程内自修

三条理由：

1. **自审不可靠**。假阳性是我自己的判据造成的，我复核时天然倾向于「判据大体是对的，只是个别命名没适配」，看不到它整体的方法论错误。
2. **漏掉的那一半更危险**。假阳性只浪费人力；假阴性会让真问题长期隐身，而隐身的问题不会自己浮出来。
3. **可证伪性**。独立执行端按「构造反例使之必报/必默」的方式做，结论要么能复现、要么当场被驳倒，不留「我觉得」。

## 3. 判据设计原则（本单要求执行端遵守）

| 原则 | 具体含义 | 反例 |
|---|---|---|
| 判事实，不判命名 | 判据问「这个文件/进程/远端状态是否存在」，不问「它是否按我的命名约定存在」 | 用 `tag.startswith(order)` 判冻结 tag ❌ |
| 证据随身 | 每条 issue 必须带 `evidence`，说清凭什么这么判 | 只输出 `frozen 无 tag`，不给查了什么 ❌ |
| 双向反例 | 每条判据必须有假阳性样本与假阴性样本各一 | 只验证「该报的报了」 ❌ |
| 不可判则标不可判 | 理由无法实测就输出 `unverifiable`，不猜「已过期」 | 见 blocked 理由含「未提交」就判过期 ❌ |
| 数字是结果不是目标 | 不允许为让 P0 归零而调松判据 | 改完 P0=0 但判据变松 ❌ |

## 4. 边界

- 只动 `scripts/queue-doctor.py` 与其新增测试。
- 不动队列数据（`queue-status.json` 一字不改）。
- 不动 `verify-order.py` / `verify-mechanism-change.py` / `dispatch-work-order.py` / `freeze-work-order.py`。
- 不清理 18 张未入库卡、11 个孤儿 run、4 条过期 blocked 理由——本单只负责把它们判准，处置另议。

## 5. 交付判据

1. 判据清单逐条列出且带四栏（断言 / 信号 / 误报条件 / 漏报条件）。
2. 每条判据正负样本各 ≥1，本轮的 10 条假阳性成为回归用例。
3. 全部 issue 带 `evidence`，`--json` 可解析，`--strict` 退出码语义不变。
4. 改造前后全库对比账完整，消失项有因、新增项保留。
5. `pytest scripts/tests` 全绿，且「改回旧写法必红」的反向验证已做。

## 6. 已知风险

- 部分判据缺少可靠的机器可读证据源（例如 `audit_run` 为空但审计确实做过），这类可能只能标 `unverifiable`。允许标不可判，不允许猜。
- 语义命名 tag 与工单号的映射关系没有权威表，只能靠 note 登记 + run 证据反推。若两者都缺，应输出「无法证明」而不是「缺失」。
- `STALE_BLOCKER` 的「理由是否仍成立」部分依赖对理由文本的理解，实测成本高；本单接受它停在 `unverifiable`，但必须写明为什么。
