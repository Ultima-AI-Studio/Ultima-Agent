## 一、唤醒（KWS）

| 参数 | 值 | 类型 | 依据 |
|---|---|---|---|
| 唤醒词 | `幂幂` | 已定 | Owner 2026-11-11 拍板 |
| `keywords_threshold` | **0.30** | 初值 | sherpa-onnx 默认 0.25 偏松（官方默认工作点，非调优值）；生产调优案例落在 0.7 量级但属不同模型不可直搬。取 0.30 = 比默认略严、离漏唤醒尚远，N-04 用实测曲线定点 |
| `keywords_score` | `1` | 已定 | 沿用 v1 取值，不改 |
| `num_trailing_blanks` | `1` | 已定 | 同上 |
| 连续确认帧 | **2–3 帧** | 初值 | 成熟做法：单帧超阈值直接触发会把关门声当唤醒；2–3 帧足够，再多响应变钝 |
| 唤醒后动态阈值 | 0–5s **+10%**，5–10s **+20%** | 已定 | 智能音箱 SDK 默认策略：交互期抬高阈值，减少自己人说话时误唤醒 |
| pre-roll 保留 | **1.5s** | 已定 | 成熟做法：不留 pre-roll 会吞掉唤醒后的指令头 |
| 唤醒响应 | 唤醒词尾 → 系统响应 **≤200ms** | 验收 | 开源唤醒方案生产线目标 |
| 触发冷却 | **2.0s** | 已裁（**R-56 裁决值**；原 1.5s 工程取值作废，入 `live.json`，实测偏离走 §六） | 防一句话触发多次；量级对齐 pre-roll |

**计算口径**：`keywords_threshold` 是置信阈值（越高越难触发），`keywords_score` 是关键词增强分（越高越易检出）。两者方向相反，调参时不可同向调。

## 二、打断（barge-in）

| 参数 | 值 | 类型 | 依据 |
|---|---|---|---|
| 最小持续时长 | **300ms** | 已定 | 多源一致 200–300ms；低于 200ms 咳嗽/语气词/「嗯」会误触发；300ms 同时是「打断延迟硬上限」 |
| 检测 → 停播 | **≤150ms** | 验收 | 生产实测：超过 150ms 用户就感到「它没听见我」 |
| TTS flush（排空缓冲） | **≤60ms** | 验收 | 生产预算 |
| LLM cancel（中止生成） | **≤40ms** | 验收 | 生产预算 |
| 播报淡出 | **最后 15ms 渐隐** | 已定 | 硬切产生爆音/咔嗒声，10–20ms 渐隐即可消除 |
| 检测架构 | **混合 VAD**：本地 VAD **50–100ms** 先暂停播报 → 语义判定 **~200ms** 确认 → 失败则恢复播报 | 已定 | 纯本地误报率约 11%，混合可降到约 2% |
| 状态回滚 | **必须**：回滚「模型以为已说完、用户实际没听到」的片段 | 已定（硬要求） | 不做则下一轮会基于用户从没听过的内容继续 |
| 能量阈值 | **-45 ~ -35 dBFS**；默认 -40，轻声用户 -50 | 初值 | 生产调参区间 |

**两条不可省的工程细节**：① 打断时不硬切音频缓冲，走渐隐；② 被打断的工具调用若为**只读且幂等**可后台跑完，**写操作**（提交/删除/支付）一旦新指令与之矛盾立即取消。

## 三、会话与回复

| 参数 | 值 | 类型 | 依据 |
|---|---|---|---|
| 轮内静默 | **10s**（用户可配 5–15s） | 已定 | 只表示"本轮暂无后续输入"（发 `voice.turn.idle`），**不改状态、不结束会话**；10s 数值沿用智能音箱 SDK 默认 |
| 会话保持时长 | 连续 **60 秒**无任何反馈 → 退出监听回 `ready` | 已定（Owner 2026-11-13，R-53；**R-55 修订：5 分钟 → 60 秒**） | 逐轮退回待唤醒 = 每问一句都要再喊一次唤醒词，**不可接受**；退监听才回 ready |
| 待机时长 | `ready` 内连续 **5 分钟**无唤醒 → 进待机（KWS 降频、ASR 关） | 已定 | 见 §九 G2；与"会话保持"是**两段独立计时**，不叠加（总静默约 **6 分钟**（60s + 300s）才降频） |
| 单次监听上限 | **15s**（单句最长） | 已定 | 防呆上限；超时按"一句结束"处理，**仍在会话内**，不退回待唤醒 |
| 单条语音回复朗读时长 | **<15s**（中文约 4 句上限） | 已定 | 业界主约束是朗读时长不是句数；640 字符截断、建议 <300（Google）；一到两次呼吸读完（Alexa） |
| 慢工具起播 | 超 **2s** 先说「正在处理」，禁用于可能被误解为「已完成」的措辞 | 已定 | 语音 Agent 最佳实践：先说在做，再给结论 |

## 四、验收门（N-04 / N-07 必须逐条实测）

| 门 | 判据 | 测法 |
|---|---|---|
| 误唤醒率 | **<0.5 次/小时** | 24h 负样本连跑（电视/音乐/聊天/厨房噪声） |
| 漏唤醒率 | **<5%** | 正样本 ≥500 条，多说话人、多距离、多噪声 |
| 误打断率 | **<2%** | 「嗯/对」、咳嗽、旁人说话不触发停播 |
| 打断成功率 | **>96%** | 播报中插话，能停住并接到新指令 |
| 首字响应 | **≤800ms（目标 500ms）** | 唤醒词尾 → 首帧音频播出 |
| 轮次间隔 | **P95 ≤450ms** | 用户说完 → 系统开口 |
| 状态回滚正确率 | 无残留：被打断内容不得进入下一轮上下文 | 打断后追问，检查是否复述未播出内容 |

> 口径说明：>800ms 用户开始重复自己，>1.5s 对话崩；人类对话轮次间隔约 200ms，故 450ms 属「可接受」而非「优秀」。

## 六、变更流程（防来回突变）

1. 改任何一项 → 先改本文件并记「变更记录」；
2. 同步 `config\voice-profile.json` 默认值；
3. 一次只动一组参数（唤醒 / 打断 / 会话分开），避免归因不清；
4. 改完跑对应验收门，证据落 `docs\reports\evidence\`；
5. 提交 + 打 tag（`next-voice-params-<日期>`）。

## 八、打断在状态机中的位置（R-46）

### 8.1 先定一件事：不新增"interrupted"态

既有口径是**七态**：`warming → ready → capturing → processing → speaking / acknowledging / stopped / error`。

若为打断新增第八态 `interrupted`，会与全仓"七态"表述冲突——这个坑本项目踩过：stage1 审计第 9 条正是"卡写七态、队列实为八态导致少验一态"。所以**不新增态**，改为：

1. 在 `speaking` 上定义**可中断子标记** `barge_in_armed=true`（只在 TTS 正在出音时为真）；
2. 定义一条**硬迁移边** `speaking → capturing`，`reason=barge_in`；
3. 加一道**回滚闸**：`speaking → capturing` 之后，未完成状态回滚则**禁止进入 `processing`**。

### 8.2 迁移表（含参数与副作用）

| # | From → To | 触发条件 | 门槛参数 | 必须执行的副作用 |
|---|---|---|---|---|
| M1 | `speaking` → `capturing` | 混合 VAD 确认用户插话 | 持续 **300ms** | 停播（检测→停 ≤**150ms**）、TTS flush ≤**60ms**、LLM cancel ≤**40ms**、末 **15ms** 淡出、置 `rollback_pending=true` |
| M2 | `capturing` → `processing` | ASR 出结果 | — | **前置闸**：`rollback_pending` 必须为 false，否则拒绝迁移并记 `barge_in_rollback_missing` |
| M3 | `speaking` → `stopped` | 自然播完，且无插话 | — | 清 `barge_in_armed` |
| M4 | `speaking` → `error` | TTS 输出异常 | — | 保留已播音频索引，供回滚定位 |

**回滚（rollback）的定义**：把"模型以为说完、用户实际没听到"的那一段从本轮上下文中截掉；预算 **≤50ms**（纯本地文本/索引截断，不许调模型）。

### 8.3 三条硬规则

1. **打断不重新唤醒**：用户插话直接接管，不需要再喊「幂幂」；任何"请先唤醒"的提示都属于实现错误。
2. **打断后禁用旧缓冲**：M1 之后旧 TTS 缓冲一律作废，禁止复用（否则会出现"停住了又突然冒出后半句"）。
3. **说话时必须继续拾音**：M1 依赖"边播边听"，因此**AEC 回采参考是硬依赖**——没有回采，TTS 自己的声音会把 `barge_in_armed` 反复触发（自唤醒）。此项在 N-04 与 AEC 方案一并定案。

### 8.4 打断的可观测点（供验收断言）

| 事件名 | 关键字段 | 用途 |
|---|---|---|
| `voice.barge_in.detected` | `t_speech_start` / `rms` / `vad_kind` | 计误打断率 |
| `voice.barge_in.stop` | `t_detect` / `t_stop` / `flush_ms` / `cancel_ms` | 断言 ≤150/60/40ms |
| `voice.barge_in.rollback` | `rolled_chars` / `rollback_ms` / `ok` | 计回滚正确率 |
| `voice.barge_in.resume` | `reason`（`false_positive`） | 误判后恢复播报 |

## 九、输入与在场（G1–G4，Owner 已定 2026-11-13）

### 9.1 四项定值

| # | 项 | 定值 | 备注 |
|---|---|---|---|
| G1 | **麦克风输入源仲裁** | **只设一个采集器**：由它开一路流，KWS 与 ASR **共用同一份音频**；共享模式，不独占；**禁止各模块自行开麦** | 结构性，N-04 |
| G2 | **用户在场检测** | 连续 **5 分钟**无人声 → 进待机（KWS 降频、ASR 关闭）；检测到人声自动回 | 与"静默超时 10s"是两件事：10s 管一轮结束，5min 管人离开 |
| G3 | **媒体 duck** | 唤醒即把正在播放的媒体降到 **20%**（**不暂停**）；播报结束 **500ms** 内恢复原音量 | **初值，实测后微调**（Owner 明确） |
| G4 | **中英混输** | **热词表偏置** + 允许中英双语识别；热词表由**权威源维护**，**禁止硬编码进代码** | 依赖 ASR 供应商定案（N-04） |

### 9.2 落地约束（写进契约，不只是参数）

1. **采集流唯一**：整个进程内只允许存在一个音频采集实例（单例 + 引用计数），KWS/ASR/VAD 全部订阅它；谁想开麦必须先拿同一实例。
2. **禁止独占**：任何模块不得把设备切到独占模式——一旦独占，其他应用（会议、音乐）会直接失声，属于产品事故。
3. **duck 是可恢复的**：恢复动作必须绑在"播报结束事件"上，不能依赖"下次交互"；进程异常退出时由宿主在退出前强制还原音量（不能把用户媒体永久留在 20%）。
4. **热词表接口稳定**：热词表是权威源文件，运行时**只读加载**；更新走权威源变更流程，不进代码常量。
5. **待机可观测**：进出待机都要发事件（`voice.presence.sleep` / `voice.presence.wake`），便于断言"5 分钟"真的生效。

### 9.3 验收（可机检）

| 门 | 判据 |
|---|---|
| 单采集器 | 全进程枚举音频采集实例 = **1**；并发触发 KWS 与 ASR 时，设备打开次数不增加 |
| 无独占 | 采集期间另一应用（如播放器）仍能正常出声 |
| 待机 | 模拟 5 分钟无人声 → 出 `sleep` 事件且 ASR 停止；一声人声 → 出 `wake` 并恢复 |
| duck | 播报期间媒体音量 = 20%±2%；播报结束 500ms 内回到原值；异常退出后回原值 |
| 热词 | 句中含 `MCP / CLI / Codex / A2UI` 各 10 条，识别正确率 ≥90%（N-04 实测口径） |

### 9.4 观测事件

| 事件 | 关键字段 |
|---|---|
| `voice.capture.open` / `close` | `instance_id` / `refcount` / `mode=shared` |
| `voice.presence.sleep` / `wake` | `silence_ms` / `trigger` |
| `voice.duck.apply` / `restore` | `target_pct` / `restored_pct` / `latency_ms` |
| `voice.asr.hotword_hit` | `term` / `hit` |

## 十、运维与体验（G5–G8，Owner 已定 2026-11-13）

### 10.1 定值

| # | 项 | 定值 | 归属 |
|---|---|---|---|
| G5 | **探针事件保留期** | **双条件，先到先清**：超过 **30 天** 或 总量超过 **100MB** → 自动滚动清理（删最旧、分批、不阻塞主链路）；**任务级回执长期保留，不属于清理范围** | 引擎 · Manager（探针是其子能力） |
| G6 | **更新换代必须问用户** | 只要**产生新版本号**（更新迭代出包/权威源出新版），**必须弹确认**：`替换并保存` / `两份都留（标 A/B，旧版只读）` / `放弃新版本`。**未确认不得落盘覆盖；禁止后台静默替换** | 引擎给"发现新版本/冲突"事件 → **客户端弹确认**（交互感知层） |
| G6-2 | **冲突仲裁**（与 G6 分开，属引擎侧规则） | **人工裁决记录 > 变更记录较新者 > 版本号高者**；冲突**必须**出 `pd-` 裁决文件留痕 | 引擎 · 治理与约束 |
| G7 | **习惯条目化可撤销** | 每条习惯 = 一个**条目**（`id` / 规则文本 / `source_turn` / `confidence` / `created_at` / `status`）；用户可**打开「用户习惯」文档浏览全部条目**，可**指定删除某一 条**、或**标为负样本**；删除/负样本后不再读入 | 引擎 · Memory + 客户端/运营出「用户习惯」查看与操作面 |
| G8 | **口播长度预算** | **≤2 句结论**；细节走**卡片**承载；结尾**必须给下一步问询**（"需要我继续做 X / Y 吗？"，候选 1–3 个） | 引擎 · ① 表达与总结（长度）+ 客户端（卡片承载） |

### 10.2 落地约束（硬规则，写进契约）

1. **清理必须自动，不靠人管**。不清理 = 垃圾冗余无限增长（本项之所以存在，就是因为不能等它烂）。清理静默执行，但清掉量超过阈值要发事件，便于事后核对。
2. **清理不碰证据**。探针事件可滚，**任务回执、审计记录、冻结 tag 记录一律长期保留**——那是验收凭据，删了等于把历史抹了。
3. **版本换代"知情同意"**：任何会改变现行版本落盘内容的动作，**先问再动**；用户不知道的情况下出现"两份文件"= 违规。用户选"两份都留"，必须带标记（A/B、旧版只读）并登记索引，否则两份都留会变成垃圾。
4. **习惯是条目，不是黑箱**。用户随时能看"我被记了哪些习惯"，能删能标负样本；**看不到的记忆不算记忆，只算隐患**。
5. **口播不啰嗦，但必须收口**。≤2 句结论 + 细节走卡片 + 结尾给下一步；**问完不要等用户再说"幂幂"**——直接进 `capturing` 听回答。
6. **G8 的自动开麦不是打断**：这是同一轮次内的自然延续，走正常 `speaking → capturing` 迁移，**不计入打断指标**（否则 barge_in 统计会被污染）。

### 10.3 验收（可机检）

| 门 | 判据 |

## 十一、会话保持（R-53，Owner 2026-11-13）

### 11.1 这条要解决的问题

原设计"一轮说完就回 `ready`"——那意味着**用户每问一句都得再喊一次「幂幂」**。这是核心交互的硬伤，不是参数微调。

**改法**：轮次结束**不退出会话**，停在 `capturing` 继续听；只有**连续 60 秒没有任何反馈**才退出监听回 `ready`。（R-55：原定 5 分钟，Owner 下调为 60 秒）

### 11.2 不加态，用子标记区分"待唤醒"与"会话内拾音"

七态口径依然固定。`ready` 与 `capturing` 已经在七态里，两者差别就是**会话是否打开**：

- `ready` = 待唤醒（KWS 全速听唤醒词，ASR 不转写）
- `capturing` + `conversation_open=true` = 会话内拾音（不用唤醒词，VAD 一响就转写）

**待机不是第八态**，只是 `ready` 上的子标记 `standby=true`（KWS 降频、ASR 关闭），恢复即清除。

### 11.3 迁移表（补 M5–M9）

| # | From → To | 触发条件 | 门槛参数 | 必须执行的副作用 |
|---|---|---|---|---|
| M5 | `speaking` → `capturing` | TTS **自然播完**、无插话（正常收口） | — | 置 `conversation_open=true`；清 `barge_in_armed`；继续拾音（采集器不关） |
| M6 | `acknowledging` → `capturing` | 应答播完 | — | 同 M5 |
| M7 | `capturing` → `ready` | 会话内连续 **60 秒**无任何反馈 | **60s**（可配 30–120） | 清 `conversation_open`；本轮会话压实为摘要落记忆；**KWS 保持全速，不进待机** |
| M8 | `ready` → 待机（`standby=true`） | `ready` 内连续 **5 分钟**无唤醒 | 300s | KWS 降频、ASR 关闭（§九 G2）；检测到人声或唤醒词立即解除 |
| M9 | `capturing` → `ready` | 用户**显式退出**（语音「退出 / 别听了」、Esc、点关闭） | — | 立即迁移，不等 60 秒；**静默执行**（不播音、不弹窗） |

**M5 与 M1 的区别**（不要混）：M1 是用户插话打断（`reason=barge_in`，带停播/flush/cancel/回滚）；M5 是系统自己说完（`reason=turn_end`，无副作用）。

### 11.4 六条硬规则

1. **轮结束 = 会话保持**。除 M7（60 秒无反馈）与 M9（用户显式退出），**任何路径不得退回 `ready`**。要求用户"再喊一次唤醒词"= 实现错误。
2. **退监听必须静默**。不播"我先退下了"，不弹提示框——安静环境下突然出声比不响应更糟。
3. **会话内不做 KWS 降频**。降频只在待机（M8）。会话内降频会导致用户小声续说时听不见。
4. **会话内不空转转写**。`capturing` 期间由 VAD 触发才拉起 ASR；60 秒内无人说话不得持续烧 CPU/电。
5. **"是不是在跟我说"由 ① 交互规则层判定**（R-49 Q1 定论）。会话内没有唤醒词作为"对谁说"的信号，判定权必须在①，其它模块不得自判。
6. **上下文不因退监听丢失**。M7 时把会话压实成摘要落记忆；新唤醒开新会话，但可检索上一会话内容（不许"刚聊完就失忆"）。

### 11.5 与打断的关系

打断（M1）之后同样**留在会话内**，不再要求重唤醒（§8.3 第一条）。所以整条交互链是一条连续的 `capturing` 区间：唤醒一次 → 多轮对话 → 打断 → 继续 ← 直到 60 秒无反馈或用户喊停。

### 11.6 验收（可机检）

| 门 | 判据 |
|---|---|
| 多轮不重唤醒 | 连问 3 句（间隔 8s / 20s / 60s）→ 全程状态**不进 `ready`**，无一次"请先唤醒"提示 |
| 60 秒退监听 | 静默 **60s±2s** → 出 `voice.session.close(reason=idle_60s)`，状态转 `ready` |
| 两段计时不叠加 | 退监听后再静默 300s → 才出 `voice.presence.sleep`；总静默约 **360s** 才降频 |
| 响应不退化 | 会话内第 60 秒尾段时的接话响应仍 ≤200ms（证明未降频） |
| 静默退出 | M7/M9 全程无 TTS 输出、无弹窗 |
| 显式退出 | 喊「退出」或按 Esc → ≤200ms 转 `ready` |
| 上下文留存 | M7 后新唤醒提问"我们刚才说到哪" → 能命中上一会话摘要 |
| 空转成本 | 会话内无人说话 60 秒，CPU 增量 ≤ 基线 +5% |

### 11.7 观测事件

| 事件 | 关键字段 |
|---|---|
| `voice.session.open` | `trigger=wake` / `session_id` |
| `voice.turn.idle` | `silence_ms`（**不改状态**，仅记录） |
| `voice.session.close` | `reason=idle_60s\|user_exit` / `duration_s` / `turns` |
| `voice.presence.sleep` / `wake` | 见 §九 |

## 十二、端点等待（调整取向：按智能音箱）

### 12.1 取向说明：为什么按"智能音箱"而不是"电话客服"

**智能音箱**（远场、家庭环境、环境噪、用户边说边做别的事、命令短、可容忍更慢）与**电话 IVR**（近场、安静、要求快、答错代价高）不是同一套手感。本产品是家里的常驻代理，取智能音箱取向：

- **下限比 IVR 更宽容**：IVR 常用 500–600ms，我们取 **800ms**；
- **语义判定必须开**：客厅噪声大，纯静默阈值在 300ms 时误切率高达 55.6%（400–600ms 也有 21.7%），光靠计时器必然抢话；
- **不采用智能音箱的 follow-up 短窗**（Alexa/Google 的"继续说"窗口只有 5–8s）：你已经定了**会话保持 60 秒**（R-53，R-55 修订）；60 秒已远宽于任何 5–8s 短窗，再设短窗只会多插一层踢出逻辑，故不采用。

### 12.2 定值

| 参数 | 值 | 可配区间 | 依据 |
|---|---|---|---|
| `min_turn_silence`（说完下限） | **800ms** | 600–1200 | 智能音箱类产品偏宽容；Rapida 平衡档 700–800ms，远场取上端 |
| `max_turn_silence`（强制收口上限） | **2500ms** | 1500–4000 | LiveKit 音频判定器档 2.5s；不用 Flux 的 5s，避免死等 |
| **语义端点判定** | **开**（开源小模型，Pipecat Smart Turn ~8MB ONNX 或 sherpa 同类） | 可关=退回纯静默 | 纯静默 300ms 误切 55.6% → 模型 4.5–9.9%；可用开源绝不自研 |
| **实体听写模式** | 识别到电话/邮箱/编号/地址意图时，`min` 抬 **1500ms**、`max` 抬 **4000ms**；答完立即恢复 800/2500 | 2000–4000（max） | 号码中间必然停顿，默认值会把它切成三段 |
| **误打断恢复** | 打断后 **2000ms** 内无转写 → 判误判，恢复播报 | 1000–3000 | LiveKit `false_interruption_timeout` 默认 2.0s + resume on |
| **无输入重问** | 10s 无输入 → 轻问 **1 次**（"还需要我做什么吗"）；再 10s 仍无 → **不再追问**，保持会话至 60 秒 | 重问次数 0–2 | 智能音箱/IVR 通例：重问 1 次后收口，禁催问 |
| 自适应端点（dynamic） | **v1 不做** | — | 需本会话停顿统计；v1 数据量不足，先固定值 + 阶段切换 |

**打断最小持续维持 300ms 不改**：我们已有"本地 50–100ms 先暂停 + 语义 ~200ms 确认"的混合判定，等效过滤力度已接近业界 `min_duration=500ms`，无需再抬。

### 12.3 与迁移表的接口（不新加态）

`capturing → processing`（M2）的**前置条件扩展**为 `endpointing_confirmed=true`：

| 触发 | 条件 | 记 `reason` |
|---|---|---|
| 语义判定"说完了" | 模型概率 ≥ 阈值（默认 0.5） | `semantic` |
| 沉默到下限 | 静默 ≥ **800ms** | `silence_min` |
| 沉默到上限（兜底） | 静默 ≥ **2500ms** | `silence_max` |
| 实体听写中 | 改用 1500 / 4000 | `entity_mode` |

三条里任一成立即确认；**未确认前不得进 `processing`**（否则就是抢话）。

### 12.4 六条硬规则

1. **端点判定只判"说完没说"，不判"是不是在跟我说"**。后者归 ① 交互规则层（R-49 Q1），引擎其它模块不得自判。
2. **不许把"等得久"当"想得深"**。等待只影响流畅感；任务复杂靠"超 2s 先说正在处理"兜，不靠拉长端点。
3. **实体听写必须当场退出**：拿到答案立刻恢复 800/2500，禁止模式残留（残留会让后续每句都等 1.5s）。
4. **无输入只重问 1 次**。第二次仍无就别追了——反问会变成催问，家里场景尤其烦人。
5. **语义模型不可用要能降级**，退回纯静默并**发事件** `voice.endpoint.fallback`；禁止静默失效（用户只会觉得"今天很笨"但查不出原因）。
6. **不采用 follow-up 短窗**。会话保持时长以 R-53 的 **60 秒**为准（R-55 修订）。

### 12.5 验收（可机检）

| 门 | 判据 |
|---|---|
| 端点及时 | 说完到进 `processing`：P95 **≤900ms**（800ms 下限 + 100ms 余量） |
| 不误切 | 10 条含 1.2s 中途停顿的测试句 → 误切 **0** 次 |
| 强制收口 | 连续说话不停顿 → 到 2500ms±100ms 强制进 `processing`（不许无限等） |
| 实体听写 | 念 11 位手机号（每 3 位停 1s）→ **一次成句**，不被切成多段 |
| 模式不残留 | 实体听写答完后的下一句：等待恢复 800ms 档（实测端点判定 ≤900ms） |
| 误打断恢复 | 制造一次假打断 → 2000ms 内自动恢复播报且**恢复位置正确**（不重播已播段） |
| 无输入收口 | 10s → 恰好 1 次重问；再 10s → 0 次追问；60 秒 → 退出会话 |
| 降级可用 | 关掉语义模型 → 仍按纯静默工作，且出 `voice.endpoint.fallback` |
| 抢话率 | 连续 20 轮真实对话 → "系统在用户句中途起播" ≤ **1 次** |

### 12.6 观测事件

| 事件 | 关键字段 |
|---|---|
| `voice.endpoint.decided` | `reason=semantic\|silence_min\|silence_max\|entity_mode` / `wait_ms` / `prob` |
| `voice.endpoint.entity_mode` | `on\|off` / `intent` |
| `voice.endpoint.fallback` | `missing_model` / `wait_ms` |
| `voice.noinput.reprompt` | `n`（第几次） / `silence_ms` |

## 十三、语音组件定版与轮间等待（R-55）

> Owner 判定：**现有 KWS / ASR / TTS 跑得挺流畅，不换模型**；本轮只补「每次交互之后的等待」这一层逻辑，且等待时长由 5 分钟下调为 **60 秒**。
> 由此**语音选型收口走 B 案（单模型）**，不再引入 streaming zipformer。本节把"沿用哪个件、降到哪个档"写死，防止 N-04 时又开一次选型会。

### 13.2 轮间等待（本条是本轮唯一新增逻辑）

| 参数 | 值 | 说明 |
|---|---|---|
| 会话保持（轮间等待） | **60 秒**（可配 30–120） | 轮结束后停在 `capturing` 继续听；连续 60 秒无任何反馈 → M7 退监听回 `ready`（R-55） |
| 待机（在场检测） | **5 分钟**（**不动**） | `ready` 内连续 5 分钟无唤醒 → `standby=true`（KWS 降频、ASR 关）；与上一行是**两段独立计时**，总静默约 6 分钟 |
| 轮内静默 | 10 秒 | 只发 `voice.turn.idle`，**不改状态、不结束会话** |
| 显式退出 | 立即 | 用户说「退出/别听了」或 Esc → 立即 M9，**静默不播音** |

**为什么 60 秒够**：等待的目的是"用户想好下一句时不用重喊唤醒词"，人类轮间思考通常在 2–10 秒；60 秒已覆盖"去查个东西再回来问"。留 60 秒还能把空转拾音成本压到 1/5（原 5 分钟一直 `capturing` 持续拾音）。

### 13.3 B 案下三条规格的降级实现（如实登记，不许假装能实现）

| 规格 | 原设计（A 案才有） | **B 案实际做法** | 影响 |
|---|---|---|---|
| G4 热词偏置 | `hotwords_score` 语音级偏置 | **文本层纠错**：权威源词表 + 拼音/编辑距离匹配，命中即替换（如「马克西皮」→「MCP」） | 只能"事后纠"，不能"事前防"；错得太远纠不回 |
| 打断语义确认 200ms | partial 转写后语义判定 | **能量阈值（-40dBFS）+ 最短持续 300ms**，靠 §八 的 **2000ms 误判恢复**兜底 | 误打断率可能高于 2% 目标，需实测确认能否达标 |
| 端点语义判定 | Smart Turn ~8MB | **纯计时 800ms / 2500ms**（§十二 12.2 其余不变） | 语义判定一律记 `voice.endpoint.fallback`，不再假装"开了" |

**一处不改**：打断的 `speaking→capturing(reason=barge_in)` + 回滚闸、300ms 最小持续、150/60/40ms 停机预算**全部有效**——这些是 VAD 级动作，不依赖 partial。

### 13.4 硬规则

1. **不改模型**：N-04 只做"接上现有件 + 加轮间等待"，禁止在 N-04 里换 ASR/TTS。
2. **等待不播音**：60 秒倒计时期间不得有任何提示音/TTS（否则用户以为在催）。
3. **等待可被打断**：60 秒内用户说任何一句即重置计时，不累计。
4. **退出即静默**：M9 不播音、不弹窗、不留"再见"提示。
5. **降级必须留痕**：热词纠错命中、语义端点缺失、误打断恢复，各自发事件，禁止静默降级。
6. **不引入第二套 ASR**：B 案下若有人提议加 streaming 模型，必须回本文 §13.3 与 A 案代价，走变更流程。

| 轮间不重喊 | 连续 5 轮问答，中间停顿 3/10/30 秒，**均不需重新唤醒**；60 秒后第 6 轮需唤醒 |
| 60 秒边界 | 停 55 秒 → 仍可直说；停 65 秒 → 已回 `ready`（出 `voice.session.close(reason=idle_60s)`） |
| 两段不叠加 | 退监听后再静默 300 秒 → 才 `voice.presence.sleep` |
| 等待期静默 | 60 秒倒计时全程 **0 次** TTS/提示音 |
| 热词纠错 | 词表内 20 个词（MCP/CLI/Codex/A2UI 等）念 3 遍，纠对 ≥ 18/20 |
| 端点纯计时 | 说完 → `processing` P95 ≤ 900ms；中途 1.2 秒停顿不误切 |
| 空转成本 | `capturing` 60 秒无人说话，CPU 增量 ≤ 基线 +5% |

### 14.1 T8 存储后端：**已裁决 SQLite 主用**（Owner 2026-11-13）

**裁定**：本地记忆主存储 = 单个 SQLite 文件（WAL 模式），检索 = **FTS5 关键词 + 向量混合**；既有文件式分层存储（`src\brain\memory\layers.py`）**降为导出/归档与迁移来源**，不再作为运行时主链。

**理由**（引自调研文档）：SQLite+FTS5+向量检索 0.3ms 级（本地 Chroma 2.1ms / Weaviate 4.8ms）；≤10 万条暴力余弦 1k≈5–10ms、100k≈50ms，正好覆盖我们 P95 ≤60ms 的门；单文件 + WAL 便于备份，且卸载零残留（对齐双域规范 §三 卸载口径）。

**硬规则**

1. **单一现行实现（M6）**：SQLite 落地后 `layers.py` 只保留导出/迁移入口，**禁止双写双读**。
2. **位置**：`%LOCALAPPDATA%\UltimaAgent\data\memory\store.db`（客户端域内部，不出域）。
3. **最小表集**：`memories(id, layer, text, created_at, last_hit_at, hits, meta)` + `memories_fts`(FTS5) + `memories_vec`(向量列)；三表同一事务维护。
4. **容量**：条目 **30k 警戒 / 60k 硬顶**，文件 **150MB 警戒 / 300MB 硬顶**；硬顶先合并去重、仍超限才逐出最旧，**逐出必写审计**。
5. **top_k 默认 5**（与 `layers.py` 现值一致）；检索超参只在此处定，不许各调用点自定。
6. **延迟度量点**：单次 `retrieve(top_k=5)` 计时；**P95 ≤60ms 通过、>120ms 告警**。
7. **隐私（R-19）**：向量由本地模型产出，**禁止调用任何外部 embedding 服务**。
8. **迁移**：`layers.py` 存量一次性导入 + 条数校验（±0），导入脚本与校验输出进证据目录。

**验收（N-03 必测）**

| 门 | 判据 |
|---|---|
| 单文件 | 新装后 `data\memory` 下只有 `store.db`(+`-wal`/`-shm`)，无散落 json |

| 检索延迟 | 注入 10 万条后 `retrieve` P95 ≤60ms |
| 混合检索 | FTS5 关键词命中不低于基线 95%（向量只做补召回） |

### 14.3 T13 边界口径：壳 / Console / Manager 三分（Owner 2026-11-13）

**裁决**：**Console 与 Manager 都属「能力」**，不是壳、也不是并列的独立产品线。详见 `docs\decisions\pd-20261113-console-manager-能力层归属裁决.md`。

| 层 | 职责 | 禁止 |
|---|---|---|
| 壳（`UltimaAgent.exe` / `HostShell.exe`） | 窗口、托盘、UI 呈现、进程拉起与回收、Guardian 探活 | **零编排、零探针、不判任务状态**，只读展示 |
| **Console**（能力层） | **任务编排**（派发/调度/优先级/依赖）+ **编排后的跟踪** + **反馈**（结果汇总、回写、呈现数据源） | 不直接改 UI 控件；不绕过状态机改队列 state |
| **Manager**（**Console 的子模块**，同进程，Console 是其管理层） | **只两件事**：对任务**下探针** + **反馈任务生命周期**（在跑哪些 / 已完成哪些 / 某任务处于哪一阶段、由哪个执行端在做） | 不编排；不改任务目标；不单独对外；不硬编码执行端厂商 |

数据流：壳触发 → Console 编排 → 下发任务 → Manager 下探针/采集 → 结果回 Console（判态、回写）→ 壳只展示。

**四条硬规则**

1. **进程隔离、产品同属**：Console/Manager 可与壳分进程，但属本产品能力层，不是外挂系统；此前"不并入客户端进程树"的口径作废。
2. **Manager 是 Console 的子模块、不是并列组件**：对外只认 Console 一个门面；Manager 内置同进程运行，起独立进程属架构变更。
3. **探针只有一个下发方**：任务下发后的探针只能由 Manager 发起；壳/Console/语音侧不得各自下探针。
4. **队列唯一状态源不变**：`tasks/queue/queue-status.json` 仍只由状态机写（现有"直接写 state 仅 `state_machine.py` 一处"铁律继续有效）；其他组件问任务态只问 Console，不直连 Manager。

## 十五、进程治理与任务生命周期（Owner 2026-11-13 定调，本节为唯一权威）

> 起因：Next 不得再出现「一堆看门狗、执行完还在跑、查不出孤儿」。**靠机制，不靠窗口**——窗口只做验收面。

### 15.1 四段分离（谁决、谁探、谁做、谁呈）

| 段 | 归属 | 做什么 | 禁止 |
|---|---|---|---|
| 决策/裁决 | **Console 编排模块**（定时能力是其**子模块**，同进程） | 决定哪些该跑、多久跑、超限停谁、优先级；守护目标口径 | 不自己起进程；不绕过壳动系统 |

| 呈现 | **Surface**（四角壳） | 展示体检表：已死未起 / 已起无主 / 多实例 / 停多久 | 不替代机制、不自动处置 |

### 15.5 七道闸（保证不产孤儿，全部可机检）

| 闸 | 做法 | 依据/坑 |
|---|---|---|
| **1 单一父进程** | 全仓只允许 `ChildProcessSupervisor` 起子进程；**禁 `Win32_Process.Create`（WMI/CIM 起进程不进 Job）**；**禁经终端/中间服务转发拉起（re-parent 会把树挪走）**；一律 `CreateNoWindow` 直起 | MS Job Objects 文档；Godmode 151 孤儿事故 |
| **2 归属可证** | 子进程命令行强制带 `--host-task-id=<id>` + `--instance-token=<uuid>`；归属判定用**令牌 + 创建时间**，禁 PID/名字白名单 | 本仓教训：硬编码僵尸 PID 换机即失效 |
| **3 单实例** | **权威**=内核 Named Mutex（随进程退出自动释放）；锁文件降为**诊断**，记 `{pid, 创建时间, 可执行路径}` 三元组；接管前须证明原持有者已死 | Qt `QLockFile`；语音 daemon 「孤儿占锁→读锁即 return False」 |
| **4 回收双保险** | ① **优先 `PROC_THREAD_ATTRIBUTE_JOB_LIST`（Win10/2016+）让进程"出生即在 Job 内"**；② 退路 = `CREATE_SUSPENDED` + `AssignProcessToJobObject` + `Resume`，**Assign 失败必须杀进程+等句柄+关句柄，禁吞**；③ 关闭时 `taskkill /T` 显式收树 + `TerminateJobObject` 兜底；**禁 BREAKAWAY_OK / SILENT_BREAKAWAY_OK；禁子进程继承 Job 句柄** | MS 官方问答（2026-11）：suspended+assign 存在孤儿窗口；句柄被继承则 KILL_ON_JOB_CLOSE 不触发 |
| **5 启动体检** | 壳启动前做基线快照（自家 exe 前缀 + 父子链），与 `config/host-tasks.json` 三方比对，输出**已死未起 / 已起无主 / 多实例**；兜底扫描三条件同时满足才处置：**父进程已死 + 命令行签名匹配 + 年龄 > 5min** | Godmode 的三条件扫描；`Get-Process` 与 CIM 判定会互相冲突，故须多视角 |
| **6 闭合证据** | "终止"≠"已终止"：`TerminateJobObject` 异步、`ACTIVE_PROCESS_ZERO` 通知不保证送达；**唯一证据 = 轮询 `QueryInformationJobObject → ActiveProcesses == 0`**，持有句柄的进程再加 `Wait` 补证 | MS 官方问答 |
| **7 重启强度** | Guardian 显式命名 **`max_restarts=3 / max_seconds=300`**（即现 20s 探活 / 3 次失败 / 300s 冷却）；超限**不硬撑，向上抛**：Guardian → 壳 → 下次登录恢复 | Erlang/OTP supervisor 的 restart intensity |

**已知代价（明确接受）**：壳崩溃后不自愈（Job 收全树），下次登录恢复。宁可全死，不留残留。

### 15.6 汇报窗口与凭据（窗口是已有的，不是新建）

**窗口（既有规格，不新造）**：四角壳 8 锚点，**任务管理器面板 960×640**（`next-双域分离与开工设置规范` §Surface）；内容形态＝「查任务状态」的 MVP（进行中/完成/失败/阻塞 → 聚合汇报 + 组合窗口 + 语音汇报，见 `product-plan`）。Manager 是给这个窗口**供数**的探针端。

**展示五列**：任务 / **现在在哪一点**（含 `activity`）/ 谁在做（`executor`）/ 停在这一步多久（`stage_entered_at` + `stalled`）/ 堵在哪（`blocker`）。

**汇报凭据（从"只认完成"扩到每档）**：
- 完成档（既有硬规则，不变）：`<工单号> 已完成｜tag <tag名>｜commit <sha>｜<一句话结论>`；**无 tag 不得报完成**，Owner 用 `git show <tag>` 核对。
- 中间档（本节新增）：进入 `executing` / `auditing` / `delivered` 必须带**证据指针**（文件路径 / 事件 / commit）；**取不到证据报 `unknown`，禁猜一个点位填上**。

### 15.7 验收（可机检，必须换机复跑）

| 门 | 判据 |
|---|---|
| 点位四问 | 任取在跑任务，视图答出「在哪一点 / 谁在做 / 停多久 / 堵在哪」4/4 |

| 无主进程 | 手工起一个不带令牌的自家进程 → 体检报「已起无主」，处置后 0 残留 |

### 15.9 硬规则汇总（违反即打回）

1. **只投影不造状态**：Manager 不写队列状态，不自造 state。
2. **点位封闭**：九点位之外不得新造；新增须走变更（改本节 + 同步视图与断言）。
3. **单调性**：只允许 `auditing ↔ fixing` 循环，其余不得回退、不得跳点。
4. **一任务一点位**：多执行端并行时取"最早未完成的点位"，不并列报多点。
5. **无证据不推进**：每次点位变更带 `stage_entered_at` + 证据指针；取不到报 `unknown`。
6. **无 tag 不报完成**；中间档也必须带证据指针。
7. **单一父进程**：壳之外任何人不得起进程；定时能力不得做成独立常驻进程。
8. **禁推断式体检**：不得用 PID 白名单、不得单靠一种查询判死活。

## 十六、模型基线与运行契约（Owner 2026-11-13 定端口与上下文，本节为唯一权威）

> 一句话：**模型是受管资产，不是能自己跑的野马**——未登记的模型不许加载，参数只从基线来，调用只有一个入口，运行态必须回读对账。

### 16.1 模型登记（fail-closed）

| 字段 | 要求 |
|---|---|
| `id` | 唯一标识，如 `mainbrain.qwen3-8b.q5km` |

| `sha256` | **加载前校验，不符即拒载** |
| `quant` | 量化档（Q4_K_M / Q5_K_M …） |

### 16.3 调用契约（只有一个入口）

1. **单入口**：全仓只允许 `brain.infer` 调用主脑；**`llama-server` 只由 `ChildProcessSupervisor` 按 `mainbrain` 条目拉起一次**，其他模块不得自起、不得直连 11435（与 §15.5 闸 1 同源）。
2. **每次调用带**：`task_id`、用途标签（`decision` / `dialog`）、`deadline`。**采样参数由 profile 查表得到，调用方不得自带**（传了即拒，记事件）。
3. **预算强制**：上下文按 R-56 的 **4000 token 由调用层截断**，不靠模型自觉；超预算必留事件。
4. **超时 / 重试 / 熔断**：首 token 超时 **30s**（与 `MB-P5` 一致）→ 重试 **1 次** → 仍失败进 R-47 梯子；**禁止无限重试**。
5. **降级不改口径**：进 L3 外脑 / L4 紧记录时本地参数不动（不许"降级时偷偷降上下文"）。

### 16.4 运行态回读（不信配置，信回读）

启动后必须从 `/props` 读回**实际**加载的模型名、量化、`n_ctx`、线程数，与 16.1 + 16.2 逐项比对：

- **一致** → 正常服务，留一条启动对账事件；
- **不一致** → **拒绝服务**（不是警告了事），记 `model_baseline_mismatch` 事件，四角壳黄灯，按 R-47 处置。

理由：配置写 4096、实际起 2048 这类静默偏差，靠人眼永远查不出来。

## 十七、记忆三库与检索契约（Owner 2026-11-13 口述重组，本节为唯一权威）

> 起因：记忆只有一个库时，用户偏好、世界知识、系统踩坑挤在同一张表里，检索只能全库混查，配额互相挤。Owner 定：**记忆层下放三个库**，同栈同索引、入口分开。

### 17.1 三库定位（按「记谁的事」分）

| 库 | code | 记什么 | 典型内容 | 谁能写 |
|---|---|---|---|---|
| 记忆 | `mem` | **用户的事** | 偏好、习惯、对话要点 | 主脑写入（可撤销，G7） |
| 知识库 | `kb` | **世界的事** | 书籍 / 文档 / 代码库的书架 | 采集能力写入 ＋ 用户确认 |
| 经验库 | `exp` | **系统自己的事** | 踩坑、故障、处置、预防 | 系统自动起草 ＋ 用户确认 |

**一条硬规矩**：三库**不做全库混检**，入口分开（`mem.search` / `kb.search` / `exp.search`）——混检会让记忆污染知识、经验污染事实。

### 17.2 存储与容量


- 后端沿用 T8：**SQLite ＋ FTS5 ＋ 向量**；三库共用同一栈与**同一个本地 embedding**（禁外部 embedding 服务）。

**总原则（R-65，2026-11-13，取代 R-62 的条数门部分）：容量不是「能存多少条」，是「盘上怎么摆、怎么找回来」。条数只是观测值，唯一的硬门是磁盘占用。**

#### 17.2.1 物理形态：库 → 层 → 子文件库

不是一个大 `store.db`，而是**分库、分层、分片**：

```
store/
├ index.db                      统一索引（只存指针、不存正文）：FTS5 ＋ 向量 ＋ (lib, shelf, layer, file, offset, len)
├ mem/
│  ├ hot.db                     热层（未压缩，常驻）
│  ├ warm.db                    温层（页压缩 zstd，mmap 按需读）
│  └ cold/2026-Q4.dbx           冷层（只读分片，可整片外移）
├ kb/
│  ├ shelves/java/hot.db        每书架一个子库：一个书架＝一套层文件
│  ├ shelves/java/warm.db
│  └ cold/java/2026-Q4.dbx
└ exp/
   ├ hot.db  /  warm.db  /  cold/2026-Q4.dbx
```

- **每个库一套层文件**；`kb` **再按书架切一层**——「建立不同的子文件库」落到这里：一个书架＝一个独立子库，`rmdir` 一个书架不动别的书架。
- 索引**物理单文件**、**逻辑按 `lib` 分区**（FTS5 加 `lib` 列、向量分区）；三个检索入口仍分开，不混检。

- **层文件可落在任意存储卷**：`cold/` 整个目录可直接指向另一块盘或 NAS（`E:\UltimaStore\kb\cold\` / `\\NAS-01\UltimaAgent\store\`），路径由 `volumes.json` 登记，**代码里不写死盘符**。


#### 17.2.2 三层阈值与自动迁移

| 层 | 上限 | 读写行为 | 命中代价 |
|---|---|---|---|
| **热** `hot.db` | **500 MB（Owner 定值，非建议值）** | 常驻、同步读写 | 最低 |
| **温** `warm.db` | **2 GB（Owner 定值）** | mmap 按需读，页压缩 | 中（单页解压） |
| **冷** `cold/*.dbx` | **不设上限**，容量＝所挂卷之和；**存档路径可指定**（§24.3） | 只读分片，可跨盘／跨 NAS | 高（单片解压 ＋ 网络 I/O） |

> **Owner 2026-11-13 定值（R-80，见 §24.3）**：热 **500 MB**、温 **2 GB**（原 250 MB / 1.2 GB 为建议值，现已升为定值，改值走 §六）；冷层**不设上限**且**存档路径可由用户指定**（默认 `%LOCALAPPDATA%\UltimaAgent\store\cold\`，可改到其他本地盘或私有 NAS）。
**自动迁移（不弹窗、可中断、可续跑，每批 ≤50 MB）**：

| 方向 | 触发条件 | 目标卷选择 |
|---|---|---|
| 热 → 温 | 热层达 **80%**，或该条 **30 天未命中** | 本地温热卷 |
| 温 → 冷 | 温层达 **80%**，或该条 **90 天未命中** | **剩余空间最大且 `online` 的冷卷** |
| 冷 → 温 | **7 天内命中 ≥3 次**（24h 冷却，防抖动） | 本地温卷（NAS 片整体 pin 下来） |

**索引跟随**：迁移只改索引里的 `(volume, file, offset, len)` 指针，**正文只搬一次、不复制**；检索永远「先查索引 → 按卷取页 → 冷层只解压命中的那一页」。

#### 17.2.3 存储卷与扩容（**没有全局容量硬门**）

**原则（R-66，2026-11-13）：容量随知识库与经验库增长而扩，不设总上限——盘满了挂新盘，或直接接 NAS。**

- 登记文件 `volumes.json`（每卷一条，运行时可热加，**不需要重启**）：

| 字段 | 说明 |
|---|---|
| `id` | 卷标识 |
| `path` | 目录 / 盘符 / UNC（`\\NAS-01\UltimaAgent\store\`） |
| `role` | `hot` / `warm` / `cold`（一个卷可兼多种角色） |
| `quota` | 可选；不填＝用到物理盘满 |
| `state` | `online` / `offline` / `full` |

- **扩容方式只有一种，且零迁移成本**：新增卷 → 以后的新分片写到新卷；**旧数据原地不动**，索引按卷指回原处。所以「换更大盘」不需要重建，直接留着旧盘当冷卷，或整目录搬到新盘后改 `path`。
- **水位按卷算，不按总量算**：
  - 卷 **85%** → 黄（只告警，照常写）；
  - 卷 **95%** → 红（**该卷停止接收新分片**，自动改投下一可用冷卷）；
  - **所有冷卷红或全部 `offline`** → 进 `CAPACITY_ALERT`：**采集排队**（入库任务排队等待，不丢、不失败），**检索与对话照常**，界面提示「挂新盘 / 接 NAS / 清书架」。
- **检索延迟分卷承诺**：本地卷 P95 ≤ **120 ms**；**NAS 卷不承诺时延**——首次命中触发 **pin 预取**（整片或整本提升到本地温卷），之后走本地。pin 占温层配额时按 LRU 让位。
- **NAS 掉线不报错**：卷标 `offline`，检索跳过该卷并在结果里注明「该卷离线，可能缺条目」；**不阻塞**其余检索。
- **边界红线**：只允许**私有 NAS ／自有盘**（自建、内网、个人所有）；**禁止接公有云盘、第三方对象存储**做冷层——知识库与经验库属「只做本地个人检索」（§17.3 ③），挂私有 NAS 不算外发，挂公网存储算外发。

### 17.3 知识库（书架）

- **初始为空**。三层组织：**书架＝领域**（如 Java 开发）／**书＝来源单元**（带来源 ＋ 许可 ＋ 入库时间）／**页＝可检索最小单元**（chunk）。
- 检索可按书架限定范围（「只在 Java 书架里找」）。
- 硬约束：① **权威源不进书架**（基线、specs、各权威文档只做指针）；② **只采公开内容**；③ 书籍类**只做本地个人检索**，不外发（**私有 NAS ／自有盘不算外发，公有云盘算**，见 §17.2.3）；④ 代码库必记 **licence**，GPL 仅作阅读参考、**不得作代码来源**。
- 写入路径：**指令驱动采集**（用户下指令 → 采集能力取内容 → 解析分块 → 入书架），**不自动全网爬**。

### 17.4 经验库（踩坑）

- 状态机：`draft` / `confirmed` / `revoked`；**未 `confirmed` 不得作决策依据**——错的经验被固化比没有经验更坏。
- 每条必带**证据指针**：日志片段 / 事件 id / 复现命令；**无证据只能算印象**。
- **先查后动**：降级六码动手处置前先查 exp——「这个码以前怎么收拾的、哪次收拾错了」。
- 与开发侧 `docs/references/lessons-log.md` 是**两套账**（工程侧 vs 产品运行时），但**字段结构对齐**（场景／症状／根因／处置／预防／证据），可互导。

### 17.5 索引与检索契约（`index` 横切层）

| 项 | 定值 |
|---|---|
| 分块 | 语义边界（章／节／函数）；重叠 **10–15%** |
| 元数据 | 库／书架、来源、许可、时间、版本、**位置（章-节-行）**；**无位置不可入库** |
| embedding | 本地单一模型，`role=embedding` 进 §十六 登记表，维度固定；换模型＝**全量重建**，走 §六 |
| 检索 | **FTS5 ＋ 向量混合**，RRF 融合；`top_k=5` |
| 阈值 | 低于阈值返回「**没找到**」，**禁硬凑** |
| 重建 | 增量优先；全量限时限额 |
| 一致门 | **索引条数 vs 源条数 ±0**，偏差即报警 |


- **逻辑位置 vs 物理位置（两者都必填）**：逻辑位置（章-节-行）证明「这句出自哪」；物理位置（`layer` / `file` / `offset` / `len`）证明「这条存在哪」。缺任一不可入库，检索按物理位置直取、不扫全表。

### 17.6 防投毒（原只覆盖 `mem`，现扩三库）

`poison_guard` 扩到 `kb` / `exp`：外部采集内容与自动起草的经验同为投毒入口；`exp` 的 `draft` 状态天然是隔离区。

### 17.7 验收（可机检，挂 N-03）

| 门 | 判据 |
|---|---|
| 三库分立 | `mem.search` 结果中 `kb` / `exp` 条目计数 **0** |
| 无位置拒入 | 塞一条无位置元数据的 chunk → **入 kb 被拒** |
| 初始空 | 新装首启：`kb` 条数 **0** |
| 索引一致 | 随机删 3 条源条目 → 索引同步后 **±0** |
| 未确认不生效 | `exp` 中 `draft` 条目进入决策路径的次数 **0** |
| 阈值兜底 | 检索无关词 → 返回「没找到」，**不返回低分条目** |

## 十八、外部能力与绑定（Owner 2026-11-13 口述定义，本节为唯一权威）

> 起因：v1/v2 把 Skill、插件、模型配置散在三处，且「Codex 写代码、DeepSeek 审计」是写死的执行端逻辑。Owner 重定义：**外脑＝能力库**，能力可加、可指派、可换绑；**Skill 与插件都沉到外部能力之下**。

### 18.1 外部能力＝三个抽屉

| 抽屉 | 内容 | 形态 |
|---|---|---|
| **能力库 Skill** | 产品策划 / 代码开发 / 方案撰写 / 代码审计 / 知识采集 … | 卡片 ＋ 指派下拉 |
| **插件 Plugin** | MCP 客户端、执行端适配器 `plugin.executor.<name>`、provider 接入 | 清单 ＋ 登记 |
| **模型库 Provider** | 已配置好的 API 接入列表（云端）＋ 可选本地第二模型 | 列表 ＋ 六态 |

呈现层级因此从**五类塌成三类**（基础能力 / 外部能力 / 交付），见 `next-基础能力盘点与缺口清单` §1.1.1。

### 18.2 能力 × 模型绑定

- **一对一**：一个能力只绑一个模型，**不设主备、不自动切换**；换绑＝在模型库列表里**手动下拉**选择，立即生效，但**在途任务等本轮结束**才切换。
- 卡片上直接看三件事：**是否添加成功**／**指派给了谁**（下拉）／**provider 状态灯**。
- 添加 skill 走**三项校验**（清单可解析 ／ 依赖可用 ／ 许可可接受）；**失败留红卡**，不静默丢失。
- **主脑不在模型库列表、不可被指派**：模型库列表里主脑条目 **0**，能力指派下拉里也不出现主脑。但主脑**可在配置面下拉替换**（R-76，见 §二十三）：候选＝主脑登记表 ∪ 模型库已配 provider，**必须分「本地」「外部·云端」两组并带标签**。

### 18.2.1 分配表（能力 × 数据范围 × 默认绑定）

| 能力 | `data_scope` | 默认绑定 | 约束 |
|---|---|---|---|
| 意图判定 / 路由 / 审计判定 | **local-only** | 主脑 `decision` | 近零温度 ＋ 固定 seed，同输入同结果 |
| 对话与播报表达 | **local-only** | 主脑 `dialog` | 口播 ≤2 句 |
| 上下文压缩 / 摘要 | **local-only** | 主脑 `decision` | **禁外派**（Q2） |
| 产品策划 / 代码开发 / 方案撰写 | remote-ok | 云端 provider | — |
| 代码审计 | remote-ok | 云端 provider | **必须 ≠ 开发所用 provider**（落成断言） |
| 知识采集 | remote-ok | 采集 provider | 分 `http` / `browser` 两档 |
| 文档解析入库 | **local-only** | 本地 | 解析完即落 `kb`，不外发 |
| 检索（`mem` / `kb` / `exp`） | **local-only** | 本地 embedding | 禁外部 embedding 服务 |

**这张表同时消解了一个争议**：外脑「日常是否参与」不是全局开关，**由能力的 `data_scope` 决定**——碰记忆／本地文件的能力只能绑本地，写代码写方案的可绑云端。

### 18.3 provider 六态（可检测，不靠猜）

| 态 | 含义 | 判定方式 |
|---|---|---|
| `ok` | 可用 | 探活成功 |
| `no_token` | 没有凭证 | 本地凭证缺失 |
| `auth_failed` | 凭证无效 | 401 / 403 |
| `unreachable` | 连不上 | 连接失败 / 超时 |
| `rate_limited` | 限流或额度不足 | **402 / 429 / insufficient_quota** |
| `disabled` | 用户停用 | 配置位 |

**纪律**：连接探活**免费勤跑**；**额度只靠失败判定**，**不做付费探测**（不花用户的钱去测余额）。

### 18.4 provider 六态 ↔ 主脑降级六码（两套不许混说）

| 维度 | 管什么 | 编号 |
|---|---|---|
| provider 六态 | **外脑／云端接入的健康** | `ok` / `no_token` / `auth_failed` / `unreachable` / `rate_limited` / `disabled` |
| 降级六码 | **主脑（`llama-server`）故障阶段** | `MB-P1` … `MB-P6`（见 `next-主脑不可用降级剧本-20261113`） |


**裁决（R-63，2026-11-13）：六态与六码是「两个对象」的健康度，编号互不替代；两者只在「系统档位」这一层交汇。**

| provider 六态 | 主脑状态 | 系统档位 | 行为 |
|---|---|---|---|
| `ok` | 正常 | **NORMAL** | 全能力可用 |
| `no_token` / `auth_failed` / `disabled` | 正常 | **LOCAL_FALLBACK** | 云端能力红卡显式不可用；可外派能力**降级到本地**（`data_scope=local-only` 的能力不受影响）；**不自动换绑**，须人工下拉改派 |
| `unreachable` / `rate_limited` | 正常 | **LOCAL_FALLBACK** ＋ 退避 | 同上；`unreachable` 指数退避重试（上限 3 次）；**`rate_limited` 不重试**，等配额窗口 |
| 任意 | `MB-P1` … `MB-P6` | **MAINBRAIN_DEGRADED** | 走降级梯子 L1→L3；此时云端 provider 是否可用**不改变档位判定** |
| 非 `ok` | `MB-P1` … `MB-P6` | **DEGRADED_READONLY** | 只读：展示、检索、回答历史；**不派发、不写、不采集** |
| 非 `ok` | 主脑为**外部** | **LOCAL_FALLBACK** | **切回本地主脑**（收窄外发，不需二次确认，§23.8）；外部条目红卡可见，**不自动换到别家 provider** |

- 档位四值（`NORMAL` / `LOCAL_FALLBACK` / `MAINBRAIN_DEGRADED` / `DEGRADED_READONLY`）进枚举总表，**只在本节定义一次**；Console **只读档位、不改档位**。
- **禁止写法**：把 `rate_limited` 当 `MB-P5` 用、把 `no_token` 记成主脑故障——**对象不同，码不许串**。
- 档位切换必须留痕（`from` / `to` / 触发码 / 时间），供 Console 与审计同时可读。

## 十九、Console 定位定稿（R-64，2026-11-13）

> 起因：Owner 连问两轮「Console 是不是终端调度器」。此前「终端」被我按**执行端**理解——**错**。Owner 明确：**「终端」＝引擎的中心管理调度器**。本节把这个词与 Console 的职能一次钉死。

### 19.1 定稿措辞

**Console ＝ 引擎的中心管理调度器（Engine Central Scheduler）**，**随 Python 引擎域常驻**（与 `queue_engine` 同进程，同进程带 Manager 子模块）；壳只经引擎域既有本地通道读其**只读视图**（R-78 定案，见 §24.1）。

### 19.2 四件职能（都属「管」，不属「做」）

| 职能 | 内容 | 谁落手 |
|---|---|---|
| **任务编排** | 派发／调度／优先级／依赖／点位推进 | Middleware 起执行端 |
| **常驻托管** | 看门狗启停意图、进程树归属、重启预算记账 | Shell 起进程 |
| **输出呈现** | 决定「此刻该给用户看什么」（内容与时机） | Surface 画像素 |
| **多端调度** | 同一任务跨用户设备／显示端的就绪与投递 | Middleware 发请求 |

**一句判定法（可机检）**：**代码只要会碰进程／网络／磁盘／像素，就不属于 Console**。Console 只碰队列、状态机、档位与账本。

### 19.3 与相邻模块的边界

| 模块 | Console 对它 | 它不得对 Console |
|---|---|---|
| Manager | 下发 `task_id` 与探针口径，收反馈 | Manager 不自建状态枚举、不反写点位 |
| Shell | 下达「起／停／查」意图，收退出证据 | Shell 不自决重启预算（预算账在 Console） |
| Surface | 下达「呈现哪张卡、什么时机」 | Surface 不自定卡内容来源 |
| Middleware | 下达派发指令与执行端标识 | Middleware 不硬编码厂商枚举 |
| Python 引擎（`queue_engine`） | 只读写八态与迁移结果 | 引擎不决定优先级、不改系统档位 |

### 19.4 为什么不做执行面（防复发）

Console 若自己 `CreateProcess` 起看门狗，就成了**第二个父进程**——§十五 闸1（单父进程归属）当场破防、孤儿看门狗必然复发。**调度者不亲自起进程**是 Console 的第一纪律。

### 19.5 「终端」一词的使用规范

- 「**终端**」**只指引擎的中心管理调度器（即 Console）**；
- **禁止**再用「终端」指执行端、用户设备或显示端——分别写「**执行端**」「**用户设备**」「**显示端**（Surface）」；
- 「**多端调度**」保留，释义固定为：Console 对**多个用户设备／显示端**的投递调度，**不是**「多执行端编排」。

### 19.6 域归属（已定案：迁入 Python 引擎域，R-78）

**原「悬空」结论作废**（原文：Console 属客户端域 C# 进程树、迁入需另立裁决）。**Owner 2026-11-13 拍板：Console 迁入 Python 引擎域**，裁决与理由见 **§24.1**。

三条不影响既有冻结条款：
1. **闸1（单父进程）不被破坏**：闸1 管「谁起进程」；Console 迁域后**仍不起任何进程**，Shell 仍是唯一父。迁域改的是「Console 的代码住哪」，**不是授权它碰进程**。
2. **Console 能力边界不变**：`CreateProcess`／客户端发起 socket／写盘／像素调用仍须 **0**（§19.7 机检）。
3. **不新增端口**：壳读 Console 视图走引擎域既有本地通道（8756），不新起服务、不新增父进程。

|---|---|

| 档位只读 | Console 对系统档位的写操作 **0** |
| 词义唯一 | 抽查 5 处「终端／终端调度器／多端调度」，释义均指 Console，**无一指执行端** |
| Manager 同进程 | Manager 与 Console 同一进程 id |
| **Console 进程归属** | 壳进程树内 Console 进程 **0**；Console 与 `queue_engine` **同 pid**（R-78） |
| 边界单向 | 数据流只允许 壳触发 → Console 编排 → Manager 探针 → Console 跟踪 → 壳展示，**无反向写** |

## 二十、治理与约束⑤的隶属清单（R-67，Owner 2026-11-13 定调）

### 20.1 一句话结论

**五条行为学原则不是独立模块，也不是与三大类并列的第四条轴**。它们归 **⑤ 治理与约束的「行为层」**，与「不变式／规则库／红线」同层：只约束「怎么表现」，不新增模块、不新增进程、不新增配置面。

### 20.2 为什么归治理（三条判据）

1. **性质相同**：行为层本来就属⑤——§16.5 已把「系统提示词、能做/不能做、拒答边界、复述确认」判给⑤，五条原则正是这一层的内容。
2. **没有载体**：原则不占端口、不起进程、不占存储、不出现在安装包里。凡无运行时载体的东西，画成模块就是虚增层级。
3. **有落点**：每条原则的落点是**既有模块**（见 20.3），它是「对模块的要求」，不是「模块本身」。挂成引擎下的并列分支，会让树看起来存在第四个顶层部件，与「三大类」口径直接冲突。

### 20.3 五条原则与落点

## 二十二、任务库与日志库（R-74 / R-75，Owner 2026-11-13 拍板）

### 22.1 一句话结论

任务库与日志库都是 **「库」不是「模块」**——**六块模块数不变**。任务库归 **Console**（它本来就是 Console 的账），日志库归 **治理⑤ 的「审计与留痕」**（保留期、防篡改、审计独立都是治理口径）；两者**物理共用 Memory 的 `store/`**，但**逻辑隔离、检索入口不混**。

### 22.2 R-74 任务库（Task Store）

**归属与实现面**

| 项 | 定案 |
|---|---|
| 归属 | **Console 名下**，与 `usage_ledger` 同级，属「管」的账本 |

1. `项目` → 2. `工单卡`（N-xx / 外部工单） → 3. `任务`（卡内 T#） → 4. `运行实例`（一次派发＝一条 run）

| 阶段 | 规则 |

### 22.3 R-75 日志库（Log Store）

**归属**：**治理⑤ 的「审计与留痕」**；**不进 Memory**——记忆有「禁外发」红线，而日志必须能导出排查，混在一起就是重演「规则库归记忆」。

| 类别 | 内容 | 保留期（拍板值） | 形态 |

### 22.4 共用物理、逻辑隔离（三层约定）

| 层 | 约定 |
|---|---|

| **入口不混** | 五个检索入口分开：`mem.search` / `kb.search` / `exp.search` / `task.query` / `log.query`；混检计数必须 **= 0** |

### 22.5 硬规则

1. 六块模块数不变；任务库、日志库以**库形态**挂在既有归属下，**不得升格为模块**（再并列一次就回到「七块」）。
2. 任务库唯一实现面是 `tasks/queue_engine`；新建第二套任务存储即违规（M1）。
3. 日志库不得并入 Memory 的检索面；交互转写只能以指针出现，正文在 Memory 冷层。
4. 审计日志 append-only；删除或改写审计日志的代码路径 **0**。
5. 本节与 §17.2 冲突时：**容量与温度以 §17.2 为准，库归属与分类以本节为准**。

### 22.6 验收（可机检）

1. 全仓任务索引实现 **= 1**（`tasks.json`）；第二份任务索引 0。
2. 任务状态取值 ⊆ 八态枚举；第二套状态名 0。
3. 冻结满 1 年的任务全部在冷层，热层命中 0。
4. 日志四类前缀齐全；审计行含 `prev_hash`，篡改一行可触发 `LOG_CHAIN_BROKEN`。
5. `mem/kb/exp/task/log` 五入口分开；跨库混检计数 0。
6. 删除/改写审计日志的代码路径 0；删除任务记录的代码路径 0（只允许 `archived`）。

## 二十三、主脑可替换与外部主脑（R-76 / R-77，Owner 2026-11-13 补充）

### 23.1 一句话结论

**主脑不是写死的**：主脑＝**可替换的推理后端**，分**本地**与**外部（云端）**两类，在**配置面（设置页）**用下拉切换——与「给某个 skill 配哪个模型」**同一套交互组件与逻辑**。**切到外部模型必须提示隐私数据可能离开本机**，且默认禁止本地记忆外发。

### 23.2 候选池与下拉分组（硬规则）

- **候选池**＝主脑登记表 `mainbrain.*`（本地）**∪** 模型库已配置 provider（外部），**不引入第三来源**。
- **下拉必须分组带标签**：`本地`（绿标，数据不出机）／`外部·云端`（黄标，上下文离开本机）。标签由条目类型**自动推导**，不许手填、不许缺省、不许混排无标。
- **保留两条不变**：模型库**列表**里主脑条目 **0**；**主脑不可被任何 skill 指派**（能力指派下拉里不出现主脑）。
- **单入口不变**：外部主脑仍只经 `brain.infer`，内部路由到 provider 客户端，**调用方不感知换型**。

### 23.3 切换流程（五步固定）

| 步 | 动作 |
|---|---|
| 1 | 配置面下拉选目标（本地/外部标签可见） |
| 2 | **目标为外部** → 弹显式确认：①调到哪家 ②**当前对话与上下文会离开本机** ③可随时切回。取消即不切 |
| 3 | 执行：本地→外部＝停 `llama-server`（Shell 执行）＋ 走 provider；外部→本地＝起 `llama-server`（按目标条目参数）＋ 回读对账 |
| 4 | **回读对账**（本地走 `/props`；外部走一次最小探活调用）；不一致 → 回滚 |
| 5 | 留痕（23.9） |

- **在途任务等本轮结束**才切换（与 §18.2 换绑同纪律）；切换期 UI 示 `switching`，**不改档位**。
- 执行面归 **Shell**（停/起进程）；Console 只出意图与读状态（与 §19.4「调度者不起进程」一致）。

### 23.4 参数随模型走（不许一套参数走天下）

§16.2 的全局值**只做默认**；每个主脑条目可带 `launch_params`（覆盖 `n_ctx`／`n_batch`／`n_threads`／`--ngl`／KV cache／flash-attn 等）。**换型即切参数集**；回读对账按**目标条目**比对，不拿全局值比。未带 `launch_params` 的条目继承 §16.2 默认。

### 23.5 失败回滚

- 换型失败（`sha256` 不符／加载 OOM／端口占用／探活失败）→ **回滚到本次换型前的条目**（撤销本次操作），记一条失败审计。
- 回滚**不自动换到第三方 provider**（与 §18.2「无主备、不自动切换」一致）；回滚后 UI 必须显示「已回滚到 <原条目>」，不得静默。

### 23.6 三道隐私闸（R-77）

**闸1 · 切换必须显式**：切外部不默认、不自动、不「记住就行」；每次切换弹确认（去向 ＋ 数据离开本机 ＋ 可回退）。

**闸2 · 记忆外发默认关**

| 数据 | 外部主脑下 | 说明 |
|---|---|---|
| 当前轮语音转写 / 当前轮对话 | **允许** | 否则外部主脑无法工作 |
| skill 请求的显式上下文片段 | **允许** | 与普通工具调用同口径，按请求粒度可见 |
| `mem` 命中片段 | **默认禁**；经**会话级一次授权**后才发 | 只发命中片段，**禁全库上传** |
| `mem` 全库 / `kb` / `exp` | **禁止** | 代码断言 |
| 审计日志 / 凭据 / 文件路径清单 / 采集原文 | **绝对禁止** | 与 §20.4 红线同级，代码断言 |

实现口径：**先本地检索、只把命中片段按授权上送**；不做整库上传，也不做「先上传再本地删」。

**闸3 · 外部状态常驻可见**（三处都不可关）

1. **状态灯分级**：本地＝**绿**；外部＝**黄**（黄代表数据出机，**禁止用绿表示外部**）；降级＝**红**。
2. **四角壳右上锚点常驻「云端主脑」角标**，切回本地后消失。
3. **首次进入外部模式**弹一次不可跳过的确认；配置面顶部另留一条不可关的「当前主脑＝外部·云端」状态条。

### 23.7 持久化与授权（Owner 2026-11-13 拍板）

| 项 | 定案 | 理由 |
|---|---|---|
| 外部主脑选择 | **持久化**（重启后仍为外部） | 切换时已显式确认过，不重复打扰 |
| 持久化的补偿 | 配置面**常驻状态条** ＋ 冷启动首屏可见「外部·云端」标识 | 让「开机即外部」一直可见，不靠记忆 |
| 记忆片段授权 | **每次会话一次授权**，会话结束失效；**续会话须重新授权** | 避免每轮弹窗打断，又不让授权永久化 |

### 23.8 档位与降级（四值不改，不新增档位）

| 情形 | 判定 |
|---|---|
| 本地主脑故障 | `MB-P1` … `MB-P6` → **`MAINBRAIN_DEGRADED`**（原样） |
| **主脑已为外部** 且 provider 非 `ok` | **`LOCAL_FALLBACK` ＝ 回本地主脑**（收窄外发，不需二次确认） |
| 换型进行中 | 只示 `switching`，**不改档位** |
| 换型成功 | 档位按目标条目重新判定，不因「换过型」而变值 |

### 23.9 留痕（进日志库「审计」类）

- **每次切换**记：`from` / `to` / 类型（`local|external`）/ provider / `sha256` / 回读是否通过 / 时间 / 操作者。
- **外部主脑每次调用**记：provider / 模型 / token 入出 / **是否携带记忆片段**（携带则记授权 id）。
- 授权事件（开始 / 失效）各记一行。

### 23.10 硬规则

1. 主脑候选只能来自登记表或已配 provider；未登记、未校验不得出现在下拉里。
2. 下拉必须分「本地／外部」两组并带标签，无标签条目为违规。
3. 切外部必须显式确认；记忆默认禁发；外部状态必须常驻可见。
4. 记忆外发需**会话级**授权，会话结束即失效，续会话重授。
5. 本地主脑参数（§16.2）不因外部模式被改写；外部模式也不许偷偷降本地上下文。
6. 「主脑不进模型库列表」「主脑不可被 skill 指派」继续有效，不因本节放开。
7. 换型失败必须回滚到换型前条目，禁止「失败后自动挑一个别的」。

### 23.11 验收（可机检）

1. 主脑下拉条目 **100%** 带 `local|external` 标签；无标签条目 **0**。
2. 模型库列表里主脑条目 **0**；能力指派下拉里主脑条目 **0**。
3. 外部模式下上送 `mem` 全库 / `kb` / `exp` 的调用计数 **= 0**（>0 即失败）。
4. 未授权会话里携带记忆片段的外部调用 **= 0**；会话结束后授权仍未失效 **= 0**。
5. 外部模式状态灯为**黄**且角标存在；切回本地后角标 **消失**。
6. 换型失败后 active 条目 **＝** 换型前条目（回滚生效），审计含失败行。
7. 审计字段齐全：切换行含 `from/to/type/provider/sha256/回读/时间/操作者`；外部调用行含 `token` 与「是否携记忆」。
8. 全仓 `llama-server` 启动点仍 **= 1**（换型只换参数集，不新增第二个启动点）。

## 二十四、域归属、沙箱、温度轴三处定案（R-78 / R-79 / R-80，Owner 2026-11-13 拍板）

### 24.1 R-78 Console 迁入 Python 引擎域

**结论**：Console **物理迁入 Python 引擎域**——与 `queue_engine` / `state_machine` / `usage_ledger` 同进程，**不再常驻客户端壳进程树**；实现栈随之改为 **Python**，C# 侧只剩壳（HostShell）与呈现（Surface），**不再承载 Console 逻辑**。

| 项 | 迁域前 | 迁域后（定案） |
|---|---|---|
| 进程归属 | 客户端域（C#）进程树内 | **Python 引擎域进程内**，与 `QueueStorage` 同栈 |
| 与队列关系 | 跨进程读状态 | **同进程直读八态**，不再有跨进程状态协议 |
| 壳如何看视图 | 同进程直读 | 经**引擎域既有本地通道（8756）**读**只读视图**；不新增端口、不新增服务 |
| 实现语言 | C# | **Python**（引擎域统一） |
| 卸载/打包 | 客户端域含 Console 条目 | 客户端域**不再出 Console 条目**（release-assets 相应调整） |

**为什么 §十五 闸1 不被破坏**：闸1 约束「**谁起进程**」——Console 迁域后**仍不起任何进程**（「碰进程的代码归 Shell」判定法不变），Shell 仍是唯一父。迁域只改「代码住哪」，**迁移不等于授权**：Console 的 `CreateProcess`／客户端 socket／写盘／像素调用仍须 **0**。

**顺带收益**：Console 与八态、账本同域，`usage_ledger` 与 `task.query` 不再跨进程取数；坏处是壳↔Console 多一层本地调用，走既有 8756 通道，不引入第二个父进程。

### 24.2 R-79 沙箱双层：进程级 ＋ 目录级

| 层 | 管什么 | 定值／形态 | 判据 |
|---|---|---|---|
| **进程级** | 跑飞、残留、越权起进程 | **Job Object**：`KILL_ON_JOB_CLOSE` ＋ **64 进程** ＋ **1 GB/进程、2 GB/作业**（沿用 T10 定值）；**出生即入 Job**（`PROC_THREAD_ATTRIBUTE_JOB_LIST`） | 强杀父进程 **3s 内** `ActiveProcesses==0`；`breakaway` 计数 **0** |
| **目录级** | 写错地方、读到不该读 | **写域白名单 `fileDomain`**：每次派发**声明可写目录**；**写入仅限声明域**；读取默认为「工作目录 ＋ 声明读取域」 | 越界写入**被拒并留审计**；未声明目录写入计数 **0** |
| 留 v1.1 | 系统级强隔离 | **AppContainer** | 不进 v1.0 |

**两层独立生效、缺一不算沙箱**：Job 防「跑飞/残留」，写域防「写错地方」。T10 的 Job 参数**不改**，本节只补第二层；目录级不是可选项——只做 Job 不做写域，Gate 不绿。

### 24.3 R-80 温度轴定值（热 500 MB / 温 2 GB / 冷路径可指定）

| 层 | 新定值（Owner 定） | 原值 | 迁移触发 |
|---|---|---|---|
| **热** `hot.db` | **500 MB**（定值，非建议值） | 250 MB | 达 **80%** 或 30 天未命中 → 温 |
| **温** `warm.db` | **2 GB**（定值） | 1.2 GB | 达 **80%** 或 90 天未命中 → 冷 |
| **冷** `cold/*.dbx` | **不设上限**（＝所挂卷之和）＋ **存档路径可由用户指定** | 不设上限、路径随卷 | 7 天内命中 ≥3 次 → pin 回温（24h 冷却） |

**冷层「指定存档路径」三条约束**：

1. **默认路径**：`%LOCALAPPDATA%\UltimaAgent\store\cold\`；可在设置里改到**其他本地盘**或**私有 NAS**，登记进 `volumes.json`，**代码不写死盘符**。
2. **红线不变**：**禁公有云盘／第三方对象存储**做冷层（§17.2.3）；路径指向公网存储 → 配置**被拒**。
3. **换路径不搬旧片**：旧分片原地不动、索引指针不变；新分片写新路径（沿用 §17.2.3「零迁移扩容」）。卷须 `online` 才参与「剩余空间最大」选择。

### 24.4 硬规则

1. Console 迁域后**不得获得**进程／客户端 socket／写盘／像素能力；启动点扫描计数 **0**。
2. 沙箱两层缺一不算通过；AppContainer 不得在 v1.0 偷跑。
3. 热 **500 MB**／温 **2 GB** 是**定值**，改值走 §六；冷层**不设上限**、**禁公有云盘**。
4. 冷层换路径**不搬旧片**，索引指针不动；直接用掉旧盘作冷卷是合法扩容。
5. 本节与 §17.2.2／§19.1／§19.6 冲突时**以本节为准**；§17.2 的其余规则（迁移批 ≤50 MB、水位 85%/95%）继续有效。

### 24.5 验收（可机检，挂 N-13 / N-02 / N-03）

1. 壳进程树内 Console 进程 **0**；Console 与 `queue_engine` **同 pid**。
2. Console 代码 `CreateProcess`／客户端发起 socket／写盘／像素调用 **= 0**。
3. 越界写声明域外目录 → **被拒 ＋ 审计有行**；未声明目录写入 **0**。
4. 强杀父进程 → **3s 内** `ActiveProcesses==0`；`breakaway` **0**。
5. 热/温上限**配置回读**均为 500 MB / 2 GB（写入配置与实际生效一致）。
6. 冷层根路径改到 `D:\UltimaStore\cold\` 后：新片落新路径、旧片索引指针**不变**（抽 3 条可回读）。
7. 冷层路径指向公有云盘/对象存储 → **配置被拒**并留审计。
