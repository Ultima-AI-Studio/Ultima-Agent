# 接口快路径配置清单（机制版）

> 版本 2026-11-06 ｜ 载体：`config/interface-routing.json` + `tools/interface_probe.py`
> 这份文档不再规定"哪个接口必须当第一"，只规定"用什么结构记、按什么规则自动换、什么时候需要人来"。

## 一、从人工清单改成机制

早先的版本把 14 类意图的默认通道逐条钉死，等于把人肉判断写进文档。问题在于：接口会变慢、会挂、会出现更快的新源，写死一次就过期，还得人工重测。

现在改成可执行的机制：

- **配置表只存候选池和实测数据**，不存"唯一正确答案"。
- **谁当首选是算出来的**：巡检器按实测延迟和覆盖率排，排完直接写回配置。
- **排错了会自己纠正**：首选连续失败自动让位，备选快 20% 以上自动上位。
- **人来负责"往池子里放什么"**：新增候选、判断某个源能不能信，这类事机器不该自己决定。

一句话：内容是运维出来的，不是拍出来的。

## 二、配置表结构

文件：`H:\UltimaAI\UltimaAgent\config\interface-routing.json`，`schema_version: 2`。

### 意图（intent）

每类问句一条，关键字段：

| 字段 | 作用 |
|---|---|
| `id` | 意图标识，如 `weather.today`、`market.gold_cn` |
| `triggers` | 命中的说法，用于规则匹配 |
| `route` | 走哪一级：`local_clock` / `http_direct` / `local_file` / `local_module` / `tool` / `model` |
| `requires_coverage` | 要答这个问题，接口**至少得提供**哪些字段 |
| `candidates` | 候选池，按 `role` 排 primary / standby / fallback |
| `excluded` | 明确不用的源，写明理由（防止以后有人又加回来） |
| `timeout_ms` / `cache_ttl_s` | 超时与缓存 |
| `template` | 一句话回答模板，字段名与 `provides` 对齐 |

### 候选（candidate）

| 字段 | 作用 |
|---|---|
| `endpoint` | 地址，`{city_code}` / `{city}` 由 `defaults` 填充 |
| `headers` | 必须带的头（新浪 Referer、天气网 Referer） |
| `expect` | 怎么判断"返回的是数据不是页面"：`kind`（json/text）+ `must_contain` |
| `provides` | 这个源**确实能给**哪些字段（人工确认，不确定就不写） |
| `role` | 当前角色，巡检器写 |
| `health` | `p50_ms` / `ok_rate` / `probes` / `fail_streak` / `eligible` / `last_probe_at`，巡检器写 |

### 策略（policy）

| 项 | 当前值 | 含义 |
|---|---|---|
| `probe.samples_per_run` | 3 | 每项每次跑 3 遍取中位数，抵掉单次抖动 |
| `probe.timeout_ms` | 5000 | 单次探测上限 |
| `probe.coverage_gate` | true | 覆盖度不足直接失去资格 |
| `promotion.min_ok_rate` | 0.9 | 备选要 90% 以上成功率才算健康 |
| `promotion.min_speed_gain_pct` | 20 | 比现首选快 20% 以上才换，防止每天来回切 |
| `demotion.fail_streak` | 3 | 首选连错 3 轮让位 |
| `history_max` | 50 | changelog 只留最近 50 条 |

## 三、巡检器怎么工作

脚本：`H:\UltimaAI\UltimaAgent\tools\interface_probe.py`
解释器：`H:\UltimaAI\UltimaAgent\tools\venv-openjarvis\Scripts\python.exe`

每轮对每个 `http_direct` 意图的全部候选做三件事：

1. **证明拿到的真是数据**——HTTP 200 不算数，要能解码（UTF-8 优先、GBK 回退）、格式对（JSON 能解析）、关键字段在（`must_contain` 命中）。这一条专治"返回 9KB HTML 页面"和"返回空壳"。
2. **卡覆盖度**——`provides` 必须包含 `requires_coverage`，不够就 `eligible: false`，永不当首选。宁可慢一点，也不能答不全。
3. **量本机端到端延迟**——跑 3 次取中位数，记进 `health.p50_ms`。

排完写回：

- 只有 `eligible` 且 `ok_rate ≥ 0.9` 的候选参与排序，按 `p50_ms` 升序。
- 第一名当 primary，其余健康候选当 standby，不合格的当 fallback。
- 如果第一名要取代现首选，必须快出 20% 以上，否则保持不动。

安全措施：

- 写回前自动复制到 `config/_backup/interface-routing-<时间戳>.json`。
- 写文件走 `.tmp` 替换，换行固定 `\n`，编码 UTF-8。
- 含运行时占位符的候选（如个股 `{symbol}`）本轮跳过，不猜、不写假数据。

退出码约定：**只有"某意图连一个可用首选都没有"才返回 1**；备选掉线只记录不报警——备选偶尔挂是正常现象，天天报警等于没报警。

## 四、自动升降级规则

| 场景 | 动作 |
|---|---|
| 首选连续 3 轮失败 | 让位给下一个健康候选 |
| 备选比首选快 ≥20%，且成功率 ≥90% | 自动上位（本轮即可生效） |
| 备选比首选快不足 20% | 保持原首选，避免抖动 |
| 候选覆盖度不足 | 永久降为 fallback，不论多快 |
| 某意图全部候选不可用 | 退出码 1，汇报里标红 |
| 意图未配置、或没有可用首选 | 调建路器从种子册建 1 主 + 2 备，建好即用；已有首选则不重建 |

写入 `changelog` 的只有角色变化，格式是 `{intent, endpoint, from, to}`，便于回溯"哪天换的、为什么换"。

## 五、机器不管的部分

**新查询类型第一次被问到、配置里又没有现成通道时，机器会自己搭一条：1 条主干 + 2 条备用，现场实测排序，写回配置。第二次再问到直接用，不重建。**

搭路只能从 `config/interface-seeds.json` 这本种子册里取源。种子册里没有的标的，建不出来，也不去网上现搜。理由很实际：一个新源能不能信，要靠人看它是不是官方、字段含义对不对、会不会突然限流；临时搜来的接口凭猜接上去，答错比答不出更糟。

所以边界是：

- 机器负责：**从种子册建路、池内择优、坏了让位、换人记录可复盘**。
- 人负责：**决定种子册里放谁**（新供应商要实测过 `expect` 和 `provides` 才能登记）。
- 种子册不够用时，建出来的路如实标 `degraded`，不拿别的品种凑数。想让某类问题答得更稳，就往种子册里加同标的的源。

## 六、定时巡检

- 频率：每天一次，04:40（低峰，非整点）。
- 执行环境：本地（要访问本机网络、要写本地配置文件，云端跑不了）。
- 动作：跑一遍巡检 → 写回 → 备份 → 出简报。
- 简报口径：各意图当前首选与耗时、本轮是否有切换、备选异常；无可用首选才标红。

## 八、已经踩过的坑（写进机制里防复发）

1. **"快"不等于"对"**。`sk_2d` 实测 26 ms，是全场最快，但它只有实时温湿度，没有今日最高/最低，当首选后模板填不出高低温度。现在 `weather.today` 的 `requires_coverage` 含 `temp_range`，它进不了候选池，只写在 `excluded` 里注明用途（实况校准）。
2. **`provides` 写宽了，机器就会信**。`dingzhi` 只有今天/今夜，我一开始把 `temp_range`、`wind` 都写进去，它靠 33 ms 直接上位。巡检器只能校验 `provides` 声明，校验不了字段真假——所以 `provides` 必须人工按实测写，不确定就不写。
3. **不同标的不能放一个池子**。早先把恒生和道指放在 `market.hk_us`，把伦敦金和 COMEX 放在 `market.gold_intl`。结果自动升权时会把道指当恒生报出去、把期货价当现货价报出去。现在一意图一标的，不同标的拆开（`market.hk` / `market.us_dji` / `market.us_ixic` / `market.gold_intl` / `market.gold_comex`）。
4. **只按延迟排序会选错源**。30 ms 的源只给笼统摘要，164 ms 的只给当天，真正能答"明天"的是 169 ms 的那个。覆盖度门禁就是为此加的。
5. **备选掉线不是故障**。open-meteo 偶发不可达，属正常波动；把它当失败会让巡检天天报警，失去意义。巡检只认"连续失败 3 轮"，单轮里 3 次采样挂 1 次不动角色。
6. **降级备用不能只看快慢**。`sk_2d` 28 ms 比 `dingzhi` 164 ms 快得多，但只要温湿度、答不了晴雨；`dingzhi` 能给温度和天气现象。现在降级备用先比"还能覆盖几个必需字段"，覆盖一样多才比延迟。

## 九、接口硬约束（不因机制化而取消）

1. 新浪行情必须带 `Referer: https://finance.sina.com.cn`，否则 403。
2. 新浪返回 GBK，必须 `decode('gbk')`。
3. 中国天气网系（`d1.weather.com.cn`）要带 `Referer: http://www.weather.com.cn/`。
4. itboy 只认城市编码，传中文名 404；编码表复用 `weather.py` 的 `_CITY_CODES`。
5. 美股代码含 `$`（`gb_$dji`），按字面传，别被 shell 展开。
6. `hf_*` 字段顺序与 A 股不同，模板不可照抄，落地时逐字段核对。
7. 休市时段标"收盘价 + 时间"，不能把昨收说成现价。

## 十一、人工介入边界（一句话版）

- 想换人认定的源 → 改 `excluded` / 删候选，写明理由。
- 想支持新的查询标的 → 先往 `config/interface-seeds.json` 加同标的的源，再让建路器跑一次。
- 想加新源到已有标的 → 加到种子册，建路器 `--force` 重建该意图，或用巡检 `--dry-run` 先看排名。
- 不想让某个切换自动发生 → 把 `policy.promotion.min_speed_gain_pct` 调高。
- 巡检自动改了什么 → 看 `config/_backup/` 的备份 diff，和 `changelog`。

## 十二、对话主链接线（2026-11-06）

目标：问一句 → 配置里没有这类查询 → 现场从种子册建一条通路 → 这一轮就用它答 → 同时写回配置。不是留一个命令行工具。

### 接线位置

`src/brain/interaction.py` 的 `handle()` 里新增 **1.3 配置表直达**，排在天气直达（1.4）之前：

| 顺序 | 分支 | 行为 |
|---|---|---|
| 1 | 配置里有这条意图、且有可用首选 | 直接取数作答，静默，60–190 ms |
| 2 | 配了但一个可用首选都没有 | 现场建路（预算 2.5 s），建完即答 |
| 3 | 种子册认识这个标的、配置里还没这条意图 | 新建意图 → 建路 → 即答 → 写回 |
| 4 | 都匹配不上 / 取数失败 | 返回 None，交回原有天气/时间/14B 路径 |

### 关于"要不要说稍等一下"

`voice_loop.handle_audio()` 是单轮单段播报（只做一次 `tts_synthesize`），架构上不支持"先说一句稍等、再合成结果"。本轮的选择是**不说"稍等"**：

- 建路预算压到 `AUTOBUILD_BUDGET_MS = 2500`，超预算的候选记 `health.probe = "skipped_budget"` 进未验证，不拖住回答；
- 建完在答案前加一句可听见的交代："刚把这个查询接上了。"；
- 也就是说：静默 ≤ 2.5 s → 直接给结果 + 一句话说明，不改播报层。

### 解析器为什么写死在代码里

各家的响应格式是供应商私有契约（新浪是逗号分列、itboy 是嵌套 JSON），写进配置比写代码更难维护。`interface_route.py` 按 endpoint 域名分发给五个解析器（`_parse_sina` / `_parse_itboy` / `_parse_wttr` / `_parse_dingzhi` / `_parse_openmeteo`）。新增供应商要加解析器——这是诚实的边界，不假装"纯配置能接任何源"。
