- **版本**：v1.0 · 2026-10-25
- **性质**：技术规格（评审通过，冻结为 ADR-011 + 回填 registry.md；v0.2-draft 审计修订版冻结）

- **对齐**：ADR-001 三层架构 / api-contract L0-L10 能力入口 / protocol-contract 消息信封与错误码 / registry.md 注册纪律 / security-spec 安全基线 / form-expansion-plan §2.2 五大能力底座

## 1. 目标、非目标与边界

### 1.1 目标

在**智能体服务器侧**建立能力插件总线，使 **L1-L10 十个能力域**（意图/领域/执行/编排/表达/呈现/交互/约束/记忆/范式）均可：独立开发、独立验收、运行期热插拔（加载/卸载/替换/回滚），互不踩踏。核心价值：补能力缺失（L3/L6/L7/L8/L9/L10 待建）与全模块热插拔一次解决。

> **边界声明**：L0 终端四 IO（语音/文字进出+渲染+网络协议）归**宿主薄壳**职责（ADR-001），不插件化、不进总线；总线只管理服务器侧能力层。L0-L10 共 11 层，其中 10 层（L1-L10）进总线。

### 1.2 非目标（本期不做）

| 不做 | 理由 | 回补条件 |
|---|---|---|
| 推翻 ADR-001 三层架构 | 总线落在服务器侧，宿主薄壳职责不变 | 架构级新决策 |
| 改动宿主薄壳职责 | 薄壳=四 IO+渲染，不承载智能（ADR-001 硬约束） | 架构级新决策 |
| 跨进程/跨机器插件沙箱 | 阶段一进程内隔离够用（信任模型见 §8.1） | 插件含不可信代码或需强隔离时 |
| 云端插件市场 | 本地优先（产品方案 §3） | 多端形态出现后评估 |
| 插件自行管理配置/权限 | 配置归总线（§7），权限归清单+security-spec（§13） | 永不（集中管控） |

### 1.3 总线与 MCP 插件接入的关系（P0-1 修订）

| 体系 | 职责 | 定位 |
|---|---|---|
| **能力插件总线**（本规格） | 管理**内部能力**：L1-L10 插件的注册/生命周期/依赖/路由/热插拔 | 内部编排层 |
| **MCP 标准层**（form-expansion §2.2⑤，已冻结） | 外部工具/设备/模型的**标准接入通道**（unitree Go2、NVIDIA XR AI 等均为 MCP 接入） | 外部接入层 |

**关系规则**：
1. MCP 工具不是"能力插件"，而是**外部资源**；通过一个**MCP 适配器插件**（属 L3 执行域的一个实现）挂进总线；
2. 能力插件通过总线调用 MCP 适配器 → 适配器转发到具体 MCP server → 结果回总线。能力插件不直连 MCP；
3. 换 MCP server / 加新外部工具 = 配置层换适配器实现或加适配器实例，**不改任何能力插件**；
4. 两套体系不重叠：总线管"内部能力怎么编排"，MCP 管"外部世界的工具怎么接"。

## 2. 架构关系（总线在 ADR-001 中的位置）

```
宿主薄壳（WinUI3·L0 四IO+渲染，可换壳，ADR-001）
        │  HS-001~010（protocol-contract §3.1）
        ▼
┌──────────────────────────────────────────────────────┐
│           能力插件总线（服务器侧·新增强制层）                 │
│  ┌───────────────┬──────────────────────────────┐   │
│  │ 总线内核        │  能力插件（L1-L10，可热插）          │   │
│  │ ·模块清单/注册表  │  L1 意图  L2 领域  L3 执行(+MCP)  │   │
│  │ ·生命周期状态机   │  L4 编排  L5 表达  L6 呈现        │   │
│  │ ·依赖/版本解析    │  L7 交互  L8 约束*  L9 记忆       │   │
│  │ ·内部事件总线     │  L10 范式*                      │   │
│  │ ·追加式运行日志   │  (*=强制驻留，不可热卸载，§5.4)      │   │
│  │ ·热插拔/回滚      │                              │   │
│  └───────────────┴──────────────────────────────┘   │
└──────────────────────────────────────────────────────┘
        │  SD-001~008（protocol-contract §3.2）
        ▼
        设备集群（NAS/传感器/空调…，经 MCP 适配器接入）
```

- 宿主不直连能力插件（api-contract §2 强制：一律走服务器编排，外部不得跳过 L10 范式直达能力）。
- 插件之间不直连，一律经总线（内部消息号，见 §9）。
- 每个能力插件对外暴露接口 = api-contract 对应层的入口函数（`intent.parse / domain.resolve / exec.run / scene.orchestrate / report.compose / voice.speak / dialog.ask / guard.check / memory.read / paradigm.run`），插件实现该接口，总线按接口路由。

## 3. 模块清单协议（Manifest）

每个能力插件必须在包内带一份机器可读清单（`module.json`），总线据此注册与加载。字段（全部必填，缺一拒绝注册）：

| 字段 | 类型 | 必填 | 说明 | 示例 |
|---|---|---|---|---|
| `module_id` | string | ✅ | 全局唯一，小写+连字符，命名规则见 §3.2 | `ultima.memory.lite` |
| `name` | string | ✅ | 模块名（规范中文） | 轻量记忆 |
| `version` | string | ✅ | 语义化版本 主.次.修订（SemVer） | `0.1.0` |
| `capability_domain` | string | ✅ | 能力域：L1~L10 之一（L0 宿主职责，不进总线） | `L9` |
| `entry` | string | ✅ | 插件入口（Python 包导入路径，ADR-004） | `ultima_memory_lite.main` |
| `exposes` | string[] | ✅ | 暴露接口名（**必须与 api-contract 对应层签名一致**，§14 验收项） | `["memory.read","memory.write"]` |
| `deps` | object | 无依赖可空 | 依赖声明：`{module_id: "版本范围"}` | `{"ultima.kernel.events": ">=0.1,<1.0"}` |
| `config_schema` | object | ✅ | 配置项 JSON Schema（校验失败拒绝加载） | 见 §7 |
| `permissions` | string[] | ✅ | 权限声明（scope 格式对齐 security-spec，§8.1/§13） | `["cap:memory.read","cred:local-vault"]` |
| `hooks` | object | ✅ | 生命周期钩子：`on_load / on_activate / on_disable / on_unload / on_rollback` | `{"on_load":"load","on_unload":"unload"}` |

### 3.2 命名规则（P1-5 修订，对齐 api-contract）

- 格式：`ultima.<能力域简称>.<实现名>`；能力域简称**严格对齐 api-contract 入口**：

| 能力域 | 简称 | api-contract 入口 |
|---|---|---|
| L1 意图 | `intent` | `intent.parse` |
| L2 领域 | `domain` | `domain.resolve` |
| L3 执行 | `exec` | `exec.run` |
| L4 编排 | `scene` | `scene.orchestrate` |
| L5 表达 | `report` | `report.compose` |
| L6 呈现 | `voice` | `voice.speak` |
| L7 交互 | `dialog` | `dialog.ask` / `queue.*` |
| L8 约束 | `guard` | `guard.check` |
| L9 记忆 | `memory` | `memory.read` / `memory.write` |
| L10 范式 | `paradigm` | `paradigm.run` |

- 同一能力域允许多个实现（如记忆域：`ultima.memory.lite` 与 `ultima.memory.mem0`），同一时刻仅一个 `routing`（§5.2 替换规则）。

### 3.3 校验

- 清单校验：字段完整 + 版本合法 + 依赖存在 + 权限格式合法 + exposes 与 api-contract 签名一致，任一失败 → 拒绝注册并记录原因（注册事件带 `error_reason`）。

## 4. 运行时注册表

### 4.1 与静态 registry.md 的关系

| 表 | 性质 | 用途 |
|---|---|---|
| `docs/specs/registry.md` | 静态登记（防重复开发，M1 强制） | 立项/开发前查重；登记新插件 |
| **运行时注册表**（本规格） | 内存态，进程启动时由清单加载，事件可持久化 | 总线查询/路由/生命周期管理依据 |

规则：**先静态登记、后运行时注册**。静态未登记的插件，总线拒绝加载（对齐 registry.md"未登记不得使用"）。

### 4.2 注册表数据（每条注册记录）

| 字段 | 说明 |
|---|---|
| `module_id` | 清单字段 |
| `capability_domain` | 能力域 |
| `state` | 生命周期状态（§5.1） |
| `routing_version` | 当前接流量的版本（蓝绿期间唯一） |
| `ready_versions[]` | 已就绪待路由的版本（蓝绿新版，冒烟通过前不入此列） |
| `installed_versions[]` | 已安装版本（回滚用，保留最近 N=3 版，§12） |
| `deps_resolved` | 依赖解析结果（成功/失败+原因） |
| `registered_at / updated_at` | 时间戳（ISO8601 本地时区） |

### 4.3 查询接口（总线内核提供）

- `registry.list(domain?)` → 模块清单 + 状态
- `registry.get(module_id)` → 单条记录
- `registry.resolve(module_id)` → 路由目标（当前 `routing` 实现）
- `registry.find_by_expose(interface_name)` → 暴露某接口的 routing 插件

## 5. 生命周期管理（核心机制）

### 5.1 状态机（P1-3 修订，强制，不允许跳状态）

```
registered ──加载成功──▶ loading ──清单/依赖/冒烟前置校验通过──▶ ready
    │                        │                                  │
    │ 加载失败/校验失败        │ 依赖缺失/接口不符/冒烟前置失败       │ 冒烟通过（§5.2）
    ▼                        ▼                                  ▼
  error ◀───────────────── error                            routing（接流量·服务态）
                                                                 │
                                                      ┌──────────┴──────────┐
                                                      │ 停用请求              │ 连续异常触发回滚(§12)
                                                      ▼                      ▼
                                                   disabling              error（触发回滚 §12）
                                                      │
                                       ┌────────正常─────┴──失败────────────┐
                                       ▼                                  ▼
                                    disabled                           error（触发回滚 §12）
                                       │
                                       ▼
                                    unloading ──清理钩子完成──▶ unloaded
```

- **状态语义**：`ready` = 已加载、校验通过、**但未接路由**（蓝绿新版待命位）；`routing` = 实际接收流量的服务态。蓝绿切换 = 路由转移，不存在"双 routing"。
- 每个状态迁移必须发出总线事件（§9.4），并写追加日志（§10）。
- 插件在 `routing` 期间的异常：首次捕获 → 标记 `error` → 调用方降级（E-5xx 熔断，protocol-contract §4）→ 不拖垮总线（§8）。

### 5.2 替换（热升级）规则：蓝绿切换

同一能力域换实现/升级版本，必须走蓝绿：

1. 新版本加载：`loading → ready`（冒烟前置：清单校验 + 依赖解析 + 静态自检通过），期间旧版继续 `routing` 服务；
2. 新版本在 `ready` 态跑**冒烟校验**（§14 验收项，不发生产流量）→ 通过 → **路由转移**：`ready → routing`（成为 `routing_version`），旧版 `routing → disabling → unloading → unloaded`；
3. 新版本冒烟失败 → 标记 `error` → **自动回滚**到旧版（§12），总线与调用方无感知中断；
4. 冒烟超时上限 30s，超时按失败处理。

禁止：直接卸载 routing 插件再装新版（会造成服务空窗）。

### 5.3 生命周期钩子（清单 `hooks`）

| 钩子 | 语义 | 超时（强制） | 失败处理 |
|---|---|---|---|
| `on_load` | 加载资源/初始化（不对外服务） | 5s | 记 error，卸载 |
| `on_activate` | 进入 ready（就绪待路由） | 5s | 记 error，回滚 |
| `on_disable` | 停止接新请求，排空在途 | 10s | 强制标记 disabled，记异常 |
| `on_unload` | 释放资源/撤销副作用 | 10s | 记 error，进程内清理兜底 |
| `on_rollback` | 回滚时恢复旧版状态 | 5s | 记 error，总线保守继续 |

### 5.4 强制驻留插件（P1-2 修订）

| 插件 | 为什么驻留 | 保护规则 |
|---|---|---|
| `ultima.guard.*`（L8 约束） | 受控执行/越界拦截是安全底线（security-spec） | **不可热卸载、不可禁用**；替换仅允许同域蓝绿（新 guard 冒烟含安全自检）；卸载/禁用需 **Owner 特批** + 期间禁写/禁控制操作 |
| `ultima.paradigm.*`（L10 范式） | api-contract §2 强制"不得跳过 L10 范式直达能力" | **不可热卸载、不可禁用**；替换仅允许同域蓝绿；卸载/禁用需 **Owner 特批** + 期间关闭全部外部调用入口 |

- 总线启动时若 guard/paradigm 缺失或加载失败 → **总线拒绝对外服务**（fail-closed），报环境错误。
- 状态机对这两个域做硬约束：禁止 `routing → disabled/unloaded`（除非特批标记）。

## 6. 依赖与版本约束

### 6.1 依赖声明（清单 `deps`）

- 值一律为版本范围表达式：`>=X,<Y` / `>=X` / `==X`（SemVer 主.次.修订）。
- 仅允许依赖**总线内核**（`ultima.kernel.*`）或其他能力插件；禁止依赖 UI 层/宿主层。

### 6.2 依赖解析规则（总线内核强制）

1. 加载前先解析依赖图，**循环依赖直接拒绝加载**（记 error + 原因）；
2. 版本冲突（两个插件要求同一依赖的不同不兼容版本）→ 加载请求失败，报告冲突双方 module_id；
3. 依赖缺失 → 加载失败，报告缺失项；
4. 解析结果写入注册表 `deps_resolved` 并追加日志。

### 6.3 升级影响面

- 升级某插件前，总线列出其**下游消费者**（依赖它的插件清单）；
- 热升级触发时，下游 `routing` 插件按 §5.2 蓝绿同步切换（新下游 + 新依赖一起验证），失败整体回滚。

## 7. 配置层组合

### 7.1 配置文件

- 服务器侧配置文件（`execution/server/config.json`，权威源）以能力域为 key 选实现：
  ```json
  {
    "capabilities": {
      "L9":  { "implementation": "ultima.memory.lite", "options": {...} },
      "L1":  { "implementation": "ultima.intent.rule",  "options": {...} }
    }
  }
  ```
- 改 `implementation` = 换提供方，**不改任何插件代码**（对齐 ADR-002"主题换皮"哲学推广到能力层）。
- MCP 外部接入在 `config.json` 单列 `mcp_servers` 段，由 L3 MCP 适配器插件消费（§1.3）。

### 7.2 配置校验

- `options` 必须通过该插件 `config_schema` 校验；校验失败 → 该插件拒绝激活，报具体字段错误。

### 7.3 服务发现

- 消费方（编排层）只声明需要什么接口（`find_by_expose`），不写死实现——换实现由配置层决定，消费方零改动。

## 8. 隔离与失败边界

### 8.1 信任模型与进程内隔离（P1-6 修订）

**信任模型（显式声明）**：阶段一**插件=自研可信代码**（仓库内 `execution/packages/`，经代码审查后合入）。第三方/社区插件：
- 进入进程内前必须 **Owner 批准 + 独立安全审查**（eng.security）；
- 未经批准的第三方插件一律拒绝加载（即使清单合法）；
- 含不可信代码或需强隔离的场景 → 直接走 §8.2 阶段二沙箱，不进进程内。

| 维度 | 要求 |
|---|---|
| 异常隔离 | 每个插件调用经总线包裹：try/catch + 超时上限（同步调用默认 10s，可配） |
| 资源上限 | 插件线程数/内存占用电量（默认线程≤4、内存≤512MB，可配置），超限熔断 |
| 权限（P1-4 修订） | 按清单 `permissions` 白名单判定，scope 对齐 security-spec：`cap:<api-contract入口>`（能力调用）/ `dev:<读|写|控制>`（设备操作三独立）/ `cred:<keyId>`（凭证引用）；**禁止路径级文件白名单**（对齐 security-spec "禁任意文件系统直写"基线）；越界拒绝并记审计 |
| 凭据 | 凭据仅经总线注入（凭证引用 keyId 进上下文，明文不出库） |
| 禁止事项 | 插件禁止：直写宿主、绕过总线调其他插件、运行时动态加载/执行未登记代码（import 清单外模块/eval）、自我修改权限声明 |

### 8.2 阶段二（回补条件触发后评估）

- 子进程/沙箱隔离（对齐 dsh bwrap"诚实代码容器，非安全边界"定位）；评估结论另走 TD 流程。

### 8.3 崩溃隔离承诺

- 单插件 `error`：调用方拿 E-5xx + 降级标记（protocol-contract §4 通用规则），总线继续服务其他插件，不整体退出（guard/paradigm 例外：见 §5.4 fail-closed）。

## 9. 模块间通信（内部总线）

### 9.1 信封复用

- 复用 protocol-contract §2 JSON 信封（v/msgId/type/ts/from/to/msgNo/reqId/payload/meta）。
- 内部总线 `from/to` 取值扩展：`server.plugin.<module_id>` / `server.kernel`。
- **契约同步（P2-1）**：本规格发布时**同步变更 protocol-contract**——①新增 §3.3 内部消息号段；②信封 `from/to` 取值扩展登记；③信封 `v` 升版（1→2）并记录变更（涉及新增取值，属契约变更，走 M3 配套）。

### 9.2 内部消息号（P 分类，登记到 protocol-contract §3.3）

| 消息号 | 方向 | 名称 | 载荷要点 |
|---|---|---|---|
| KP-001 | 消费→总线→提供 | 服务调用（同步） | 接口名+参数+会话ID；返回 `{ok,data?,error?}` |
| KP-002 | 消费→总线→提供 | 服务调用（异步） | 同上 + 回调事件引用；结果经 KP-005 回传 |
| KP-003 | 任意→总线 | 事件发布 | 事件名+payload（对齐 HS/SD 事件语义） |
| KP-004 | 总线→订阅者 | 事件派发 | 事件名+payload+来源 module_id |
| KP-005 | 提供→消费 | 异步结果回传 | reqId + `{ok,data?,error?}` |
| KP-006 | 总线→全插件 | 生命周期事件 | 状态迁移通知（§5.1） |

### 9.3 调用规则

- 插件间禁止直连，一律 KP-001/002 经总线；违反=审计项。
- 同步调用超时/失败 → 按 §8.3 降级；异步调用必须带 reqId，防重（api-contract §2 幂等规则沿用）。

### 9.4 事件发布订阅

- 总线维护订阅表；插件可订阅生命周期事件（KP-006）与业务事件（KP-003→KP-004）。
- 订阅注册在 `on_activate` 时声明，`on_disable` 时自动注销（对齐 dsh"注册副作用在卸载时撤销"）。

## 10. 追加式运行日志（对齐 dsh Trajectory）

### 10.1 强制记录范围（模型看到的 = 必记录）

| 内容 | 记录项 |
|---|---|
| 输入侧 | 系统提示、用户输入（语音转文本后）、上下文注入 |
| 推理侧 | 模型推理摘要（reasoning 摘要，不记录原始敏感字段） |
| 行动侧 | 工具/插件调用（接口名+参数+结果）、子模块调度、错误与降级 |
| 输出侧 | 汇报文本、渲染指令（HS-005）、语音状态 |

### 10.2 日志特性（强制）

- **只追加不修改**：日志文件只 append，禁止改写历史记录（对齐"追加式会话日志"）；
- 每条记录带：时间戳（毫秒）+ 会话ID + 来源 module_id + 事件类型 + 载荷引用；
- 敏感字段脱敏（key/凭证/隐私，security-spec §3）；
- 支持按 会话/时间/来源/事件类型 检索；后续支持回放与分叉（回补条件：日志量级与检索需求明确后评估）。

### 10.3 与现有审计的关系

- 追加日志 = 运行期事实流；现有审计器（eng.audit 工单审计）= 结果核对。两者并存：日志供回放取证，审计供结论闭环。

## 11. 热插拔触发入口

### 11.1 入口（阶段一）

- 总线内核提供 CLI：`python -m ultima_bus <command>`，命令集：

| 命令 | 动作 | 结果 |
|---|---|---|
| `bus list [domain]` | 列出注册表 | 模块/状态/版本 |
| `bus load <module_id>` | 加载插件 | 状态迁移 + 日志 |
| `bus unload <module_id>` | 卸载插件（非 routing 或经替换流程；guard/paradigm 需特批） | 状态迁移 |
| `bus switch <module_id> <version>` | 蓝绿热升级/换实现 | 冒烟 → 切换/回滚 |
| `bus rollback <module_id>` | 回滚到上一版本 | 回滚记录 |
| `bus status` | 总线健康（各插件状态/资源占用） | 状态表 |

- 阶段二+：宿主征询入口（HS-007/008 复用）——对话里说"换记忆实现"→ 总线执行，仍走同命令语义。

### 11.2 操作留痕

- 每次热插拔写**变更记录**（追加式）：谁触发（CLI/对话/配置变更）/ 何时 / 从哪版到哪版 / 结果（成功/回滚+原因）。记录落 `sync/plugin-ops.jsonl`。

## 12. 失败回滚

### 12.1 触发条件

- 蓝绿切换冒烟失败（§5.2）；
- routing 插件运行期连续异常（阈值：5 分钟内 ≥3 次 error）→ 总线主动回滚到上一稳定版本并告警。

### 12.2 回滚规则

| 项 | 规则 |
|---|---|
| 版本保留 | 每插件保留最近 3 个版本（`installed_versions`），超出清理 |
| 回滚动作 | 新版本 `disabling → unloaded`（走 `on_rollback`），旧版本重新 `loading → ready → routing` |
| 依赖联动 | 依赖它的下游插件若因版本不兼容失败，一并回滚到与旧版匹配组合（§6.3） |
| 结果记录 | 写 `sync/plugin-ops.jsonl` + 追加日志；回滚失败 = 高优审计项（eng.audit） |

## 13. 安全约束（对齐 security-spec）

| 项 | 要求 |
|---|---|
| 权限声明 | 插件清单 `permissions` 白名单（scope 见 §8.1）；未声明的能力调用一律拒绝 |
| 强制驻留 | L8 guard / L10 paradigm 不可热卸载，特批与降级规则见 §5.4 |
| 受控执行 | 写/控制/删除类操作先征询（HS-007）或按 L8 guard.check 判定，默认最小权限 |
| 供应链 | 新插件引入前：License 审查（不采 GPL 底座）+ 依赖 CVE 扫描（security-spec §3）；第三方插件另走 §8.1 批准流程 |
| 审计独立 | 插件自述不代审；总线/插件行为由 eng.audit / eng.security 独立核查 |

## 14. 验收口径（DoD 级，可测）

| # | 验收项 | 通过标准 |
|---|---|---|
| 1 | 清单校验 | 缺失字段/非法版本/非法权限/exposes 与 api-contract 不一致 → 拒绝注册并记录原因 |
| 2 | 注册/查询 | `bus list/get/find_by_expose` 返回正确 |
| 3 | 加载/激活 | 走完整状态机（含 ready→routing），事件齐全，日志有记录 |
| 4 | 依赖解析 | 正常解析通过；循环依赖/版本冲突/缺失 → 拒绝+报告 |
| 5 | 蓝绿热升级 | 服务无空窗（无双 routing）；新版本冒烟失败 → 自动回滚，调用方无感 |
| 6 | 崩溃隔离 | 单插件异常 → 其他插件与总线继续服务，调用方拿 E-5xx+降级标记 |
| 7 | 配置换实现 | 改 config `implementation` → 换提供方，消费方零改动 |
| 8 | 内部总线 | KP-001/002 同步异步调用成功，事件订阅/注销正确 |
| 9 | 追加日志 | 记录范围覆盖 §10.1；只追加不可改；检索可用；敏感字段脱敏 |
| 10 | 回滚 | 触发条件成立即回滚，版本保留 3 个，ops 记录完整 |
| 11 | 安全 | 越权调用被拒；凭证明文零出现；新插件供应链审查留痕 |
| 12 | 权限边界 | 未声明能力调用 → 拒绝并记审计 |
| 13 | **强制驻留** | 对 guard/paradigm 执行 unload/disable → 被拒（无特批）；总线启动缺二者 → fail-closed |
| 14 | **接口一致性** | 随机抽查插件 exposes 与 api-contract 签名逐字段一致 |
| 15 | **MCP 接入** | L3 MCP 适配器插件经总线调用外部 MCP server 成功；换适配器不改能力插件 |
