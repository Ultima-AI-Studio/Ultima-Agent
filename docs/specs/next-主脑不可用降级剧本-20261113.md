# Next 主脑不可用降级剧本（R-47）

> 状态：**已定五级梯子，参数为初值，N-04 实测后冻结**｜ 日期：2026-11-13
> 关联：`next-基础能力盘点与缺口清单-20261113.md` 结构性问题 3；R-24（本地数据不出本机）、R-29（主脑只做查/登记/汇报）
> 一句话：**先查清原因，再决定重启、换外脑，还是转离线只记账。不许一挂就静默。**

---

## 一、五级梯子（按序执行，不跳级）

```
L0 探活 → L1 诊断分类 → L2 重启（限次） → L3 外脑接替（限授权） → L4 离线紧记录
```

| 级 | 做什么 | 不做 | 允许跳级吗 |
|---|---|---|---|
| L0 | 探主脑存活（进程 + 端口 + 模型可用） | 不做任何判断 | — |
| L1 | 把"不可用"分成 6 类原因码 | 不重启、不换脑 | 否（原因不明禁止重启） |
| L2 | 按原因码决定是否重启，限次数 | 不无限重启 | 仅 L1 判为"可自愈"才进 |
| L3 | 外脑接替（需用户已配置且授权） | 不外发记忆/习惯/本地文件 | 否 |
| L4 | 转离线，只做紧记录 | 不出方案、不验收、不签冻结 | 否 |

## 二、L0 探活

| 项 | 值 | 说明 |
|---|---|---|
| 探活间隔 | **15s** | 与 Shell 的 Guardian（20s 探 8756）错开，避免同拍 |
| 失败判定 | **连续 2 次** | 单次抖动不算挂（防瞬时 GC/加载误判） |
| 探活方式 | ① 进程存在 ② `127.0.0.1:11434` TCP 可连 ③ `GET /api/tags` 返回 200 且含主脑模型 ④ `GET /api/ps` 显示模型已驻留 | 四步全过才算 alive |
| 探活超时 | 单步 **3s**，任意一步超时即记该步失败 | 不许无限等 |

> **主脑不自己重启自己**。按 R-34「牵扯本地的动作由主脑执行」，主脑挂了就没人执行——所以**重启动作归 Shell.Guardian**（宿主级、无窗后台），不由主脑发起。这是本剧本最关键的分工。

## 三、L1 诊断（六类原因码）

> **判据已按 R-58 收口（2026-11-13）**：主脑形态 = **`llama-server` 独立子进程**，端点 `127.0.0.1:11435`，探活 `/health`，回读 `/props`。下表即为**验收依据**（形态已定，原"待重定、不得作验收依据"的注作废）。

| 码 | 现象 | 判据（`llama-server` 子进程口径） | 可自愈 | 下一步 |
|---|---|---|---|---|
| `MB-P1` 进程不在 | 主脑子进程不存在 | Job 内查不到 `llama-server.exe`，或命令行 `--instance-token` 与本次启动令牌不符 | ✅ | → L2 |
| `MB-P2` 端口不通 | 11435 拒绝连接 | TCP connect 失败，或 `/health` 非 200 | ✅ | → L2 |
| `MB-P3` 模型未加载 | 进程在、模型没起来 | `/props` 无 `model` 字段或为空；日志含 `failed to load model` | ✅ | → L2 |
| `MB-P4` 内存不足 | 启动即退出，日志含 OOM / 分配失败 | 日志关键串 + 退出码 | ⚠️ 条件可自愈 | 先降 `n_ctx` 或换登记表里的 `q4km` 档，**走 §六 备案，不许静默降级** |
| `MB-P5` 响应超时 | 连接正常但首 token > **30s** | 连续三次超时 | ❌ | → L3 |
| `MB-P6` 锁/并发占用 | 端口或权重被占 | 11435 被**非本应用**进程监听；或 `.gguf` 文件锁被另一进程持有 | ✅ | → L2（**等占位释放，非强杀**） |

**判死活的纪律**：先按 `--instance-token` 认"是不是我们的进程"，再判在不在——**不得用 PID、进程名白名单或单次查询判定**（§15.9 硬规则 8；`Get-Process` 与 `Get-CimInstance` 结论相反已在 2026-11-13 实测证实）。

**诊断必须落一条记录**：`{ts, code, evidence:{进程/端口/props/log 摘要}, 判定, 采取动作}`，进本地日志。原因不明的**禁止进 L2**——盲目重启只会掩盖真故障。

## 四、L2 重启（限次、限界）

### 4.0 执行者已有实现，不需要新写一套（2026-11-13 读码核实）

应用自愈这件事在 v1 已经落地，分两块：

| 能力 | 实现 | 归属 |
|---|---|---|
| 探活 + 拉起 + 失败限次 + 冷却 | `src/host-shell/UltimaAgent.HostShell/ProcessHost/GuardianService.cs`（0054 内化 watchdog） | **Shell**（宿主级） |
| 子进程树随宿主回收（崩溃不留孤儿） | `JobObjectManager` + `ChildProcessSupervisor`（0052） | **Lifecycle** |
| 任务注册表 | `config/host-tasks.json`（`restart.policy = guardian / manual`） | Shell |

Guardian 的既有常量（与 0054 裁决一致）：探活间隔 **20s**、拉起后静置 **3s**、连续失败 **3 次**进冷却、冷却 **300s**、拉起走 **CreateNoWindow**（零控制台），全过程落事件（`guardian_started` / 探活记录 / `restart_failed` / `cooldown_ended`）。

### 4.1 现状缺口：只守一个目标，且目标写死

读码发现两处硬编码，决定了"主脑能不能被自愈"：

1. `GuardianService.cs` 里 `const string taskId = "agent-server";`，并且探活用 `_probe.IsAgentReadyAsync`（固定打 `http://127.0.0.1:8756/health`）——**它守着 agent server 一个目标，不遍历注册表**。
2. `config/host-tasks.json` 现在只有两条：`agent-server`（guardian）、`voice-launcher`（manual）。**主脑根本不在名单里**（v1 主脑是 Ollama 服务；Next 主脑后端改 llama.cpp，见 R-57）。

所以当前事实是：**机制在、名单不全、目标写死**。主脑挂了没有人守，不是因为没做自愈，而是因为它没被登记。

### 4.2 因此 L2 落到实现上只有三件事

1. **Guardian 改遍历**：读 `host-tasks.json`，凡 `restart.policy=guardian` 的任务逐条守，**每条独立失败计数与独立冷却**（不能共用一套计数，否则一条坏任务会把别的拖进冷却）。
2. **探活器按任务类型分派**：`http-health`（8756 / 11435 这类）/ `process-exists`（纯进程型）。现在只有 http-health 一种。
3. **登记主脑条目**（形态已定 = `llama-server` 子进程，R-58；参数取自基线 §16.2，此处为落 N-05 时的示例）：

```json
{
  "id": "mainbrain",
  "name": "Main Brain (llama.cpp)",
  "executable": "llama-server.exe",
  "arguments": [
    "-m", "%LOCALAPPDATA%\\UltimaAgent\\models\\qwen3-8b-q5km.gguf",
    "-c", "4096", "-b", "512", "-t", "7", "-np", "1",
    "--host", "127.0.0.1", "--port", "11435",
    "--instance-token", "<uuid>"
  ],
  "health": { "kind": "http-health", "port": 11435, "path": "/health" },
  "restart": { "policy": "guardian", "check_interval_seconds": 15, "fail_limit": 2, "cooldown_seconds": 30 }
}
```

> 注意主脑这条的间隔与限次和 agent-server **不同**（15s / 2 次 / 30s）：主脑不可用会直接触发 L3/L4 降级，需要更快判定；而 agent server 是宿主命脉，拉太急会自己把自己拖死。两类目标共用一套参数是错的。

### 4.3 触发后仍走本剧本的梯子

Guardian 只负责"发现 + 按策略重启"，**它不做诊断分级**。重启失败/被限次之后，仍要进 L1 记原因码、按码进 L3 或 L4——否则就退化成"无限重启掩盖真故障"。

**归属定论**：主脑**不自愈**（它挂了就没人执行本地动作，见 R-34），自愈由 **Shell.Guardian 代为执行**，进程回收由 **Lifecycle** 兜底。这不是新增模块，是把已有守护扩成多目标。

| 项 | 值 |
|---|---|
| 重启执行者 | **Shell.Guardian**（宿主级，无窗后台；禁止弹窗引导用户手动启动） |
| 重启后的复探 | **10s 内**四步复探 |
| 频次限流 | **30s 内只重启一次**；**连续 2 次**重启仍失败即停手 |
| 停手后 | 直接进 L3，并记 `restart_exhausted=true` |
| 禁止 | 连续第 3 次重启；强杀正在加载的进程（会损坏模型缓存，对应 `MB-P6` 的"等占位释放"） |

## 五、L3 外脑接替（唯一允许外发的情形，且需授权）

**准入四条，缺一不进**：

1. 用户**安装或设置时已配置外脑**（R-10 允许自定义指派）；
2. 用户**显式授权过"主脑不可用时允许外脑代答"**——默认**关闭**；
3. 任务被标记为**可外派**（见下"不外派清单"）；
4. 网络与外脑端点可用（不可用则直接进 L4）。

**外发内容的硬边界（不许突破 R-24）**：

| 允许外发 | 禁止外发 |
|---|---|
| 当前这一轮的**指令文本**与必要上下文摘要（脱敏后） | 记忆库、习惯库、权威源、范式文件原文 |
| 模型能力所需的公开知识 | 本地文件路径、文件内容、用户名/凭据 |
| 用户明确同意发送的片段 | 任何"整库打包"形态的数据 |

**不外派清单（外脑也接不了，只能等主脑恢复）**：
记忆写入、习惯总结、权威源变更、打 tag、本地登记、验收签署、冻结——这些都属于"牵扯本地"的动作（R-29/R-34），外脑**只能出建议文本，不能执行**。

**界面必须明示**：四角壳显示"主脑离线，外脑代答"（黄），外脑的回复带统一前缀标识，禁止让用户误以为是主脑在答。

## 六、L4 离线紧记录（外脑也不可用）

**只做三件事**：入队、打戳、留因。

```
{
  "id": "<任务ID>#<轮次>",        // 去重键，恢复后按此幂等重放
  "ts": "ISO-8601 本地时间",
  "cause": "MB-P5 | MB-P4 | no_network | no_extbrain",
  "request_digest": "<指令文本的 sha256 前 16 位>",
  "payload_ref": "<本地暂存路径>",  // 原话/附件指针，不外发
  "replayed": false
}
```

| 规则 | 内容 |
|---|---|
| 状态 | `DEGRADED-OFFLINE`，四角壳常驻黄标"主脑离线，仅记录" |
| 不做 | 不出方案、不做验收、不签冻结、不写记忆、不改权威源 |
| 恢复后 | 按 `ts` 顺序重放；`replayed` 置 true 再执行；同一 `id` 只执行一次 |
| 恢复判定 | L0 四步全过 + 连续 2 次探活成功 |
| 丢弃 | 只有用户显式删除才丢；**不许自动清理**（离线期间的输入是用户的话，不是垃圾） |

## 七、验收判据（可机检）

| 门 | 判据 |
|---|---|
| 原因可辨 | 六类码各有可复现的注入方式，注入后诊断码必须正确，且**原因不明时不重启** |
| 重启限次 | 模拟连续失败，第 3 次重启**必须不发生**，`restart_exhausted=true` |
| 无窗 | 重启全程零控制台窗口（复用 0054 的零窗四要素） |
| 外发可控 | 关掉授权后，任何路径都不得产生外网请求（抓包/日志断言 0 条） |
| 外脑不越权 | 外脑代答期间，本地写操作（tag/登记/记忆）必须 0 次 |
| 离线不丢 | 离线输入 10 条 → 恢复后按序重放 10 条，无重复、无丢失 |
