# pd-20261113 · Console 与 Manager 归属裁决（能力层口径）

- **状态**：已裁决（Owner 2026-11-13）
- **影响面**：Next 架构分层、T13 壳边界、HUD/任务面板数据源、探针下发链路
- **一句话**：**Console 与 Manager 都是「能力」，不是壳、也不是并列的独立产品线**；Console 负责**任务编排 + 编排后的跟踪与反馈**，Manager 归 Console 管理、**负责下发探针并回收结果**。

---

## 一、裁决原文（Owner 表述）

> "Console 和 Manage 是能力当中的一部分，它是对任务编排之后的跟踪和反馈用的。任务下发后探针是谁下的？是 Manage 下的。Manager 归 Console 管理。任务编排就应该是 Console 的能力。"

## 二、这条裁决纠了什么

此前的口径（本仓 2026-11-13 两处文档）把 Console / Manager 当成"另一条产品线"，并据此建议**"Console/Manager 不并入客户端进程树、只经本地 API 对接"**。该建议**作废**。

错在两处：

1. **归属错**：把能力层组件当成外部系统 → 会导致"任务编排无处落脚"（壳不该编排，外部产品又不在客户端域）。
2. **因果错**：把"进程要分开"推出成"产品要分开"。真正的约束只是**进程隔离**（能力层与壳解耦），不是产品割裂。

## 三、定界（可机检口径）

| 层 | 归属 | 职责 | 不该做什么 |
|---|---|---|---|
| **壳**（`UltimaAgent.exe` / `HostShell.exe`） | 客户端域 · 表现与生命周期 | 窗口、托盘、UI 呈现、进程拉起与回收、Guardian 探活 | **不编排任务**、不判任务状态、不下探针、不写队列状态 |
| **Console** | 客户端域 · **能力层** | **任务编排**（派发/调度/优先级/依赖）+ **编排后的跟踪** + **反馈**（结果汇总/回写/呈现数据源） | 不直接改 UI 控件、不越权写队列唯一状态源 |
| **Manager** | 客户端域 · **能力层** · **Console 的子模块**（Console 是它的管理层） | **只做两件事**：对任务**下探针** + **反馈任务生命周期**（当前在跑哪些、已完成哪些、某任务处于哪一阶段/由哪个执行端在做） | 不自作主张改任务目标、不编排、不绕过 Console 直接对外派活 |

数据流（单向，不回头）：

```
壳（UI）  ──触发──▶  Console（编排）
                        │  下发任务
                        ▼
                     Manager（下发探针 / 采集执行面）
                        │  探针结果
                        ▼
                     Console（跟踪与反馈：汇总、判状态、回写队列）
                        │  呈现数据
                        ▼
                     壳（只展示，不改判）
```

**判定口径**：谁决定"做什么/先做哪个" = Console；谁负责"做完没有/卡在哪"的采集 = Manager；谁负责"让人看到" = 壳。三者任一跨界即为越界。

## 三之补 · 二次澄清（Owner 2026-11-13 同日）

> "Manager 是 Console 的子模块，Console 是它的管理层。Manager 只是对任务下探针和反馈任务生命周期用的。比如当前有哪些正在执行的任务、已经完成了哪些，或者某个任务在某个状态下是在 Codex 开发还是 DeepSeek 审计——举例，不一定未来是这两家。"

据此再收三层：

1. **从属关系定死**：Manager **不是并列能力层组件，而是 Console 的子模块**；Console 是它的管理层。对外只认 Console 一个门面，Manager 不单独对外。
2. **职责只有两件**：① 对任务**下探针**；② **反馈任务生命周期**——"当前哪些在跑 / 哪些已完成 / 某任务处于哪一阶段、由哪个执行端在做"。**不含编排**（编排是 Console 的），也**不含判态裁决**（判态在 Console）。
3. **执行端不绑定厂商**：Codex / DeepSeek 只是当前示例，Manager 的模型是"执行端=可插拔标识"，字段取值来自实际派发记录，**禁止硬编码厂商枚举**。

**形态结论**（结掉上一版"同进程/两进程未定"）：Manager 作为子模块运行于 Console 之内（同进程），**不单独起进程**；确需拆进程属架构变更，须新开裁决。

**生命周期视图（最小字段，建议值待 Owner 确认）**：`task_id` / `state`（排队·执行中·审计中·已冻结·阻塞·失败）/ `stage`（当前阶段名）/ `executor`（执行端标识，可空）/ `updated_at` / `probe_seq`（探针序号，防旧读数覆盖新读数）。

## 四、落地约束

1. **进程隔离而非产品割裂**：Console / Manager 是客户端域内的能力层进程（可与壳分进程、由生命周期管理拉起），但**属于本产品**，不是外挂系统。
2. **壳零编排**：壳侧禁止出现编排/调度/探针逻辑；现有 HUD/任务面板只做**读展示**（数据源走 Console 的反馈面）。
3. **队列唯一状态源不变**：`tasks/queue/queue-status.json` 仍由编排链写，Console 不得绕过状态机直接改 state（既有"直接写 state 仅 state_machine.py 一处"铁律继续有效）。
4. **探针只有一个下发方**：任务下发后的探针**只能由 Manager 下发**；壳、Console、语音侧都不得各自下探针（否则同一任务多份口径）。
5. **Manager 的对外接口只面向 Console**：其他组件要任务态，一律问 Console，不直连 Manager。
6. **注册/登记不重复实现**：派发登记仍走既有登记链（G-DISPATCH-001），Manager 不另起一套登记。

## 六、任务点位（Manager 反馈的主视图，2026-11-13 追加）

**问题**：只报"状态"（QUEUED / EXECUTING / AUDIT …）回答不了"这个任务现在卡在哪一步"。Owner 要的是**点位**：在做方案？在派工单？在写数据？在审计？还是已交付。

### 7.1 九个点位（封闭枚举，不得自造）

| # | 点位 code | 中文 | 判据（怎么证明它就在这一点） | 权威源 |
|---|---|---|---|---|
| 1 | `intake` | 需求受理 | 需求已登记（需求文档或明确 Owner 指令） | requirements / 对话确认 |
| 2 | `planning` | 做方案 | 方案文档已落盘、**工单卡尚未生成**（G-PLAN-001） | `docs/plans/*` |
| 3 | `workorder` | 派工单 | 工单卡存在且 DoR 五项全绿、**尚未派发** | `tasks/queue/wo-*.md` |
| 4 | `queued` | 已排队 | 队列 `state=QUEUED` | `queue-status.json` |
| 5 | `executing` | 执行中 | 队列 `state=EXECUTING`；`activity` 细分见 7.2 | `queue-status.json` + 运行记录 |
| 6 | `selfcheck` | 自检 | 队列 `state=SELF-CHECK` | `queue-status.json` |
| 7 | `auditing` | 审计 | 队列 `state=AUDIT`；修复轮见 `fix_round` | `queue-status.json` |
| 8 | `fixing` | 有界修复 | `state=AUDIT` 且 `fix_round ≥ 1`（审计打回后的修复轮） | `queue-status.json` |
| 9 | `delivered` | 已交付 | `state=COMPLETED` **且** 冻结 tag 已打 **且** 已推送/合并 | git + 冻结记录 |

**异常位（与点位并列，不占点位序号）**：`blocked`（带 `blocker` 必填）/ `failed` / `cancelled`。

映射要点：**点位 4–9 是对既有队列状态的投影**（不新造状态机）；**点位 1–3 在队列外**，由"方案文档 / 工单卡是否存在"判定。所以点位**不是第二套状态源**。

### 7.2 执行中的细分（回答"是不是在写数据"）

`executing` 带 `activity` 子值（**暂定值**：Owner 2026-11-13 认可先按此写入，后续实测再微调；微调只增删子值，不改点位语义）：`plan_write`（写方案/文档）/ `code_write`（写代码）/ `data_write`（写数据/落盘产物）/ `tool_call`（调工具/外部接口）/ `awaiting_executor`（已派给执行端、尚未回第一包产物）。

### 7.3 停滞标记（"停在这一步多久"）

点位不变但超过阈值 → 打 `stalled=true`（**不是新状态**，只是标记）：

| 点位 | 停滞阈值（建议值） |
|---|---|
| planning / workorder | 24h |
| executing | 2h 无新事件 |
| auditing / fixing | 2h |
| queued | 24h（排队久说明 WIP 上限或执行端不可用） |

### 7.4 展示视图（一行一问全答完）

列：**任务 / 现在在哪一点（含 activity）/ 谁在做（executor）/ 停在这一步多久 / 堵在哪（blocker）**。

### 7.5 五条硬规则

1. **只投影不造状态**：Manager 不得写 `queue-status.json`，不得自造 state；点位由状态投影 + 产物存在性判定得出。
2. **每次点位变更必带证据**：`stage_entered_at` + 证据指针（文件路径 / 事件 / commit），无证据不得推进点位。
3. **禁止推断**：探针只能取证据，不能"看日志猜"；取不到就报 `unknown`，不许猜一个点位填上。
4. **点位单调**：只允许 `auditing ↔ fixing` 循环，其余不得回退；异常位之外不得跳点。
5. **一个任务只有一个当前点位**：多执行端并行时按"最早未完成的点位"报，不并列报多点。

### 7.6 验收（可机检）

| 门 | 判据 |
|---|---|
| 四问全答 | 任取一个在跑任务，视图能答"在哪一点/谁在做/停多久/堵在哪" 4/4 |
| 五态判定 | 造 5 个停在 planning / workorder / executing / auditing / delivered 的任务，点位判定 5/5 正确 |
| 停滞识别 | 某任务 3h 无事件 → `stalled=true` 且阈值未误报其他任务 |
| 零反写 | Manager 全程 0 次写 `queue-status.json`（diff 断言为空） |
| 不猜 | 证据缺失时点位 = `unknown`（不是猜一个值） |

> 点位表是**封闭枚举**：新增点位必须走变更（改本节 + 同步视图与断言），不得在执行端自行扩一个。
