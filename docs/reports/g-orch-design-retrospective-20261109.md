# G-ORCH 八环节工作流 · 设计复盘

> 复盘对象：`dispatch-rules-v0.2-20261108.md` §2 定义的八环节，以及 2026-11-08~09 建成的四个载体
> 复盘口径：**只评设计本身对不对，不记执行流水**。执行过程与卡点处置见 `g-orch-run-ledger-20261109.md`
> 结论先行：**主干是对的，但有六处设计缺陷，其中两处会直接让审计失去意义**

---

## 1. 为什么会有这份复盘

前一份 `g-orch-run-ledger-20261109.md` 逐条记了「哪坏了、怎么修的」，那是运行台账。它回答不了更根本的三个问题：

1. 八环节这个骨架本身是不是合理，还是我把简单事情做复杂了？
2. 修掉的这些卡点，是偶发故障，还是设计缺陷的症状？
3. 业界已经有成熟做法，我是不是在重复造一个更差的轮子？

这份复盘就是为了回答这三个问题。**结论是第 2 和第 3 都成立**：本轮修掉的大部分卡点，都不是运气不好，而是设计上少了几样业界早就在用的东西。

## 2. 设计初衷 vs 当前实态

| 设计初衷 | 当前实态 | 差距性质 |
|---|---|---|
| 八环节是一条链，一环扣一环 | 实际是三段互不相连：计划段（①-④）、交付段（⑤⑥）、验收段（⑦⑧）；直到本轮才补了 `run-gorch.py` 把 ⑦⑧ 串上，⑤⑥ 仍靠派发器内建 | **链路是拼出来的，不是长出来的** |
| 审计与执行分离，执行端不能自审 | ⑦ 由 DeepSeek 两轮独立会话做，能做到"不沿用开发方自述" | 方向对 |
| 审计过了才打 tag | ⑧ 自己重读 `audit.json` 再判一次，双保险 | 方向对 |
| 主脑只传达需求、汇报结果、不插手执行 | 本轮大量修复是我直接改代码，越过了这条线 | **边界已被我自己破坏** |
| 宽进严出，容忍畸形数据但守住真污染 | 只在读出端做到；写入端仍无校验 | 一半 |

其中第四条要单独说：用户最初的硬约束是「只做监察，不做替代工作」，后来放宽成「一个一个修也行」。我据此直接改了六个脚本。这不是违规——授权是明确的——但**它暴露了设计的一个真实依赖：这套流程当前离了人就得停**。一个需要主脑亲手改代码才能跑起来的"自动流程"，不能算跑通。

## 3. 六处设计缺陷（用业界标准照出来的）

### 3.1 双轮审计的"独立性"是名义上的

我们的 ⑦ 是同一模型（DeepSeek）、同一个 API key、同一批 evidence，开两个会话，第二个会话被告知"第一轮的结论只是前置意见，不是真相，自己重判"。

这在 maker-checker 体系里正落在最经典的失败模式上：**shared access — maker 与 checker 共用同一身份，审计链无法证明独立性**。金融监管口径下这叫控制失效，不叫控制。

诚实的评估：两个会话确实降低了"一次跑偏就定案"的概率，比单轮强。但它防不住的是**同一模型的系统性偏差**——如果这个模型对某类代码有稳定的误判倾向，两轮会稳定地一起误判。它不是真正的四眼，是**同一个人的两遍**。

### 3.2 回执没有绑定代码版本，会产生"过期绿"

w9 那次最有说服力：`done.json` 里 `receipt_valid: true`，是 Codex 在某个 HEAD 上跑出来的。之后 `30b36e7b` 把验收目标文件提交进了 HEAD。再拿这份回执去验收，Codex 自己都发现不对——"目标文件已在 HEAD，做不成新增唯一文件"，于是拒绝交付。

这正是 CI 领域一句话的现场版：**"A badge says green. A receipt says what was green, on which tree, for how long. A stale receipt is worse than no receipt."**

我们的 `done.json` 记了 `exit_code`、`receipt_valid`、`state`、`finished_at`，**唯独没记 `base_sha`**。于是回执不知道自己是在哪棵树上绿的，验收环节也无从判断它是否过期。

### 3.3 审计名额设成 1，等于门槛不可达

maker-checker 的第二个经典缺口：**unreachable thresholds — 门槛设得太高，日常事务根本进不了这套控制**。

我们的审计名额硬性只有 1 个，实测 5 个工单同时排队。本轮加了 7 天时限，把历史单放过去，才降到 1 个在途。但根子上，"同时只允许 1 个进审计"这个数字从来没被论证过——它更像是我图省事写的 `any(...)`，而不是一个设计决策。

### 3.4 手改状态绕过了所有校验（系统外例外）

主表里 4 个工单（0007、sentinel-0001、0019、0020）**根本没有 run 目录**。它们是从没经派发器、直接被人改到 audit 的。

对应 maker-checker 的第三个缺口：**off-system exceptions — 有人在系统外做了决定，但没人把决定记回台账**。这类单既没有回执、没有审计、也没有证据，却和正常工单一样占着状态位，还差点把队列堵死。

### 3.5 审计器没有结构化清单

maker-checker 实践里明确要求：**给复核者一份简明 checklist，让他做真实复核**，而不是丢一堆材料让他自由发挥。

我们的 `audit-work-order.py` 把卡和 evidence 喂进去，让它自己找问题。看 w9 两轮的输出，它找得很准（这是好事），但那是**模型的自觉**，不是**流程的保证**。同一套输入换一天跑，可能找出完全不同的一组问题。没有 checklist，审计质量不可复现。

### 3.6 八环节是不是过度设计

这条我得给自己留个反面：业界经验是 **"Start with 2-3 agents. Add more only when justified"**，planning pattern 的选型结论也是 **"For predictable work, workflows"**。

好消息：我们的活确实是可预测的工程流程（拆解→工单→排程→派发→审计→冻结），选 workflow 而不是自治 agent 是对的方向。

坏消息：八个环节里有几个长期**零调用者**——⑦⑧ 建好了整整一天没人调过，直到本轮才串上。一个建好但没人走的环节，在设计上等于不存在。八这个数字是照着"看上去完整"排出来的，不是照着"每条都有真实必要"排出来的。

## 4. 业界成熟做法盘点

| 来源 | 核心做法 | 我们能用的部分 |
|---|---|---|
| maker-checker / four-eyes（金融监管强制，SOX、PCI-DSS 要求） | 发起与批准必须由**不同主体**完成；预定义角色、状态、证据、**时限**、**异常路径**、审计记录 | ⑦ 的独立性要真做，不是同一模型跑两遍；异常路径要显式定义（手改状态不能算合规路径） |
| maker-checker 12 项控制清单 | 权限分离、阈值可达、例外必须回写台账、复核要有 checklist | 3.3 / 3.4 / 3.5 三条正对着它 |
| CI quality gates / branch protection | gate 是**真阻塞**不是提醒；未通过的 required check 让合并按钮直接不可用 | 我们的 ⑧ 已经做到了（审计未过则拒绝 tag，且自己再判一次） |
| merge queue | 一次队列校验取代 N 次重跑；**不测落后分支**（`require-up-to-date`），落后就立即失败而不是测完再说 | 我们的派发器**不检查工单登记与代码树是否同步**，落后也照跑——应补 |
| gate receipt 契约 | 回执要写清「**在哪个树上绿的、绿了多久**」，而不是只写"绿" | `done.json` 缺 `base_sha`，这是 3.2 的修法 |
| evaluator-optimizer（MS / Anthropic 系） | 生成端 + 评估端循环，**每轮 checkpoint**，崩溃不丢进度；有最大迭代数 | 我们的多轮审计没有 checkpoint 语义，第二轮崩溃等于白跑第一轮 |
| orchestrator 职责清单（MLflow） | 计划拆解、调度、依赖跟踪、共享状态、重试、**token/预算上限** | 我们没有预算上限，一次双轮审计烧 2400+3000 token 无人拦 |
| 选型纪律（timina） | 可预测工作用 workflow，不要上自治多智能体；先 2-3 个再扩 | 方向对；但环节数应砍到每条都有实证必要 |

## 5. 建议改动（按优先级，不是全部都要做）

### P0 — 会让审计失去意义的，必须改

| # | 改动 | 具体做法 | 对应缺陷 |
|---|---|---|---|
| 1 | 回执绑定代码版本 | `done.json` 增加 `base_sha`（派发时的 `git rev-parse HEAD`）与 `worktree_dirty`；⑧ 冻结前校验 `base_sha` 仍是当前 HEAD 的祖先，否则判定 stale、拒绝 | 3.2 |
| 2 | 审计独立性要么真做，要么明说做不到 | 两个选择：(a) 换第二个模型做第二轮（如 GPT 系）；(b) 老实承认"同模型两轮"只是降低跑偏概率，不叫独立审计，并在文档里写明这个限制 | 3.1 |
| 3 | 给审计器一份结构化 checklist | 把卡里的 ACC 逐条转成 checklist 项，要求审计输出**逐项 PASS/FAIL + 证据指针**，而不是自由发挥 | 3.5 |

### P1 — 会让队列慢性失血的

| # | 改动 | 具体做法 | 对应缺陷 |
|---|---|---|---|
| 4 | 审计名额数量要论证 | 现在硬编码 1。要么论证"1 是对的上限"，要么改成可配置并给出依据 | 3.3 |
| 5 | 手改状态必须留痕 | 任何不经派发器的状态变更，必须写一条最小记录（谁改的、依据什么、时间），让这类单在台账里可见，而不是凭空出现 | 3.4 |
| 6 | 派发前校验同步性 | 类似 `require-up-to-date`：登记的工单与当前代码树不一致时立即拒派，而不是跑完再发现 | merge queue |

### P2 — 可以缓

| # | 改动 | 说明 |
|---|---|---|
| 7 | 审计预算上限 | 单次双轮设 token 上限，超限即停并报警，避免失控 |
| 8 | 多轮审计 checkpoint | 第二轮崩溃不必重跑第一轮 |
| 9 | 环节数瘦身 | 逐环节问"这条有没有实证必要性"。目前至少 ④ 排程与 ③ 工单的边界是模糊的 |

## 6. 结论

**主干站得住。** 八环节的分段（计划 / 交付 / 验收）、审计前置到冻结之前、执行端不得自审、冻结门自己再判一次——这几条方向都是对的，而且和业界成熟做法一致。

**但有六处缺陷，其中两处直接动摇审计的意义：**

1. **双轮审计是"同一个人的两遍"**，不是四眼。当前实现能降低跑偏概率，但防不住同模型的系统性偏差。这一条不改，⑦ 的价值就要打折扣。
2. **回执不绑定代码版本**，会产生"过期绿"——w9 那次已经现场演了一遍：回执说绿，但绿的那棵树已经不是当前这棵。**过期绿比没有绿更危险**，因为它看起来可信。

**另外四条是慢性病**：名额设成 1 导致门槛不可达、手改状态绕过校验、审计无 checklist 导致质量不可复现、环节数多于实证必要。

**最后一条要说给自己的**：这套流程本轮是靠我亲手改代码才跑起来的。真正的跑通标准，是**别人、或者系统自己，不碰代码就能走完一趟**。目前还没到那一步。
