# 评审

## 一、事实与口径

1. **性能数字全部是作者自测，文档直接当"成立"用**。88.78ms 冷启动、2394 条/s 写入、110 万条 99.8ms 启动——这些是单机、单作者、无并发争用下的数字，且未说明硬件、SQLite 配置（WAL/synchronous）、是否含投影。要成立需：给出测试脚本与硬件规格、在你们目标开发机复跑、并给出 p99 而非均值。文档 §1 把"视频 <0.1 秒即 88ms，成立"写成结论，这是把宣传口径换算成事实，不是验证。
2. **"一周 4549 star"被当作"热度真实"的证据**。star 数不证明工程质量，也不证明机制在你的栈里可迁移。要成立需：至少 3 个非作者的生产使用报告，或你自己跑通一条端到端流水线。
3. **"命中 8 条 BLOCKER/HIGH"是作者自己做的映射**，0056 的缺口编号与 M1–M9 的对应关系未经独立复核。要成立需：逐条给出"缺口原文 → 机制哪一段 → 为什么这机制能堵"，且由不写这份稿的人复核。
4. **"运行时 0 依赖"只覆盖 npm 依赖**，Node ≥ 24 本身、SQLite 原生绑定、以及它调用的 Codex CLI 都是供应链面。要成立需：列出完整运行时闭包（含 Node 版本 EOL、better-sqlite3 之类原生模块的 CVE 状态）。
5. **"MIT 允许拷代码"被轻描淡写**。MIT 只解决版权，不解决专利、不解决你方"新增代码模块化封装 + 旧版冻结"的内部约束，也不解决把 TS 逻辑翻成 Python 时的行为等价性。要成立需：License 审查记录 + 翻译后的等价性测试，而不是"本稿只借机制"一句话带过。

## 三、A/B/C 排序

**B > C > A**。

- **B 是产品侧正解**，理由文档自己说了：单栈单源、治理不破。代价是等 0057/0059，可接受。
- **A 只做开发期加速器**，判定正确。
- **C 的"不存在双源"不成立。**

C 说"外挂与引擎只走 HTTP 事件+回执 JSON、不共享数据库，所以不存在双源"——**这是把"不共享存储"偷换成"不存在双源"**。双源的定义不是"共享同一个数据库"，而是"同一个事实有两个可写副本、且没有单一裁决者"。C 里至少三处双源：

1. **队列状态双写**：Autoloop 的 run 状态（queued/claimed/done/cancelled）与 `queue-status.json` 的八态是两套状态机，适配层要把一边翻成另一边。适配层崩了、或回执丢了，两边就不一致，且没有裁决者——因为"队列仍是唯一事实源"只是文档里的一句话，不是机制。
2. **回执与 note 双写**：§3 说"回执落到 `docs/reports/fix-*.md` 与队列 note"，这是两个写点，不是一次事务。回执写成功、note 写失败，就是双源。
3. **claim 双源**：Autoloop 的 claim 幂等只在它自己的 SQLite 里成立；你的队列若也允许"重派"，两个 claim 语义叠加，谁先谁后没有定义。

**怎么堵**：适配层必须是**单向、幂等、可重放**的——队列是唯一写入口，Autoloop 只读事件、只写回执到一个**收件箱目录**（不是直接写 note），由队列侧一个消费者把收件箱回执**一次事务**并入队列并写 note；收件箱回执带 `claim_id`，重复投递按 `claim_id` 去重。这样"双源"退化为"一个写者 + 一个幂等收件箱"，才成立。文档 §3 第 3 点"对账点只有一个"是口号，不是机制。

## 四、作者没意识到的风险

1. **数据一致性**：C 形态下 Autoloop 的 SQLite 与 `queue-status.json` 无跨库事务，适配层崩溃窗口内两边状态分叉，且无对账脚本。文档只说"对账点只有一个"，没给对账算法。
2. **并发与幂等**：`claim` 幂等在 Autoloop 内成立，但你现有 `dispatch-work-order.py` 是否也幂等未验证；两个 claim 语义叠加时，"同一份活被两个执行端领走"的窗口没被分析。
3. **Token 与费用**：M1"挂起零消耗"成立的前提是"会话可续接"，但续接时上下文重放会重新计费；文档把"三天零 token"当结论，没算续接时的重放成本。M4 跳数上限 8 只限深度不限宽度，一个节点扇出 8 个仍可指数烧钱。
4. **审计独立性**：C 形态下 Autoloop 的 run 回执进入 `docs/reports/fix-*.md`，而这份报告是审计输入之一。外挂层由开发侧维护，等于让开发侧间接影响审计输入——与"审计独立于开发"红线冲突。文档 §5 只说"它的审查独立不采纳"，没意识到外挂层本身污染审计输入。
5. **许可与供应链**：Node ≥ 24 进开发机、SQLite 原生绑定、Codex CLI 版本漂移，三者任一变动都可能让"回执格式"变。文档只提"将来真引代码需审查"，但 C 形态是**现在就引运行时**，审查时点错了。
6. **注意力成本**：M7 解决"反复轰炸"，但 C 形态新增一个 Node 服务、一个适配层、一个收件箱，运维告警本身会成为新的注意力消耗源。文档 §6.5 抄"默认安静"，但没算外挂层自己的告警预算。

## 五、若只采纳 3 条

选 **M3、M4、M7**，先落 **M3**。

- **M3**：`dispatch`/`composer` 入参 schema 中，`access`/`cwd` 字段随事件传入必须被拒收，且有一条负例测试通过——可机检。
- **M4**：构造 9 层自触发事件链，第 9 层只写日志不派活，断言派活调用次数 = 8——可机检。
- **M7**：同一 `ask.key` 在卡片未关闭时第二次 `ask` 不产生新卡片，断言卡片表行数不变——可机检。

三条都是低代价、不依赖 M2、不碰冻结参数、不新增产品承诺。

## 结论

**改条件后推进**：C 形态可保留，但"不存在双源"必须改成"单向写入口 + 幂等收件箱"的机制描述并补对账脚本；M2/M8/M9 降级为 v1.1 提案不进本轮；外挂层不得写入审计输入路径。否则按现稿推进，等于用一个未定义的双源换一周开发速度。
