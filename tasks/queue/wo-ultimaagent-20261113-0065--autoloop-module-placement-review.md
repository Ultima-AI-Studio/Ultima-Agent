## 0. 范围冻结

**本单只做**
1. 独立评审一个问题：Autoloop 融合方案（含 P0／P1／P2 三阶段与 §11 归属表）**应挂在 Next 基础能力六块中的哪一块／哪几块**。
2. 复核方案 §11 已有的六行归属裁定：逐行给出「维持／改判／反对」三态之一，并附模块职责原文引文与坐标。
3. 复核 0061／0062／0063 三张卡的写入域是否与其归属模块一致（卡写的地方，是否正是它被判定归属的那一块）。
4. 产出评审报告一份（新增文件，路径见 T1）。

**本单不做**
- 不改基线、不改方案文档、不改三卡、不改队列、不改 tracker、不写任何实现代码。
- 不评审方案的技术正确性（协议细节、Gate 是否可机检等属 0066 骨架评审范围；本单只裁「挂哪一块」）。
- 不新增模块、不改「模块数仍是六块」的口径。
- 不对 0061／0062／0063 做开工前审卡（那是另一张审卡单的事）。

## 2. 任务明细

### T1 · 报告骨架与依据清单

**文件**：`docs/reports/review-autoloop-module-placement-0065.md`（新建，UTF-8）

**写什么**
1. 按 §1 结论／§2 模块职责事实表／§3 方案 §11 六行裁定／§4 双源判定／§5 三卡写域核对／§6 未决与建议落点／§7 自证 的段序建立骨架，先落盘再填内容。
2. 依据清单逐项列出实际读取的文件路径与版本标识（方案 v0.3 ＋ §11、三卡文件名、架构页行区间、基线章节号）。
3. 每完成一个 T，把该 T 的证据追加写入本报告，禁止把结论攒到最后一次性补写。

**验收（Gate T1）**
1. 报告文件存在，七段标题齐全且顺序与上文一致，可 `grep` 到每个段标题。
2. 依据清单中每个路径均真实存在（逐条 `Test-Path` 或等价命令，输出留证）。
3. 报告内不含凭记忆写的模块职责，凡称「模块职责」处必须已附坐标。

**禁止**：不得在 T1 就写出最终结论；不得把报告写成方案复述。

### T2 · 六块职责事实表

**文件**：同 T1 报告 §2

**写什么**
1. 从 `docs/tracker/next-基础能力架构-20261113.html` §02 与 §04 逐块摘录职责原文一句话（Core／Senses.Voice／Shell／Surface／Memory／Middleware），每条附行号。
2. 单列 Console 与「治理⑤ 横切」两条：说明它们不是六块之一，各自管什么、边界判据原文为何。
3. 摘录基线中与队列／票据／状态机归属相关的定案原文（§21.2～§21.7 中与「谁持有写权」有关的句子、§22 任务库归属、§25 主链各节的模块落点），每条附章节号与行号。
4. 若某块职责原文与方案 §11 的归属判断存在字面冲突，本 T 只记录冲突，不裁决。

**验收（Gate T2）**
1. 六块 ＋ Console ＋ 治理⑤ 共八条职责摘录齐全，每条带文件＋行号。
2. 每条摘录为原文直引（可被 `grep` 命中），不得改写或概括后仍标为原文。
3. 记录的冲突项逐条可回指到具体两处原文。

**禁止**：不得只写块名不写职责；不得把「我以为」写进事实表。

### T3 · 方案 §11 六行归属裁定

**文件**：同 T1 报告 §3

**写什么**
1. 逐行重述方案 §11 表中的归属判断（P0 三件套→Middleware.queue_engine；M3→Middleware.delegation 主体＋治理⑤约束；M4→Console.orchestration；M7→Core 澄清出口＋Surface 呈现；session_id→Core↔Voice 对话信封；cancel_observe→Middleware.state_machine＋Shell）。
2. 每行给出三态裁定之一：**维持／改判／反对**，并写明理由链：模块职责原文 → 该方案部件的行为性质 → 为何落这块而不落另一块。
3. 改判或反对的行必须给出具体落点（落到哪个模块的哪个子件、对应哪一节或哪张卡），不得只写「不合适」。
4. 单列一节回答「是否应新增第七块」：给出是／否与理由；若答「是」，必须同时说明为何六块口径可以变更（否则视为与本单 §0 冲突）。
5. 独立判断要求：若你的结论与方案完全一致，必须给出至少一条方案未写、由你补上的归属边界（例如某个部件的第二归属或禁止项），不得只做认同式复述。

**验收（Gate T3）**
1. 方案 §11 表中每一行都有三态裁定，未裁定行数为 0；每行均带理由链与坐标。
2. 「是否新增第七块」有明确结论；结论与「模块数仍是六块」口径的关系被写明。
3. 至少存在一条非复述性判断（改判、反对、或方案未写的补充边界），可被单独引用。
4. 三态用词固定为「维持／改判／反对」，可 `grep` 统计。

**禁止**：不得用「建议进一步研究」代替裁定；不得把裁定写成对方案的整体表扬。

### T4 · 双源判定与三卡写域核对

**文件**：同 T1 报告 §4／§5

**写什么**
1. 审方案「写口在 Middleware.queue_engine、读视图在 Console」这一判定：按「同一事实两个可写副本且无单一裁决者＝双源」的定义，判断该安排在什么条件下不是双源、在什么条件下会退化成双源；给出可机检的判别句。
2. 核对 0061：其写域（`tasks/queue/inbox/`、`scripts/queue-writer.py`、`scripts/reconcile-inbox.py`）是否正落在被判定归属的那一块；有无越到 Console 或 Shell 的写入。
3. 核对 0062：§27.1～§27.4 各自落在 M3／M4／M7／session_id 的归属模块，卡内是否出现「同一契约两处主文」。
4. 核对 0063：其唯一写域为基线 §25.10 段内，是否与「state_machine 定义八态」的归属一致；`CANCELLED_PENDING` 是否被写成第九态。
5. 每张卡给一条结论：**写域与归属一致／需调整（说明调整点）**。

**验收（Gate T4）**
1. 双源判定给出「成立条件」与「退化条件」两侧，且判别句可被脚本执行（指明查什么文件、什么字段）。
2. 三卡各有一条结论，用词固定为「一致」或「需调整」；「需调整」必须写明具体行或字段。
3. 三卡结论均有卡内坐标（文件＋行号或 T 编号）支撑。

**禁止**：不得用「大体一致」这类不可判定表述；不得在未读卡的情况下给结论。

### T5 · 总验收与自证

**文件**：同 T1 报告 §6／§7

**写什么**
1. §6 列未决项：本单无法判定的问题、需 Owner 拍板的点、建议后续动作（每条给承担方与落点）。
2. §7 自证：证据清单（逐 T Gate 结果 ＋ 命令输出）、抽检回读（随机抽取报告中不少于 5 条坐标，回读原文核对一致并附输出）、越界声明（无＝明确写「无」）。
3. 报告结论行：`T5_GATE=PASS` 或 `T5_GATE=FAIL`，并写明结论等级（通过／有条件通过／不通过）。

**验收（Gate T5）**
1. 抽检回读不少于 5 条坐标，逐条给出「坐标→原文片段→一致／不一致」。
2. 越界声明逐项列：基线／方案／三卡／队列／tracker／代码各自是否被改，未改须写「未改」。
3. 结论行存在且与 §1 结论一致；两者矛盾即本单不通过。

**禁止**：不得自行提交、打 tag、更新队列或宣布冻结；不得把未运行的检查写成已通过。
