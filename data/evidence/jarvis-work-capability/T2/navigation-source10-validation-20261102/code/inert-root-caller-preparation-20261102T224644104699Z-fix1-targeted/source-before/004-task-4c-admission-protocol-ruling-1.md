## RC-03: durable consumption before the caller's fallible claim

A caller with identical readable inputs and no successful state change cannot distinguish an earlier failed open from a first invocation. Another caller-side file or rename alone does not solve a failure before any filesystem mutation. Reusing the same readable release after such a failure is forbidden. A new native launcher/controller, secret authentication system and retry scheme are outside scope.

Ruling: use a fixed two-message CLI handoff and a separately ROOT-created durable dispatch record bound to this one live entry. No new native process ownership algorithm is introduced.

1. The reviewed CLI still takes no arguments. It captures ENTRY_NS before case-specific I/O and a fresh process-entry UUID4 nonce, prints one small flushed HELLO JSON with its actual os.getpid(), nonce, ENTRY_NS and fixed candidate/caller identity, then waits for exactly one ROOT go/abort line on stdin. No P4/native/helper/socket/headless operation occurs before a valid bound grant. Waiting time remains charged to ENTRY_NS; no timer renewal. Empty/abort/malformed input fails. No interactive user action is required; ROOT drives the existing exec session.
2. After the HELLO and only after code/independent reviews are clean, ROOT may create NEW V/inert-root-dispatch.json, durably close it, then issue the separately bound V/inert-root-release.json. The dispatch is the authoritative consumed1/max1/retry0 allocation receipt, fixed to exact caller manifest, live HELLO pid/entry nonce/ENTRY_NS, scope and release identity. Release binds its raw hash and the same entry tuple. ROOT never launches a replacement caller or reissues this allocation. If ROOT cannot close the dispatch/release, it sends abort and does not grant work. These are future runtime data, never created by preparation code or author.
3. ROOT sends one strict go object binding the dispatch hash. The caller validates current ROOT release/dispatch raw hashes and exact typed entry tuple before any P4/native work. A new process has a different entry nonce even if its PID is reused; it cannot reuse the release. The reviewed process also consumes an in-memory one-entry guard before attempting work, so calling run twice within that entry is refused. No CLI/environment/parameter can choose or renew the actual entry tuple.
4. The original caller-created exclusive claim remains an additional immutable diagnostic barrier, not the sole durable consumption authority. Failure before claim creation still leaves the ROOT dispatch consumed. Record permanent failure outside the case if possible; if writes are unavailable, ROOT's dispatch remains authoritative and effects stay unknown. Do not retry, remove old objects, choose another UUID or promote a missing result. A pure mocked pre-creation failure followed by both same-entry replay and a new-entry replay must show no extra P4/native/headless call.

This is the smallest non-controller handoff that represents the required failure. Cost if wrong: a consumed allocation may fail without a caller result; ROOT must retain that unknown failure rather than retry. This is preferable to silently reusing the release. Actual execution of the handshake remains a separately released, independently reviewed operational step.
